# ADR 0004：自译分层——应用内草稿存进度库，贡献产出走导出脚本人工对照

- 日期：2026-10-07
- 状态：已接受
- 延续：应用 ADR 0002（官方教程全量翻译是内容基准）；主仓库 ADR 0037/0053
  （进度库随仓库走）、0052（激励与统计同回路，自译不判分不入掌握度）

## 背景

应用内允许学习者在正文段落上写自己的中文译文（自译），有两个动机：

1. 学习动作本身：对官方段落挑错、精读、写出自己的译法，是深度精读；
2. 反哺上游：目标是将来把译文整理成 PO 文件提交给 gtkmm-documentation
   上游（GNOME Damned Lies / MR），作为对官方教程翻译的贡献。

既有产出链路（sync_upstream.py / export_contribution.py）的语义是：
快照 `zh` 字段是「我们的现行译文」（唯一手写内容，进版本库）；
`export_contribution.py` 以 `po/reference.zh_CN.po` 为骨架，把快照 zh
按指纹填进贡献 PO——基准里空/fuzzy 的条目直接填，与上游社区译文不同的
条目**不自动覆盖**，写入 `contribution-report.json` 的 differs 清单供
人工确认后替换。

## 决策

1. **自译草稿存进度库，不就地写内容层。** 应用内保存的自译进
   `learning.db` 的 `my_translations` 表（按段落 sha）。快照 JSON 与
   PO 是内容层，只由构建期脚本（sync_upstream.py / apply_po.py /
   export_contribution.py）与人工编辑维护；应用运行时对内容层只读。
   「官方译文不允许在应用里被改写」由此结构性保证。

2. **正文显示分层并存。** 有官方译文的段落：官方译文照常显示，
   学习者的译法以「我的译文」块并排在其下（订正候选）；待译/待复核
   段落：自译块顶替「此段待译」徽章显示。

3. **贡献产出：自译经导出脚本并入既有流程。** export_contribution.py
   额外读取 `my_translations` 作为译文输入源（有自译的段，自译优先
   作为「我们的译文」）：待译段（快照 zh 为空）按填空处理；已有官方
   译文的段进 differs 清单，人工确认更优后手工替换进快照 zh / PO，
   下次导出即成为贡献文件里的正式译文。草稿永不自动进入贡献 PO。

## 后果

- 应用对内容层只读的边界不破；贡献内容的定稿动作（人工确认、写入
  快照 zh）留在 git 可审的脚本/人工侧。
- 学习者的订正想成为正式译文需要两步（应用内写 → 人工确认进 zh），
  这是「尊重上游社区译文」的既有代价，换来贡献文件永不含未复核草稿。
- 自译按段落 sha 寻址：原文变更后 sha 变化，旧自译成为孤儿留在库里
  不再渲染（与快照 stale 机制同理，无需额外清理）。
