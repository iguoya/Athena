# Athena 学习工作台：手册主导 + 渲染期挂载

- 状态：参考提案，尚未实施
- 平行方案：`docs/LEARNING_WORKSPACE_PROPOSAL.md`（提案 A：内容结构）、
  `docs/LEARNING_WORKSPACE_LOOP_ENGINE.md`（方案 B：闭环引擎）
- 界面草图：`docs/LEARNING_WORKSPACE_SKETCH.html`（探索阶段的可视化参考，浏览器直接打开；
  不是实现规格，已落地的真实原型见 `ui/workbench_page.h/.cc`）
- 目的：在 `AGENTS.md`「项目定位与学习内容」已经定义的文档—代码关系**之内**设计工作台，
  而不是另立一套关系模型
- 约束：同 A、B——不替代 `AGENTS.md`、`docs/ARCHITECTURE.md` 或已接受的 ADR；
  所有名称、字段、交互都是候选，需经原型验证并写入 ADR（下一个编号为 0020）才成为实施方向

> **修订说明（本文第 2 版）**
> 第 1 版把文档和代码写成"台面上两件**对等**的料"，并提出在 Markdown 里写一行绑定标记。
> 重读 `AGENTS.md` 后判断这两点都不成立：项目定义的关系是**不对称**的（文档主导、
> 代码从属、C++ 语义仲裁），而把绑定写进文档会给"文档按实验切节"开一个口子。
> 本版按既有约束重做，并把第 1 版里唯一值得保留的东西——"工作台不生产内容"——
> 落到一个更省的机制上：**渲染期挂载**。

## 1. 先把你已经定义的关系写清楚

`AGENTS.md`「项目定位与学习内容」定义的不是"两个并列的工件"，而是一个**不对称三角**：

```text
                    正确的 C++ 语义
                    （唯一仲裁者，不在仓库里）
                          ↑
                     核对 │
                          │
                    学习文档  ────决定教什么、教到什么边界────┐
                    （主导方）                                │
                          │                                  │ 派生
                     反哺 ↑                                  ↓
                    「这里讲漏了/讲错了/边界没说清」      代码实验
                                                          （从属方）
                                                       把思想变成
                                                       可观察的行动
```

四条来自 `AGENTS.md` 的规则，是这张图的全部依据：

1. 文档是"知识体系、概念语义、适用边界、常见误区和思维模型的主要载体"，
   **不得按源码结构写成源码说明书，不得由总结现有实现反向决定教什么**。
2. **教学方向由知识点和学习文档主导**，代码负责把思想转化为短小、真实、可运行的行动。
3. 不一致时，**先依据正确的 C++ 语义核对文档**，再让代码覆盖经确认的学习目标；
   不得为迁就当前实现而删减或扭曲知识点。
4. 实验反馈**可以**揭示文档的遗漏、错误和认知边界，推动知识体系修正深化；
   但**不能从当前实现反向限定应学习的内容**。

工作台设计必须落在这张图里。下面四节是我读完这些约束后认为值得补充的判断。

## 2. 建议一：两种"缺口"性质完全相反，不能对称处理

从"文档主导、代码派生"直接推出：

```text
◇ 有文档、无实验    正常状态。纯理论、原则和工程思想本来就不该硬造函数
                    （AGENTS.md 已明确"不强行生成函数"）。这不是缺口。

◈ 有实验、无文档    真正的债。意味着存在一个"不知道自己在教什么"的实验——
                    它只能是从实现反向长出来的，正是规则 1 禁止的东西。
```

本文第 1 版把两者对称地列成"空工位看板"，那是错的：它会制造"每节文档都该配一个实验"
的暗示，而那正是规则 4 的反面。

**建议**：`scripts/generate_project.py check` 只报告一种情况——**孤儿实验**
（`subchapter` 没有任何文档小节声明它在教什么）。文档侧不统计"覆盖率"，
因为文档不需要被实验覆盖。

## 3. 建议二：绑定关系不能写进 Markdown，应该住在配置层

第 1 版提议在文档小节后写一行 `> 实验 \`cpp.Reference.const_reference\``。放弃它，理由：

- 一旦文档里能声明实验，作者写文档时就会开始考虑"这一节能不能挂一个实验"，
  于是**小节切分被实验可得性影响**。这是"写成源码说明书"最隐蔽的形式——
  不是抄源码结构，而是为了让每节都挂得上实验而切节。规则 1 禁止的正是这个方向。
- `AGENTS.md` 已经规定 `resources/athena.json` 是项目配置的唯一数据源，
  承载知识点元数据。"这个知识点由哪一节文档讲"就是知识点元数据。
- 现成的先例：`chapter.overview_document` 已经是"章 → 手册内某份文档"的指针
  （ADR 0012）。本文要的只是把同一件事做到知识点粒度。

**结论：文档保持 100% 普通 Markdown，一个字符都不为 Athena 而写。**
绑定写在 `athena.json` 的 `subchapter` 上：

```json
{
  "name": "const_reference",
  "title": "const 引用",
  "description": "理解 const 引用的只读语义及临时对象绑定规则。",
  "teaches": {
    "document": "resources/articles/cpp/reference_overview.md",
    "heading": "2.2 const 引用：能绑定临时对象，还能延长它的寿命"
  }
}
```

按**标题文本**而不是 `athena-heading-N` 定位：现有锚点是文档内出现顺序编号
（`render/markdown_renderer.cc`），插一节就整体错位；标题文本改了则 `check` 直接报错，
这是想要的行为——标题变了本来就该重新确认这一节还在不在讲这个知识点。

方向也对得上规则 2：是**知识点声明"我在哪一节被讲到"**，不是文档声明"我这里能跑什么"。
文档不知道 Athena 存在，代码不知道文档存在，`athena.json` 作为知识点定义层持有这条指针。

## 4. 建议三：判定学习者预测对错的依据是语义，不是 stdout

这是我认为方案 B 里唯一和你的约束冲突的地方，也是最容易被忽略的一条。

方案 B §4.1 的理由是单选预测"能被机器直接和实际结果比对"。但规则 3 说得很清楚：
仲裁者是**正确的 C++ 语义**。而运行输出可能是未定义行为、实现定义行为，
或只是这台机器这套编译器这次的表现。把"实际输出"当成正确答案，等于把仲裁权
从语义交给了 stdout——恰恰是规则 3 禁止的"迁就当前实现"。

**建议**：预测选项自带正确项标记，来源是作者或 AI 对**语义命题**的判断；
运行输出的角色是**证据展示**，不是判卷依据。三类情况分开处理：

```text
输出即证据            多数运行时知识点。判定用预设正确项，输出用来看"果然如此"
输出不构成保证        UB / 实现定义 / 平台相关。卡片必须显式标注这一点，
                      否则工作台会亲手教出"我跑过一次所以是对的"这种坏习惯
根本没有输出          编译期知识。AGENTS.md 已说"不必伪造运行输出"，
                      此时预测—对照闭环仍然成立，只是证据换成类型或诊断
```

第三行顺带说明：闭环不依赖 stdout，所以它对编译期知识同样适用——
这比方案 B 的"运行按钮 + 输出比对"覆盖面更宽，成本却没有增加。

## 5. 建议四：给"实验反哺文档"一个真实出口

规则 4 允许实验反馈推动文档修正，但 A、B 和本文第 1 版都没有把它落成一个动作。
偏差账本因此只有一个出口（学习者的误解清单），另一个方向浪费了。

**建议**：预测失败后，除了自动记一条偏差，再给一个可选按钮：

```text
[这节文档没讲清]  →  追加一条文档待办：
                     文档 / 小节 / 我当时以为什么 / 实际语义是什么 / 日期
```

约束（直接来自规则 4）：这条待办的合法内容**只能是"文档这里要补、要改、要说清边界"**。
它不允许表达"这个知识点没实验所以别讲了"或"按当前实现改文档"。生成的待办进
一个纯文本清单，由人决定改不改——工作台不自动改文档。

这样偏差账本有了两个出口，正好对应约束里的两条路径：

```text
偏差 ──┬──▶ 我的误解清单        （学习者侧：我哪里想错了）
       └──▶ 文档待办清单        （文档侧：文档哪里没讲到）
```

## 6. 工作台设计

### 6.1 一句话

**工作台 = 手册页（文档主体）+ 渲染期挂载的实验入口 + 右侧实验坞 + 一条台面状态。**
不新建内容，不改文档，不改实验执行模型。

### 6.2 渲染期挂载

这是本文唯一的新机制，也是"配合但分离"的落点：

```text
写作期    文档作者写纯 Markdown，不知道有实验
配置期    athena.json 的 subchapter 声明 teaches.document + teaches.heading
渲染期    render_markdown_html() 拿到「标题 → 知识点」表，
          在匹配的小节末尾插入一个纯 HTML 链接卡片
阅读期    点它 → 已有的链接拦截 → 右侧实验坞打开该知识点
```

挂载**只发生在渲染期**。文件系统上的 `.md` 永远是干净的，`git diff` 里看不到任何
Athena 痕迹；`markdown_renderer` 是共享层，这个插入逻辑可以用现有的
`tests/markdown_renderer_test.cc` 直接测。

插入的是纯 HTML 链接（`athena://knowledge/<id>`），不需要 JS 桥接——
`ArticleView` 的两个后端（WKWebView / WebKitGTK）**已经**在
`decidePolicyForNavigationAction` / `decide-policy` 里拦截链接激活，
只需给契约加一个 `set_link_handler`，两端对称实现即可。

### 6.3 布局：主从，不是对等双轨

```text
┌ 手册 · C++ ······································ 台面：偏差 3 · 待办 1 ┐
├──────────────────────────────────────────┬─────────────────────────────┤
│ 目录     │ 2.2 const 引用                │ 实验坞                      │
│          │                               │                             │
│ 2.1 引用 │ 普通的非 const 引用不能绑定    │ const 引用                  │
│ ▸2.2 c…  │ 右值，因为右值理论上"用完就    │                             │
│ 2.3 传参 │ 该消失"。const 引用打开了这个  │ 真实源码（聚焦本函数）       │
│⚠2.4 返回 │ 口子，同时编译器会把临时对象   │ void const_reference(…)     │
│          │ 的生命周期延长到……            │ { … }                       │
│          │                               │                             │
│          │ ┌───────────────────────────┐ │ 先判断：临时对象何时销毁？   │
│          │ │ ▶ 动手验证：const 引用     │ │  ○ 表达式结束               │
│          │ └───────────────────────────┘ │  ○ 引用存活期间             │
│          │      ↑ 渲染期插入，文件里没有  │  ○ 函数返回时               │
│          │                               │ [▶ 运行]                    │
│ 2.3 值传递 vs 引用传递                    │ 输出 …                      │
│          │ 函数拿到的是副本还是本体……     │ ⚠ 你选「表达式结束」        │
│          │                               │ [为什么我错了][这节没讲清]  │
└──────────┴───────────────────────────────┴─────────────────────────────┘
```

- **文档占主，实验坞占从**，宽度比例固定表达"谁主导"。这不是审美选择，
  是让规则 2 在界面上可见。
- 实验坞初始为空，提示"从左边文档里点一个实验开始"。它是文档的**下游**，
  不是可以独立驾驶的第二条轨道。
- 代码章节页 `CodeChapterPage` **原样保留**，作为从代码侧进入的入口。
  "不能只有文档、不能只有代码"讲的是**学习闭环**必须含读和做，不是要求把两个
  入口合并成一个页面。
- 窄窗口：实验坞降级为覆盖在文档上的抽屉，从卡片点开、可关闭；不做三栏挤压。

### 6.4 台面：会话与两份清单

工作台之所以是"工作台"而不是"手册页"，只靠两件事，都不涉及内容：

1. **台面记得你在做什么**：顶部状态条显示未消化的偏差数和文档待办数，点进去是两份清单。
2. **两份清单会长**：`我的误解清单`（可导出为 Markdown，放用户数据目录，
   不进仓库——它是学习者的痕迹，不是教学内容）和 `文档待办清单`。

不做知识地图、不做 7 阶段状态机、不做复习队列（复习队列留到真的有偏差积累之后再说）。

## 7. 数据与模块边界

```text
表示层
MainWindow
└── HandbookPage（增强，不新建 WorkbenchPage）
    ├── ArticleView            + set_link_handler（两端对称实现）
    └── ExperimentDock         复用 SourceView + ExperimentRunner

GTK 无关
├── TeachingIndex              athena.json 的 teaches → 「文档+标题 → 知识点」双向表
├── markdown_renderer          + 渲染期挂载（已有测试文件可直接扩展）
├── DivergenceLog              偏差记录 + 两个出口
└── LearningStore              + divergence 表、+ doc_todo 表
```

- `TeachingIndex` 是唯一的新领域概念，输入是配置和标题列表，输出两张 map，
  GTK 无关、可直接用 Google Test 验证。**一旦它开始长关系类型、权重或多对多，
  就说明它在变成 A、B 都判定为不值得的知识图谱，应当停手。**
- `MainWindow` 不感知 `teaches`、预测和偏差；跨章节跳转仍然经它。
- 不改 `FunctionRegistry`、`ExperimentRunner` 和现有实验函数签名。
- `check` 校验：`teaches.document` 必须在同分类 `handbook_documents` 里
  （与 ADR 0012 对 `overview_document` 的既有校验同构）；`teaches.heading`
  必须能在该文档中唯一匹配；报告孤儿实验。

## 8. 分期

- **Phase 0**：`teaches` 字段 + `TeachingIndex` + `check` 校验 + 渲染期挂载 +
  `set_link_handler` + 实验坞只显示源码和运行（**先不做预测**）。
  只给 `cpp.Reference` 四个知识点配 `teaches`。
  验证：读文档时"想动手"的那一下，点一次就到位，是否真的比现在来回切页顺畅。
- **Phase 1**：预测单选（正确项来自配置或 AI，**不从输出解析**）+ `divergence` 表 +
  自动对照。两周后只看一件事：偏差表在涨吗（沿用方案 B 的 go/no-go）。
- **Phase 2**：两份清单成形——误解清单导出、文档待办清单、目录上的 ⚠ 标记。
- **Phase 3（只在真被需要时）**：复习队列与间隔调度、反事实"换一个条件"、会话落地页。
- **永不，除非被真实使用证明需要**：知识图谱、7 阶段 `LearningSession`、
  Markdown 自定义指令、滚动位置联动、多种 `EvidenceKind` 呈现器、执行模型改造。

## 9. 与提案 A、方案 B 的关系

| | 提案 A | 方案 B | 本文（第 2 版） |
|---|---|---|---|
| 文档—代码关系 | 文档被吸收进"学习主线" | 文档基本不参与 | 按 `AGENTS.md` 的不对称三角：文档主导、代码派生、语义仲裁 |
| 文档要不要为 Athena 改写 | 要（`:::experiment` 指令） | 不改（也不用） | **不改一个字符**，挂载发生在渲染期 |
| 绑定写在哪 | 文档里 | 无绑定 | `athena.json` 的 `teaches`（知识点元数据，唯一数据源） |
| 预测判定依据 | 自由文本，不判定 | 与实际结果比对 | **语义命题的预设正确项**；输出只是证据 |
| 缺口如何处理 | 未涉及 | 未涉及 | 只报孤儿实验；"有文档无实验"是正常态 |
| 反哺文档 | 提到未落地 | 未涉及 | 偏差的第二个出口：文档待办清单 |
| 新增页面 | `LearningWorkspacePage` | 无（改代码页） | 无（增强手册页） |

从 A 继承：文档承担知识体系、不强制锁步骤、窄窗口降级。
从 B 继承：作者零新内容、预测是单选、偏差才是资产、软门槛、AI 不是硬依赖。

## 10. 风险与边界

- `teaches.heading` 按标题文本匹配，改标题即断。这是**故意**的，但如果文档处于频繁
  重写期，会变成持续的 `check` 噪音——此时应允许暂时留空，而不是为了让 `check` 过
  去改标题。**任何时候都不许为了迁就绑定而改文档措辞。**
- 渲染期插入的卡片会打断阅读节奏。必须做到：一节最多一张、放在小节末尾、
  没有配 `teaches` 的小节完全无痕。
- 实验坞和文档同屏，可能让人以为"读一段跑一段"是唯一正确用法。代码章节页必须保留，
  提醒还有"连续跑一整章实验"这条路。
- 预测选项若由 AI 生成，AI 也可能把 UB 说成确定行为。凡标注为"输出不构成保证"的
  知识点，正确项应由人写死，不交给 AI。
- 文档待办清单可能只涨不消。它是提示，不是考核；长期不消化就该缩回到 `check` 输出。
- 偏差表可能一条都不涨（反射性直接点运行）。这仍是整套方案的单点赌注。

## 11. 待进一步验证的问题

1. 渲染期插入的实验卡片，读起来是文档的自然延伸，还是明显的外来物？
2. 主从布局（文档 2 : 实验坞 1）是否真的传达了"文档主导"，还是只是实验区太窄不好用？
3. `teaches.heading` 按标题文本绑定，在真实的文档修订节奏下断得有多频繁？
4. 预测正确项由人写死的成本，在多少个知识点之后会变得不可接受？届时能否安全交给 AI？
5. 文档待办清单会真的推动文档修订，还是变成一个只涨不消的焦虑列表？
6. "有文档无实验是正常态"这条，会不会在实践中被自己违反——即不自觉地开始
   按"能不能挂实验"来写文档？如何自查？
7. 手册页同时承担阅读和实验后，`HandbookPage` 是否会突破 500 行的拆分信号线？
