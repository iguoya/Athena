# ADR 0053：教学实验改为可编辑的骨架案例，本机编译运行

- 日期：2026-09-15
- 状态：已接受；机制先行，存量章节逐个改造
- 借鉴：`apps/dsa` ADR 0003（实验给骨架不给白板）、ADR 0004（实验逻辑在 C++，
  前端不重写一份真相）
- 延续：ADR 0028 第三层（教学实验）、仓库 ADR 0047（默认不写平台分支）
- 不取代：`FunctionRegistry` 的只读实验路径继续存在，见决策第 1 条
- 编号说明：本应用序列停在 0039，但 ADR 0039 正文里「后续：ADR 0040」指的是
  仓库级 0040。再造一个同号的本应用 0040 会让那句引用产生歧义，故跳到全局
  未使用的 0053。ADR 0045 第 3 条要的是「不重排历史编号」，不是必须制造重号。

## 背景

本应用的教学实验是**编译进应用自身的成员函数**：`athena.json` 声明知识点，
生成器产出注册表，`ExperimentRunner` 通过 `FunctionRegistry` 调用，页面把
`cout` 抓回来显示。学员在源码框里看到真实源文件，然后点「运行」。

这条闭环——选知识点 → 看真实源码 → 运行 → 看输出——在 ADR 0001 立项时是对的，
它保证了展示的代码和跑的代码是同一份。但它有一个当初没有正视的缺口：

**学员从头到尾不写一行 C++。**

这在一个教 C++ 的应用里格外刺眼。仓库里另一个编程类应用 `apps/dsa` 教的是数据
结构，实验反而要求学员动手写 C++：案例源码放 `content/cases/<id>/main.cpp`，
是纯内容不进构建；骨架自带接口声明与 `main` 驱动，学员补 `TODO` 函数体；本机
`c++ -std=c++20` 子进程编译运行，编译诊断完整展示。它的 ADR 0003 把理由讲清楚了
——实验的目标是验证概念与代价直觉、练一小段程序性技能，不是练「从空白 `main`
搭工程」，所以给骨架、不给白板。

对照之下，本应用现有机制有三个后果：

1. **教学上只能验证「读懂」，验证不了「写得出」。** 值类别、拷贝控制、模板推导
   这类东西，不自己写一遍、不被编译器顶回来几次，理解停在似懂非懂。而这恰恰是
   本应用的主题。
2. **实验的边际成本被绑在构建上。** 每加一个知识点实验都要改 `meson.build`、
   重编整个应用。`apps/dsa` 加一个案例只是建一个目录。74 个知识点里只有 4 章
   有实现代码，这个成本是原因之一。
3. **实验形态被锁死在「跑一次看输出」。** 想让学员改一个参数看结果怎么变——
   现在做不到，只能作者预先写死几个变体。

## 决策

### 1. 两条实验路径并存，不是替换

`FunctionRegistry` 的只读实验路径**保留**。它有现有路径独有的价值：展示的源码
就是应用自己编译过的源码，没有第二份真相，适合「看真实工程代码怎么写」。

新增**可编辑案例**路径。两者在知识点粒度上选用，一个知识点可以两者都挂：
只读示范负责「看懂它长什么样」，可编辑案例负责「自己写一遍」。

这正是 dsa ADR 0003 第 3 条的「示范与待填可并存」——本应用现有的只读源码恰好
已经是「示范」那一半，这条 ADR 补的是「待填」那一半，不是推翻重来。

### 2. 案例源码随 GResource 分发，工作副本落用户数据目录

`AGENTS.md` 有一条硬规则：**教学内容只从 GResource 读**，运行期不按文件路径找
任何随程序分发的东西。案例源码是教学内容，这条继续适用——否则装到别的机器上
就找不到案例了。

所以分成两份：

- **骨架原件**：`content/cases/<case_id>/*.cpp`，由生成器打包进 GResource，
  只读，随应用分发。
- **工作副本**：`released_data_dir()/cases/<case_id>/`（发行副本即用户数据目录下的
  `athena-cpp/cases/`），首次打开
  该案例时从 GResource 展开，之后学员的编辑都写在这里。

「重置」就是删掉工作副本重新展开。仓库里的案例源码任何时候都不被应用改写。

### 3. 骨架必须自带可编译的接口与驱动

照搬 dsa ADR 0003 的验收标准，一条不减：

- 必要头文件与 `using`；
- **待实现的接口**：自由函数签名或类的 public 成员声明，可带空实现或错误占位体；
- **`main` 作为固定驱动**：构造输入、调用接口、按约定格式打印结果；
- 用注释划清可改区域，例如 `// TODO(学员)：实现下列函数体` 与
  `// —— 以下驱动请勿改 ——`。

**验收标准是：不改任何一行就能编译运行。** 学员只填 TODO 也能通过驱动看到结果。

### 4. 编译运行走本机工具链，用 GLib 的跨平台 spawn

按 ADR 0047「默认不写平台分支」：用 `g_spawn_sync()` 传 argv 数组
（不是 `g_spawn_command_line_sync()`——它按 shell 规则拆参数，路径含空格就出错），
编译器按 `c++` → `clang++` → `g++` 顺序探测，`-std=c++20`。

找不到编译器时给**具体的**安装指引而不是一句「请先安装」（仓库 ADR 0057 的分寸：
只给省时间的那部分，例如 VS 要勾哪个工作负载、MSYS2 的包名叫什么）；这属于需要
使用者动手才能继续的情况，用对话框而不是状态栏。

**编译诊断完整展示，不截断、不吞掉。** 对学 C++ 的人来说编译器错误信息本身
就是教学内容——看懂 `error: cannot bind non-const lvalue reference` 是能力的一部分。

### 5. 案例挂在知识点上，由配置声明

`athena.json` 的知识点增加可选的 `labs[]`，字段照 dsa 的语义取名：

- `case`：案例目录名；
- `prompt`：**题干**——要验证或解决什么问题、观察什么现象；
- `goal`：补哪个符号、对照哪段输出；
- `hint`：可选提示。

dsa ADR 0003 第 5 条的教训一并采纳：**先写清题目再写动手清单**，避免只有
「补全 xxx」而看不到这道题在认知上要解决什么。

配置契约先于解析器和界面定义（`AGENTS.md` 既有规则），生成器负责校验
`case` 指向的目录存在、骨架文件存在。

## 后果

**得到**：学员开始产出代码，「写得出」进入可验证范围；新增实验不再需要动构建，
边际成本从「改 meson + 重编应用」降到「建一个目录」；实验形态打开——改参数、
改一处循环、补一个函数都成立。

**付出**：多一条运行路径要维护；依赖本机有 C++ 工具链（按仓库 ADR 0057 的基线，
这是可以直接假定的，但要给出探测失败时的具体指引）；工作副本引入了「仓库原件
与本地编辑不一致」的状态，靠显式的重置入口和「原件只读」来管理。

**2026-09-16 补充（使用者看过第一个案例的界面后定的标准）**：可实操的知识点
**默认每个配一个独立案例，一对一**。原文写的是「一个知识点可以两者都挂」，那只
说明了两条路径可以并存，没说覆盖到什么程度；实际标准是覆盖全部可实操的知识点，
不是挑几个示范。无法用可运行代码观察的知识点才没有案例。

**连带**：
- `ExperimentRunner` 现在只认 `function_id`，要扩成能表达两类请求。
- 源码框（`ui/source_view`）要从只读变成可编辑，`GtkSourceView` 本来就支持。
- 编译产物是临时文件，放工作副本目录下，不进仓库。
- 判分若要接入（本 ADR 不做），方向是 dsa 的 `pass.includes`——驱动打印约定字段、
  本地比对，而不是把学员代码交给 AI 判断。这与仓库 ADR 0043「判分条目必须有
  可核对的出处」是同一个方向，另开 ADR 处理。
