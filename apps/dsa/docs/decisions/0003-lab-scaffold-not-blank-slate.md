# ADR 0003：实验提供接口/类骨架，学生补全而非从零编写

- 日期：2026-09-12
- 状态：已接受；写作规范即时生效，现有 cases 已按骨架改写
- 延续：ADR 0001（实验工作台）、ADR 0002（随堂实现优先短补全）

## 背景

DSA 实验的目标是验证概念与代价直觉，或练一小段程序性技能，不是练「从空白
`main` 搭工程」。若案例要求读者自己写 `#include`、驱动输出和全部函数，负担会偏到
语言脚手架，自学注意力被扯离知识点。

## 决策

1. **每个 case 必须自带可编译的骨架（scaffold）。** 至少包括：
   - 必要头文件与 `using`；
   - **待实现的接口**：自由函数签名，或类的 public 成员声明（可含空/错误占位体）；
   - **`main`（或既定入口）作为固定驱动**：构造输入、调用接口、按约定打印结果。
2. **学生默认只改「待填」区域。** 用清晰注释标出，例如
   `// TODO(学员)：实现下列函数体` / `// —— 以下驱动请勿改（除非题目要求）——`。
   观察与对照依赖驱动输出格式稳定。
3. **示范与待填可并存。** 允许先给一个已实现的参考函数（只读理解），再留一个同构的
   待填变式（如 `demo_square` 已实现，`todo_cubic` 留给学员）。概念验证型实验也可以
   「改参数 / 改一处循环」为主，仍须保留完整可跑骨架，而不是空文件。
4. **不做从零 OJ。** 不要求学员自写完整程序、自选入口、自搭测试框架；需要判对错时，
   由驱动打印约定字段或后续加隐藏对照，而不是让学员先搭测试床。
5. **课表先写清「题目」再写「动手」。**
   - `labs[].prompt`：**题干**——要验证或解决什么问题、观察什么现象（读者第一眼读这个）。
   - `labs[].goal`：补哪个符号、对照哪段输出（动手清单）。
   - 避免只有「补全 xxx」而看不到应用/认知问题。

## 后果

- 新增 case 的验收标准：克隆后不改即可编译运行；学员只填 TODO 仍能通过驱动看到结果。
- 实验页顶部用醒目「题目」卡展示 `prompt`；`goal` / `hint` 退居「你要做的 / 提示」。
- 与随堂实现（ADR 0002）一致：技能练习是短补全，不是空白项目。
