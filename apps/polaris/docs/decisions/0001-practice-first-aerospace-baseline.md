# ADR 0001：以航天行业技术体系为根本目的，实践优先组织路径

- 日期：2026-09-15
- 状态：已接受（场景取舍与地图构成由 [ADR 0005](0005-launch-vehicle-process-not-robotics.md) 修订）

## 背景

Polaris 的根本目的，是帮助普通开发者逐步建立能够进入并胜任**航天行业软硬融合工程**的技术
体系。它不是一张通用技术图谱恰好附带航天分支，也不是把某个航天软件框架的 API 整理成
学习清单。卫星平台、测控通信、飞控与地面处理、统一时间、任务级仿真和高可靠验证共同决定
了路线的技术取舍：优先选择能形成精度、实时性、算力、接口和验证闭环的能力。

计算机、电子信息、人工智能、机器人、嵌入式和硬件地图是这一根本目标的分层实践入口：它们
既能服务各自行业，也应最终能迁移、组合到航天工程的复杂系统要求中。若直接照搬高门槛院校
的课程顺序，普通开发者会先遇到长串抽象理论，却迟迟做不出能测量、调试和复盘的系统；但若
把理论全部删去，又会无法判断精度、实时性、算力和可靠性的工程边界。

此前“航天框架只是参考样本”的表达不完整：框架不能定义 Polaris，但航天行业技术体系定义了
Polaris 为什么存在、哪些能力值得优先学习，以及何种工程验证才算完成。具体框架仍只是证据样本。

## 决策

1. **航天行业技术体系是 Polaris 的根本目的和技术取舍准则。**任何候选节点、工具或学习
   顺序，先回答它是否提升进入航天软硬融合工程所需的精度、实时、算力、接口、可靠性或
   验证能力；不能回答的，不因流行或招聘关键词而进入主干。其他行业的可迁移价值是次级
   收益，不反过来决定主干。
2. Polaris 把“中国航天工程 · 高精度实时系统”作为核心一级地图，而非一个通用可靠性附录。
   它以官方公开的卫星平台和测控通信系统资料为场景证据，内容仍保持在公开、通用的工程
   能力层，不描述任务敏感细节。
3. 每个节点采用“先实践、后原理”的表达：必须有可交付的最小实践、可观察指标和验证方式；
   `stable_definition` 只给完成这项实践所需的理论下限。进阶理论可以作为后续节点或来源，
   不伪装成所有人的先修门槛。
4. **所有路线同时从软件、硬件和软硬件接口三个角度取舍。**软件侧负责算法/模型、数据
   处理、飞行或地面运行时、通信协议、调度、状态机、故障处理与可观测性；硬件侧负责传感
   与执行、板卡/总线、供电、时钟、FPGA/SoC、热与物理环境；接口层负责数据格式、命令、
   时间基准、资源上界、仿真台架和验收证据。任何一侧都不能独立宣称“系统完成”。
5. 每张地图的主干实践必须至少落到一次软硬件闭环：软件能读到来自实体或模拟硬件的可追溯
   输入，硬件的时序/状态能被软件测量和诊断，系统能在异常时降级或恢复。大模型这类软件
   入口也应在部署、异构计算、数据搬运与边缘/地面接口处说明其硬件边界，不把模型效果当作
   独立于计算平台的结论。
6. 强先修只保留“没有它就无法安全/有效完成下一个实践”的关系。对有价值但可并行深化的知识，
   使用 `enables` 或 `optional`，而不制造一条看似严谨的理论长链。
7. 把高精度、高实时性、高计算性和可靠性验证作为跨图约束：所有方向都应最终能够做时间/误差
   测量、端到端性能测量、接口/异常验证和交付复盘。它们不是航天框架的专属术语。
8. 高校培养方案和岗位描述仅是范围/现实性证据：前者不能被复制成课程表，后者也不能成为稳定
   的学科先修。岗位来源必须标注为时效性样本。

## 后果

- Polaris 的初版有七张地图，其中航天工程图是根本目的的核心高阶投影；其余地图是朝向这一
  目的组织的实践入口，而不是平行竞争的兴趣分类。
- 内容编辑工作增加：每个节点和每条边都要有来源，还要明确写出实践和验证；但可避免漂亮却
  无法行动的“技能词云”。
- 后续增加或删减节点时，要先检查它在软件侧、硬件侧或接口层的职责，以及它如何与另两侧
  闭环；单纯的软件名词、芯片名词或框架名词都不是可直接入图的理由。
- Polaris 不承诺用户跳过数学、控制或信号理论就能胜任安全关键岗位。路径只是用作品和测量建立
  进入更深理论的动机和问题意识。
