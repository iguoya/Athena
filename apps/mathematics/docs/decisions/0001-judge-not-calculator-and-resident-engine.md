# ADR 0001：工具当裁判不当计算器；符号引擎随包常驻前端

- 日期：2026-09-13
- 状态：已接受；技术选型即时生效，Pyodide 加载预算待首次实现时实测
- 精神对齐：主仓库 ADR 0032（异构独立应用）、0037（各应用自建进度库）、
  0033（活的可视化）；载体为 Web UI，不照搬 GTK 约束

## 背景

### 1. 考试形态决定工具角色

研究生入学考试数学是**闭卷手算**：三小时内靠纸笔完成极限、积分、级数、线代
运算和概率计算，考的是推导的准确率与速度。

一个「输入题目 → 输出答案」的数学应用对这个目标是零帮助甚至负帮助——它练的是
打字，还会制造「我看懂了」的错觉。这类工具已经很多（Wolfram Alpha、各种解题
App），本应用再做一个没有意义。

真正缺的是**批改**：我手推完一道题，第三步错了，需要有人指出是第三步错而不是
只告诉我最终答案不对。这件事人做很贵（需要老师逐题看），机器做很便宜（符号
等价判定是 CAS 的基本能力）。这是本应用存在的理由。

### 2. 批改交互决定引擎形态

「逐步判等」是**高频、低延迟**的交互：用户每写完一步就要立刻知道对不对。
超过 100 ms 的往返会让人放弃逐步写，退回到「全写完再对答案」——那就又变回
计算器了。

`apps/dsa` 的实验是「编辑代码 → 点运行 → 看输出」，一次往返一秒可以接受，
所以它每次 fork 子进程编译运行。**本应用不能照搬这个模式**。本机实测
（SymPy 1.14.0，macOS）：

| 环节 | 耗时 |
|---|---|
| 子进程完整跑一次验算（冷启动） | 640–980 ms |
| ├ Python 解释器启动 | 70–100 ms |
| └ `import sympy` | **508 ms** |
| 判等 `simplify` | 36 ms |
| 求极限 `limit` | 0.2 ms |
| 不定积分 `integrate(x*log(x))` | 62 ms |
| 分部积分 `integrate(exp(x)*sin(x))` | 29 ms |
| 泰勒展开 `series` | 14 ms |
| 解微分方程 `dsolve` | 27 ms |

结论很清楚：**运算本身是毫秒级的，延迟的九成以上来自进程启动和 import，
与题目难度基本无关。** 引擎必须常驻，只付一次 import。

### 3. 备选引擎

- **MATLAB**：商业授权，不能内嵌、不能随包分发；进程启动以秒计；强项在数值与
  工程仿真，而考研考的是符号推导——授权、性能、方向三重不合。
- **Octave**：GPL 可分发，但符号能力是拿 `symbolic` 包包了一层 SymPy，绕一圈
  还是 SymPy，中间多一层语法兼容不全的壳。
- **JS 原生 CAS**（mathjs、Nerdamer）：能求导和化简，但不定积分、级数、微分
  方程都不够用，覆盖不了考纲。
- **SymPy**：覆盖面正好压满考纲（`limit` / `diff` / `integrate` / `series` /
  `dsolve` / `Matrix` / 概率分布），纯 Python 实现无 C 扩展，可在 WASM 中运行。

## 决策

### 1. 工具的角色是裁判

**主交互是「我推一步，你判一步」**，不是「我出题，你出答案」。

三类实验形态，分别练准确、理解、速度：

| 形态 | 练什么 | 引擎的职责 |
|---|---|---|
| **推导验算** | 准确 | 判每步与上一步是否等价，报告第一处断裂的位置与性质 |
| **参数实验** | 理解 | 按参数求值供前端绘图；先让用户预测，再显示结果 |
| **限时做题** | 速度 | 题型模板参数随机化、算标准答案、判分 |

**约束**：

1. 任何把完整解答直接呈给用户的路径，都需要另开 ADR 才能加。允许的例外是
   **用户已经作答之后**的解析——那时答案不再替代思考。
2. 报错要落到步骤上（「第 3 步不等价」「第 3 步等价但引入了增根」），不是
   只报最终结果对错。
3. 判等失败不等于用户错——可能是 `simplify` 没化开。引擎给不出结论时必须说
   「无法判定」，不得判错。误判会摧毁工具的可信度，比慢更致命。

### 2. 符号引擎随包分发、在前端常驻

**Pyodide + SymPy，打包进应用，跑在前端，进程内常驻。**

- 用户机器**不需要**装 Python 或 SymPy。这与主仓库「优先零外部运行时依赖」的
  取向一致：子进程方案反而会引入一个外部环境依赖。
- 一次 `import sympy` 之后常驻内存，后续每次判等是毫秒级，满足 100 ms 预算。
- Rust 侧因此**完全不碰数学**，只管窗口、路径和进度，壳比 `apps/dsa` 更薄。
- Pyodide 资源从 `vendor/pyodide/` 本地加载，不走 CDN——离线可用，且不受外部
  站点可用性影响。

### 3. 引擎预热在进入学习页时开始

首次加载 WASM 与 SymPy wheel 有数秒级成本。**在用户打开学习页时就后台启动
预热**，等他读完讲解、开始写推导时引擎已就绪。界面需显示就绪状态，未就绪时
禁用验算入口而不是让用户等在那里。

### 4. 待实测与回退路线

Pyodide 首次加载时间依赖本机磁盘与 WASM 编译速度，本 ADR 未实测。首次实现时
必须测量并记录：

- **预算**：冷启动到引擎可用 ≤ 5 s，且可被第 3 节的预热完全掩盖。
- **超预算的回退**：改为 Rust 侧拉起**一个长期存活的 Python 进程**，用
  stdin/stdout 通信。它同样只付一次 import，代价是要求用户机器有 Python 与
  SymPy——退回到有外部依赖，故为次选。
- **不回退到**每次 fork 子进程：实测已证明该方案不满足交互预算。

### 5. 公式的输入与渲染

- 渲染用 **KaTeX**，本地打包。
- 输入用 **MathLive**，所见即所得，输出 LaTeX 后转 SymPy 表达式。
  「写下我的下一步」是本应用最高频的动作，让用户敲 LaTeX 源码不可接受。
- LaTeX → SymPy 的转换必须有明确的失败反馈（哪个记号没认出来），不得静默猜测
  成另一个表达式——那会导致第 1 节第 3 条禁止的误判。

## 后果

- 应用体积增加约 15–25 MB（Pyodide 运行时 + SymPy wheel），对桌面应用可接受，
  换来的是零外部环境依赖。
- 前端承担了远比 `apps/english`、`apps/dsa` 更重的职责（符号计算 + 公式输入 +
  实时绘图），`src/` 需要比那两个应用更认真地分层。
- 「只判不算」会让某些功能做起来比直接给答案难得多（例如要定位错在第几步，
  就必须让用户分步输入，而不能只收一个最终结果）。这是有意付出的成本。
- 出题依赖 SymPy 算标准答案，因此**题目质量受限于引擎能力**：引擎算不出或算得
  不规范的题型（如需要特定技巧的凑微分）要人工校对，不能盲目随机生成。
