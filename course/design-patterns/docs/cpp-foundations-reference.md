# 设计模式应用的 C++ 前置参考

这份参考从 `subjects/cpp` 的现有课程中抽取设计模式实验真正会用到的 C++ 能力。它不把
设计模式重新归入 C++ 教程，也不是未来设计模式应用的教学大纲；未来应用应自行拥有
课程、案例、进度库和内容格式。

设计模式的教学主线应始终是：**先看清哪一种耦合让代码难改，再判断某种结构是否真的
能降低那项代价。** 模式名称、类图和 GoF 的三类划分只是定位工具，不能替代这个判断。

## 前置能力与模式结构的关系

| C++ 能力 | C++ 侧现有主题 | 支撑的模式结构 | 常见误读 |
|---|---|---|---|
| 类、对象、`const` 与拷贝控制 | `ClassObject` | 用小而稳定的对象边界表达职责；区分可变状态与值对象 | 只会画类图，却不知道状态由谁拥有、复制后是否独立 |
| 抽象接口、虚函数、继承与组合 | `ClassObject` | Strategy、Factory Method、Template Method、Observer、Visitor 等需要可替换协作方的场景 | 把继承当默认复用手段；很多变化更适合组合 |
| RAII、独占 / 共享所有权、移动语义 | `RAII` | Factory、Builder、Composite、Decorator、Proxy 等对象图的创建、转交和销毁 | 为了“有模式”而引入不清楚的共享所有权或单例全局状态 |
| 函数对象、Lambda、回调 | `FunctionCallable` | 用行为参数与对象策略作并列比较；理解 Observer / Command 的最小通信形态 | 以为回调和模式互斥，或把所有回调都包装成层层对象 |
| STL 容器与迭代器 | `STLContainer`、`IteratorRange` | 以已有的聚合对象和遍历接口理解 Composite、Iterator、Visitor | 把标准库的迭代器使用和“迭代器模式解决什么问题”混为一谈 |

上述主题的当前权威元数据在
[`../../cpp/resources/athena.json`](../../cpp/resources/athena.json)；本文件只保留设计
模式应用需要的边界和映射。

## 先按问题组织，再按模式命名

未来课表不宜把 23 个模式机械拆成 23 份相同格式的页面。可先从下面四类变化压力建立
教学主线，再把模式作为可比较的候选解法：

| 变化压力 | 候选结构 | 实验应保持可观察的证据 |
|---|---|---|
| 创建依赖具体类型，新增产品会修改调用方 | Factory Method、Abstract Factory、Builder、Prototype | 增加一种产品时哪些模块变化；对象创建和使用是否分开 |
| 需要在不改原类型的情况下调整接口或职责 | Adapter、Bridge、Decorator、Facade、Proxy、Composite、Flyweight | 调用面是否稳定；职责是否真的分离；额外间接层的代价 |
| 变化的是行为、协作顺序或状态 | Strategy、Command、Observer、State、Mediator、Chain of Responsibility、Template Method、Visitor、Memento、Interpreter | 谁依赖谁、消息怎样流动、状态保存在哪里，以及新需求修改的范围 |
| 需要控制全局生命周期或共享资源 | Singleton 及其替代方案 | 并发、测试隔离、隐藏依赖和销毁顺序；先比较显式依赖注入，再讨论单例 |

每一个案例至少给出“难改的原始设计”和“重构后的候选结构”，用同一驱动验证外部行为
不变，并让学习者看见增加需求时修改面如何变化。模式不是目标；降低特定耦合才是。

## 与 C++ 教程的边界

- C++ 教程负责语言机制：对象生命周期、虚派发、组合、资源管理、模板和标准库。
- 设计模式应用负责结构性判断：什么时候出现耦合、有哪些替代方案、哪种方案的代价可接受。
- `IteratorPattern` 在旧 C++ 配置中因名称冲突带了后缀；独立应用无需沿用，可用
  `Iterator`。但必须明确：C++ 侧讲怎样使用迭代器 / Ranges，这里讲为何不暴露聚合对象
  内部表示仍能遍历。
- 模式历史上有 C++ 示例、未来案例也可以使用 C++20，但领域本身不隶属于 C++。不应将
  设计模式应用的配置、源码或进度迁回 `subjects/cpp`。

## 实施前的约束

1. 仍未存在可运行的设计模式应用。开始实现时先建立自己的 `app.json`、内容唯一源、
   `scripts/check.py` 和独立进度库，而不是把 `subjects/cpp/resources/athena.json` 当作过渡
   课表。
2. 例题和考核应标出具体出处与定位；可使用 GoF 的意图 / 适用性、可核验的框架用例等
   作为来源，但不能只用“23 个模式清单”充当内容依据。
3. C++ 示例应给出可编译的骨架与稳定的行为验证；学习者重构结构后，观察点应能检验
   行为和依赖变化，而不是只检查类名是否出现。
4. 这是一份参考快照。只有设计模式课程的真实前置或实验策略改变时才维护它，不建立
   对 C++ 应用的运行期、构建期或配置依赖。
