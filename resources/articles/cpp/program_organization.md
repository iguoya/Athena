# 从语言知识走向程序组织

程序组织不是另一组需要死记的语法，而是把已经学过的类型、函数、对象和模板放进真实工程时所遵循的一套边界。把这一章放在 C++ 学习路线的末尾，重点不是“运行一次得到什么数字”，而是理解编译器如何看待多个文件，以及人如何让工程保持清晰。

> 核心目标：让每个名称有明确归属，让每个声明只有必要的可见范围，让每个定义满足链接规则，并让文件边界服务于维护，而不是制造重复。

## 命名空间：组织名称，而不是组织文件

命名空间解决的是**名称归属与冲突**。目录解决的是文件存放位置；二者可以采用相似结构，但没有自动对应关系。

```cpp
namespace geometry {

class Point final {
public:
    double distance_to(const Point& other) const;
};

} // namespace geometry
```

命名空间应该表达真实的复用边界，而不是机械重复项目名或目录名。Athena 当前是独立
桌面应用，不作为公共库嵌入其他程序，因此项目类型和课程类直接使用 `Reference`、
`RAII` 等类名。将来如果某部分成为独立公共库，再为那部分引入有明确领域含义的
命名空间。`.cpp` 文件中不需要导出的辅助类型和函数，则可以放入匿名命名空间，
把可见范围限制在当前翻译单元。

### `using namespace std` 的项目约定

本项目为了降低教学代码里的视觉噪声，允许在项目代码和实验代码中优先使用 `using namespace std;`。它是一条项目级取舍，不代表所有库头文件和大型公共 API 都应无条件这样做。出现实际名称冲突，或需要强调名称来源时，仍可显式写出 `std::`。

## 声明与定义：接口和实现的分工

声明告诉编译器“这个名称及其类型存在”，定义则真正提供实体或函数体。头文件通常承载需要跨翻译单元共享的声明，源文件承载不必向外暴露的实现。

```cpp
// reference.h
class Reference final {
public:
    void reference_basics() const;
};

// reference.cpp
void Reference::reference_basics() const {
    // 实验实现
}
```

判断某段内容放在哪里时，可以先问两个问题：

- 其他源文件是否必须看见它的完整定义？
- 修改它以后，是否值得让所有包含者重新编译？

模板定义通常必须对实例化位置可见，因此经常留在头文件中；普通非内联函数通常把声明放在头文件、定义放在 `.cpp` 文件中。

## 翻译单元与链接：编译器实际看到什么

一个 `.cpp` 文件经过预处理、展开它包含的头文件后，形成一个翻译单元。各翻译单元先分别编译，最后由链接器把外部符号连接成程序。

```text
reference.cpp + 所有展开的头文件  ->  reference.o
mainwindow.cc + 所有展开的头文件  ->  mainwindow.o
reference.o + mainwindow.o        ->  Athena
```

这解释了几个常见现象：

- 头文件中的改动会触发多个翻译单元重新编译。
- 某个 `.cpp` 中不可见的声明，会在编译阶段报错。
- 声明存在但定义缺失，往往到链接阶段才报错。
- 文件内辅助对象可以使用内部链接，避免泄漏为整个程序的符号。

## 单一定义规则（ODR）

ODR 约束“哪些实体只能定义一次，以及哪些定义允许出现在多个翻译单元中”。最典型的错误，是把普通函数定义直接放进一个被多个 `.cpp` 包含的头文件，最终产生重复符号。

```cpp
// 错误倾向：普通非 inline 函数定义在公共头文件中
int answer() {
    return 42;
}
```

类定义、模板以及符合规则的 `inline` 定义可以出现在多个翻译单元，但它们的定义必须保持一致。这里的 `inline` 更重要的意义是 ODR 与链接规则，不只是“建议编译器内联展开”。

### 实用检查

- 公共头文件是否有 include guard 或 `#pragma once`？
- 普通函数的非内联定义是否只存在于一个 `.cpp`？
- 头文件中的全局变量是否使用了正确的 `inline`、`constexpr` 或 `extern` 设计？
- 是否因为不同宏条件，让同一实体在不同翻译单元中拥有不一致定义？

## C++20 Modules：更明确的接口边界

C++20 Modules 使用模块接口和 `import` 表达依赖，目标之一是减少文本包含带来的重复解析和宏污染。

```cpp
export module athena.reference;

export class Reference final {
public:
    void reference_basics() const;
};
```

模块并不会自动替你设计合理架构，也不会立刻取代所有头文件。编译器、构建系统和第三方库的模块支持需要共同配合，因此在实际项目中通常采用渐进迁移。先理解翻译单元、可见性和 ODR，再学习 Modules，会更容易看清它解决了什么问题。

## 文件拆分的现实尺度

文件不是越少越简单，也不是越多越专业。Athena 的实验类可以按以下尺度判断：

1. 一个知识点方法通常控制在容易完整阅读的范围内。
2. 同一主题的多个小实验共享一个类，避免为每个函数创建零碎类型。
3. 当一个主题自然形成明确分组，或单个实现文件变得难以浏览时，再把同一个类的成员函数拆到多个 `.cpp`。
4. JSON 中的 `group.source` 可以指向分组源码，但分组不会额外生成类层级。

最终目标不是追求固定行数，而是让新手打开一个页面时，能快速回答：“我现在学习的主题是什么，这段代码验证了什么，它和其他文件如何连接？”

## 本章结论

程序组织属于**可以用代码举例，但不适合只靠一次运行结果解释**的主题，因此采用文章章节。它仍然可以包含短代码片段和工程结构示例，只是不提供容易误导的“运行”按钮。

- 命名空间管理名称归属。
- 头文件与源文件分担接口和实现。
- 翻译单元是独立编译的基本单位。
- ODR 约束跨文件定义的一致性和唯一性。
- Modules 提供更明确的新式依赖边界，但需要工具链配合。
- 文件拆分应由可读性、变化边界和编译依赖共同决定。
