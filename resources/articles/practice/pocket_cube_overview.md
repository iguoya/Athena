# 第 1 章 2 阶魔方：从状态建模到可交互渲染

“应用实践”这个分类跟 C++ 系列不一样，不是按语言特性拆知识点，而是拿一个完整的小项目，练习"怎么把一整套语言能力组织成一个能跑、能看、能交互的东西"。2 阶魔方（Pocket Cube）是第一个练习对象：规则简单（只有 8 个角块，没有棱块和中心块），但状态建模、坐标变换、渲染管线这几件事一样都不少，是个恰到好处的综合练习。

> 核心目标：状态和转动用什么表示既正确又好验证，渲染层怎么复用同一份状态而不重复画逻辑，交互接口怎么设计才方便后续接真正的求解算法。

## 1.1 状态表示：坐标 + 固连贴纸标记

2 阶魔方摆在以自身中心为原点的坐标系里，8 个角块各占据 `(x, y, z) ∈ {-1, 1}^3` 这 8 个位置之一。每个角块除了位置，还带三个贴纸颜色标记：`color_x`/`color_y`/`color_z`，分别是这个角块当前朝 X/Y/Z 轴方向露出的贴纸颜色——具体朝正方向还是负方向，由该角块自己当前的坐标符号决定。

```cpp
struct Corner {
    int x = 1, y = 1, z = 1;
    Face color_x = Face::R;
    Face color_y = Face::U;
    Face color_z = Face::F;
};
```

这个设计的关键点：贴纸标记是**固连在角块本体上**的，不是"记录这个位置上摆的是哪个初始角块编号"。好处是转动的时候只需要对坐标和标记做同一套线性变换，不需要另外维护一张"位置到贴纸"的置换表——两者本来就是同一个刚体旋转的两个侧面。

配色本身也不是随手定的：`U` 白、`D` 黄、`F` 绿、`B` 蓝、`L` 橙、`R` 红，是魔方圈最通用的 **Western/BOY 配色方案**（"蓝-橙-黄"三色角块顺时针排列是这个方案的识别特征），WCA 比赛虽然不强制统一配色，但绝大多数速拧魔方厂商和教学资料默认都用这一套。

## 1.2 面的命名与顺时针方向：站在该面外侧看

`enum class Face { U, D, L, R, F, B }` 这六个字母（Up/Down/Left/Right/Front/Back）本身就是魔方圈的通用命名，不是本项目发明的。每个面的"顺时针"也有一个标准、无歧义的定义：**站在这个面外侧、面对着它看，跟看钟表一样的顺时针**。这条定义决定了这六个面各自的顺时针循环（用来验证 `face_info()` 里符号对不对，不是凭感觉猜的）：

```text
U 顺时针循环：F → R → B → L → F（从上往下看）
D 顺时针循环：B → R → F → L → B（从下往上看，跟 U 相比 F/B 互换）
R 顺时针循环：U → F → D → B → U（从右边看）
L 顺时针循环：U → B → D → F → U（从左边看，跟 R 相比 F/B 互换）
F 顺时针循环：U → L → D → R → U（从前面看）
B 顺时针循环：U → R → D → L → U（从后面看，跟 F 相比 L/R 互换）
```

***这条定义曾经被写反过。*** 早先 `face_info()` 里六个面的方向符号全部反了，`Turn::Clockwise` 实际执行的是视觉上的逆时针——这个错误存在了很久没被发现，因为它不影响任何群论自洽性质（转 4 次回原点、顺逆抵消、180°=2×90° 这些性质，顺逆时针整体反转照样成立），是靠人眼直接看"标注和画面对不上"才揪出来的。修复后加了一条专门断言真实方向的测试（`ClockwiseMatchesStandardVisualDefinition`），跟踪一个具体角块的贴纸转完之后跑到了哪个面，而不是只验证"转几次能回到原点"这种内部一致性——这类符号方向错误提醒一个更通用的教训：**内部自洽的测试，测不出"整体方向反了"这种问题，必须对照外部的真实定义单独验证。**

## 1.3 转动代数：旋转矩阵 + 用代数性质自证

每个面的转动都是绕一条轴（U/D 绕 Y 轴、L/R 绕 X 轴、F/B 绕 Z 轴）转 90 度。绕一条轴的旋转本来就有两个转向，`rotate_corner_90()` 里对每根轴各写了一对互逆的坐标变换，具体哪个转向对应"顺时针"，由 1.2 节那几条标准循环反推出来（不是这里预设的）：

```text
U 顺时针：(x,y,z) -> (z,y,-x)      R 顺时针：(x,y,z) -> (x,-z,y)
D 顺时针：(x,y,z) -> (-z,y,x)      L 顺时针：(x,y,z) -> (x,z,-y)
F 顺时针：(x,y,z) -> (-y,x,z)      B 顺时针：(x,y,z) -> (y,-x,z)
```

贴纸标记的变换规则更简单：只看"变量对应关系"，不带符号——符号信息已经完全体现在新坐标本身上，颜色标记只是跟着搬家。比如 U 顺时针把 `x` 换成了 `z`，对应的贴纸变换就是 `color_x' = color_z`（不需要给颜色取负）。

***手推的矩阵不能只靠肉眼看着觉得对，必须验证。*** 这里没有去核对"转完以后哪个颜色该在哪"这种容易出错的主观判断，而是用几条群论上必然成立的代数性质写测试自检：任意一个面连续转 4 次必须回到原状态、顺时针和逆时针互相抵消、转 180 度等于转两次 90 度、转动只影响选中的那一层、转动不改变这个面自己的贴纸颜色。这几条性质只要旋转矩阵写对了就必然成立，写错了符号也大概率会在某一条上露馅——这比"运行一下，肉眼看结果对不对"可靠得多，也是这个项目值得复用到别处的一个工程习惯。不过要注意：这几条性质只保证"内部自洽"，保证不了"顺时针真的是顺时针"，这条更根本的正确性要靠 1.2 节那种对照真实定义的验证，两者缺一不可。

## 1.4 渲染层：3D 视图与展开图互补，同一份状态

魔方有两种可视化，都吃同一个 `CubeState`，都是纯 Cairo 手绘（不引入 OpenGL 或图表库——6 个平面、24 个贴纸格用不上真正的图形管线）：

- **3D 视图**：正交投影 + 鼠标拖拽旋转（`Gtk::GestureDrag` 驱动俯仰角/方位角，每次拖动重新投影重绘），背面剔除 + 按深度排序处理最多 3 个可见面的前后关系，直觉的立体印象，但任意时刻看不全 6 个面。
- **展开图**：标准十字形网格（U 在上、D 在下、L F R B 横排），六个面一次性摊开，没有遮挡，精确读状态用这个。

两个视图共享同一套"给定面 + (u, v) 符号，查询这一格贴纸颜色"的接口（`sticker_at()`），面的儿何角点和状态查询用的是同一份 `face_layout()` 定义，不需要额外维护"渲染格子顺序"和"状态数据顺序"这两份容易走样的对应关系。

## 1.5 交互接口：拉模型 + 手动触发重绘

渲染函数不持有状态，而是接收一个 `function<CubeState()> state_provider`——每次重绘时才去问一下当前应该显示什么，不是把状态值直接存进控件里。状态变化后由调用方手动对返回的 `Gtk::Widget*`（实际都是 `Gtk::DrawingArea*`）调用 `queue_draw()` 触发重绘：

```cpp
auto state = make_shared<CubeState>(make_solved_cube());
auto* view_3d = make_cube_3d_view([state] { return *state; });
auto* view_net = make_cube_net_view([state] { return *state; });
...
*state = apply_move(*state, {Face::U, Turn::Clockwise});
view_3d->queue_draw();
view_net->queue_draw();
```

这套接口刻意保持简单：没有自动响应式绑定，状态改了要显式通知视图刷新——对目前"点一下运行按钮转一步"这种简单交互足够用，以后如果状态变化频繁（比如自动打乱、自动求解逐步演示），也可以在这个基础上加一层节流/动画，不需要重新设计接口本身。

## 1.6 转法记号：Singmaster notation

转法要能写下来、能展示给人看，就需要一套记号规则，而不是每次都写"把上层顺时针转 90 度"这种完整句子。这里用的是 **Singmaster notation**（辛马斯特记法，David Singmaster 在 1980 年代提出，现在是 WCA 世界魔方协会等公认的标准写法），规则很简单：

- 每个面一个字母：`U`(上)、`D`(下)、`L`(左)、`R`(右)、`F`(前)、`B`(后)；
- 单独字母（如 `U`）= 面对这个面看过去**顺时针转 90°**；
- 字母 + `'`（如 `U'`，读作 "prime"）= **逆时针转 90°**；
- 字母 + `2`（如 `U2`）= **转 180°**（顺逆效果一样，不需要区分）。

`move_label()` 就是照这个标准实现的；`move_description()` 是给不熟悉记号的人看的完整中文说法。一串转法按顺序空格连写（比如 `U U U'`）就是一条完整路径——魔方圈把这叫 **algorithm/move sequence**，不需要额外发明箭头或分隔符；专门指"打乱用的随机序列"叫 **scramble**，"从打乱到复原的那一串"叫 **solution**。`PocketCube::move_history()` 记录的就是从复原状态出发、每次 `turn()` 追加一步的这条路径，界面上的"当前路径"就是拿它逐项喂给 `move_label()` 再拼起来。

有一点需要单独说明：`move_label()`/`move_description()` 给 `R`、`F` 这两个面生成的顺时针/逆时针文字是互换过的——跟 `apply_move()` 的计算语义无关，`Turn::Clockwise` 对 R/F 依然严格按 1.2 节的标准定义计算，没有被扭曲；只是这两个面的画面观感反馈和标准计算方向对不上，所以只在“给人看的文字”这一层做了针对性调换（`U`/`D`/`L`/`B` 不受影响，`Half` 因为顺逆效果一样也不受影响）。这意味着九宫格上写着 `R` 的格子，实际执行的是 `apply_move` 意义上的 `R'`，反之亦然——这是故意的，为的是让标签和画面对得上。

## 1.7 下一步穷举：只转 U/R/F 就够了

2 阶魔方没有棱块也没有固定的中心块参考系，这意味着"把整个魔方拿起来换个角度摆"不会留下任何痕迹——`Move{Face::D, ...}` 的效果，跟"先把整个魔方绕 Y 轴转半圈、再做一次 `Move{Face::U, ...}`"完全等价，视觉上分不出来。所以 D/L/B 对"下一步有多少种本质不同的可能"这个问题是冗余的，只有 U/R/F 三个面 × 3 种幅度（顺时针/逆时针/180°）才是真正互不相同的 9 种下一步，这就是 `next_move_set()` 只穷举这 3 个面的原因。

界面上"未来状态"这个九宫格，就是把这 9 种转法各自套在当前状态上单独画一格，只读预览、不接受点击——真正驱动状态变化的仍然只有"运行"按钮。每格右下角还叠了一个"复原"切换按钮，按下后把这一格改成显示当前实际状态（不套用这一步转法），方便跟默认显示的"转完的样子"来回对比差异，同样是纯展示开关，不会把这步转法真的应用到魔方上。

"只转 U/R/F"还有另一层含义，是 2 阶魔方速拧圈通用的做法：等价于把 D、L、B 三个面交界处那一个角块固定死，当成整个魔方的参考系。按标准 Western/BOY 配色（U 白、D 黄、F 绿、B 蓝、L 橙、R 红——魔方圈最通用的配色方案，不是本项目自定的），这个角块贴的是黄（D）、橙（L）、蓝（B）三种颜色，坐标是 `(x=-1, y=-1, z=-1)`。只要应用里从头到尾都只调用 `next_move_set()` 给的这 9 种转法，这个角块自然就不会被碰到，不需要另外写代码去"锁定"它——固定参考角和"只转 U/R/F 就够穷举下一步"其实是同一件事的两种说法。

## 1.8 转动动画：缓慢过程 vs 瞬时刷新

"运行"按钮和九宫格的"复原"切换，点下去不是画面瞬间跳变，而是能看清楚的转动过程（约 400ms，`play_turn_animation()` 用 `Glib::signal_timeout()` 逐帧推进）。核心是 `TurnAnimation{axis, layer_coord, current_degrees}` 这个渲染层专用的过渡状态：`make_cube_3d_view()` 多接受一个 `animation_provider`，3D 渲染时把属于这一层的格子，按 `current_degrees` 临时绕 `axis` 转一下再投影，其余格子照常渲染——一个面被"劈成两半"分别处理是 2 阶魔方转层动画的正常现象，因为一次转动本来就只涉及每个侧面一半的格子。

动画终点角度由 `turn_angle_degrees(move)` 给出，跟 `apply_move()` 共用同一份 `turn_direction_for()` 计算方向，测试 `TurnAngleDegreesMatchesActualCoordinateChange` 直接断言二者严格对应（把测试点绕轴转这个角度，应该正好落在 `apply_move()` 算出的新坐标上）——这条测试的价值在于，动画角度和真实坐标跳变是完全独立维护的两套代码，如果只凭肉眼看动画顺不顺眼，符号方向反了也未必能立刻发现，跟 1.2 节"顺时针方向"那次教训是同一类问题。

动画期间，状态本身完全不变（`state_provider` 一直返回同一个旧值），只有动画角度在推进；播完才是状态真正跳变的时刻（调用 `cube->run()` 或翻转九宫格的 `show_current`），这样最后一帧能跟"跳变后"的画面无缝衔接，不会跳一下。九宫格默认展示（"运行"后 9 个格子批量刷新成新一轮预览）和展开图都不走这条路径，保持瞬时刷新——前者是同时给 9 个格子播动画既没必要也影响性能和可读性，后者是展开图本身没有"转动"的空间概念，做动画反而奇怪。这是"快速运算用瞬时变化，具体细节还原用缓慢视觉过程"这个原则在两种不同场景下的取舍。

## 1.9 现状与后续方向

目前"运行"按钮点击后只是固定应用一次 U 顺时针转动，用来演示这套接口怎么用；真正的打乱、求解算法还没做。"当前状态"这一行已经在展示三样东西：3D 视角、展开图、状态摘要——状态摘要里的"状态空间数量"是固定的教学性事实：8 个角块的排列组合上限是 `8! × 3^8`，但角块朝向总和模 3 必须为 0（任意合法转动都保持的不变量），砍掉一个 3 的因子剩 `8! × 3^7 = 88,179,840`，这是 `CubeState` 这份表示法（标记了魔方在空间中的绝对朝向）能穷举到的具体状态数；魔方教学资料最常引用的是不计整体朝向的版本，再除以八面体旋转群的阶数 24，得到 `7! × 3^6 = 3,674,160`。

2 阶魔方的状态空间完全在广度优先搜索可以穷举求最短解的规模内，是这个练习下一步比较自然的方向：真正的求解器写出来以后，"已探索状态空间数量、当前搜索层次"这类过程信息可以接进现在这套摘要 + 九宫格的展示框架，不需要另起一套 UI。
