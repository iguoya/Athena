## 基线：使用者是资深开发人员，机器是一台完整的开发机（ADR 0057）

**运行前提**：可以直接假定机器上装有 Python、Git、C/C++ 编译器、Node 这类开发
必备工具，不要为「万一没装」付出代价——不内嵌解释器（例如拿 Pyodide 替代本机
Python + SymPy）、不内置编译器、不把功能降级成「没有工具链也能凑合用」、不在
文档和代码里堆「如果你没有 X 怎么办」的兜底分支。

**技术选型**：**判据是这个技术合不合适，不是它好不好装、依赖多不多、包体积多大。**
运行库的安装与分发成本在本仓库不计入权衡；该用重依赖就用（SymPy 即是一例），
不要为了「零依赖」「好分发」「免安装」退而求其次。

**编码过程**：代码按专业水准写，不迁就零基础读者。该用的语言特性、抽象和库照用，
不为了「看起来简单」换成更笨的写法；注释解释**为什么这样选**和非显然的约束，
不解释语言基础；错误信息和文档直接用术语，不展开科普。边界是**清晰**而不是
**浅显**——不写晦涩代码、不堆无谓的抽象，但也不把读者当成需要照顾的初学者。

**这一条的首要目的是减少代码复杂度**——少一条兜底路径，就少一处要维护、要测试、
会悄悄退化的地方，不是对使用者的态度表态。

**但这不等于可以敷衍。** 检测不到某个工具时仍要给出具体的安装指引，而不是一句
「请先安装」；需要使用者动手才能继续的，**用对话框**而不是状态栏。分寸在于
**只给省时间的那部分**：`subjects/dsa` 找不到 C++ 编译器时，
值得写的是「VS 要勾哪个工作负载」「MSYS2 的包名叫什么」这些查起来费事的；
官网 URL、「LLVM 带 clang++」之类的常识不写——写进去反而是把人当小白。

## 跨平台优先（强约束）

**技术选型和代码编写一律跨平台优先（ADR 0047）**，适用于仓库里每一个应用。
但**跨平台是成本收益判断，不是"三平台必须对称"（ADR 0049）**：某个软件、工具
甚至整个项目，跨平台成本很高时就整体排除在跨平台之外，让它在专用平台上发挥最大
优势——排除的粒度可以很大，不限于某个函数里的平台分支。被排除的必须写明白：
ADR 里写清成本、收益与降级，应用文档里写明哪个平台不支持，CI 里不留假装在支持
的探测位。含糊比排除更糟。当前的排除清单在 ADR 0049 里。

**平台之间有优先级：macOS ≈ Windows > Linux（ADR 0051）。** 不是放弃 Linux，
是排序——遇到取舍先保前两个。选型时 macOS 与 Windows 上的成熟度是硬指标，Linux
上的表现是加分项；在 Linux 上是一等公民、却要在 Windows 上跟上游缺陷缠斗的框架，
在这个排序下是减分的。同时冒出来的平台问题，先修 Windows 与 macOS 的；Linux 特有
的坑（Wayland 不允许抢焦点、GNOME 默认没有托盘区）停在如实降级提示上就够。

没被排除的地方，下面这些照旧：

- **选型时先确认 macOS 与 Windows 可用**，再看 Linux；只在部分平台可用的，
  要么找等价替代，要么在 ADR 里写明为什么值得、其他平台怎么降级。
- **优先选把平台差异自己吃掉的抽象**，而不是自己按平台分叉：打开 URI 用系统默认
  处理器，问桌面能力用框架的设置项，界面用跨平台工具包。这类抽象往往还更正确——
  按平台判断会漏掉同一平台上的例外。
- **能在构建期解决的不要留到运行期**：应用图标、包元数据、依赖收集都是打包工作，
  不该变成代码里的分支。
- **构建过程本身也跨平台**：构建系统、检查入口、开发脚本都要能在三个平台上跑
  （Meson / CMake / Cargo / npm / Python 都行，`.sh` 不行——Windows 要靠 Git Bash
  或 WSL）。只有产出安装包那一步允许平台专用，因为 `.dmg` / `.deb` / `.msi` 本就
  不同；验证、生成、启动这些每天都跑的环节不允许。支持哪个平台就在 CI 里跑哪个，
  否则支持会悄悄退化。
- **写平台分支前先问**：这条分支服务什么业务？有没有所有平台都走得通的路？如果有，
  平台特有的那条还剩多少价值？留下来的必须关在单独模块里，其他平台有明确降级行为，
  而不是编不过或崩溃。

## 验证要求

仓库根有一个统一入口，本地与 CI 共用（ADR 0007、0045）：

```sh
python3 scripts/check.py            # 跨应用内容出处检查 + 每个应用自己的检查
python3 scripts/check.py cpp        # 只跑某个应用，余下参数原样透传给它
python3 scripts/check.py --sources-only   # 只跑跨应用检查（院所名、skill 两处一致、出处）
```

检查逻辑归各应用自己（`subjects/<id>/` 与 `practice/<id>/` 下的 `scripts/check.py`），根入口只负责依次调用，
新增应用放一份自己的 `check.py` 就会被带上。**每个应用都必须有这份脚本**——
没有它的应用会被根入口静默跳过，等于没人验证。

CI 跑的是同一条入口，每个应用一个 job：依赖各装各的，命令都是
`python3 scripts/check.py <id>`。三个 Tauri 应用共用一个矩阵，新增同类应用
时往 `matrix.app` 里加一行；换一种技术栈就新起一组 job，因为要装的依赖不同。
支持哪个平台就在那个平台上跑，否则支持会悄悄退化（ADR 0047）。
