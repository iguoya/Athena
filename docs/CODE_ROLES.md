# 代码角色分工：君臣佐使及其边界

本文档记录本项目作者对代码组织的一个思维模型，以及针对这个模型的评注、修正和补充。
它是**背景观念**，帮助理解 `AGENTS.md` 和 `docs/ARCHITECTURE.md` 里那些规则为什么
这么定；它本身不是可机械校验的硬规则，遇到冲突以 `AGENTS.md` 和 ADR 为准。

## 1. 原始表述

作者的感悟：软件代码开发类似中医方剂的**君臣佐使**，各司其职。

| 角色 | 作者的定义 |
| --- | --- |
| 组织者 | 只管大局方向，不管细节 |
| 协调者 | 类似参谋角色，负责协调上下各方反馈、制定方案 |
| 辅助者 | 有工具倾向，更多负责专业化工作和通用工作 |
| 具体实现者 | 负责各种具体杂活、细节的实现 |

## 2. 这个模型对的地方

**2.1 角色分化优于平铺。** 坚持"每段代码在整体里有它的位置"，比"所有模块一律平等"
更接近真实软件的结构。分层架构、六边形架构、Clean Architecture 的共同直觉就是这个。

**2.2 “组织者只管大局、不管细节”命中了抽象层次一致性。** 这条对应软件工程里的
SLAP（Single Level of Abstraction Principle）：一个函数或类内部不应混杂不同抽象层次的
语句。一段代码里既有"切换到某个分类"又有 `gtk_text_buffer_get_iter_at_offset()`，
就是层次混杂。本项目里 `MainWindow` 的目标形态正是"只做导航与模块生命周期"。

**2.3 “辅助者有工具倾向、做通用工作”准确描述了基础设施层。** `content/`、`render/` 下
的模块就是这一类：`ContentLoader` 只管从 GResource 或源码树读字节，`SourceLocator` 只管
在文本里定位成员函数范围，`markdown_renderer` 只管 Markdown 转 HTML。它们都不知道
"知识点""熟练度""自测"这些业务概念，因此可以被任何用例复用，也可以脱离 GTK 单独测试。

**2.4 君臣佐使自带“剂量”概念，这是它比多数架构比喻多出来的东西。** 方剂里君药剂量最大、
使药最轻。映射到代码就是一句很有用的判据：**核心逻辑应当在篇幅上占主导，胶水应当最少。**
这条可以直接用来体检本项目——见下一节。

## 3. 这个模型不足的地方

### 3.1 角色是相对于“某一方”的位置，不是类的固有身份

中医里同一味药在不同方剂中角色不同：麻黄在麻黄汤里是君，在别的方里可以退为臣或佐。
代码同理：`LearningStore` 在"保存熟练度"这条用例里是主角，在"AI 自测出题"这条用例里
只是个存 Key 的配角。

把角色钉死成类的固有属性，最常见的后果就是产生一个**永久的君**，也就是上帝类。作者用的
"组织者"这个词风险最大——组织者很容易滑向"什么都经手的人"。

> **修正：先说清楚"在哪条用例里"，再谈谁是君。** 同一个模块在不同用例里换角色是正常的，
> 不是设计缺陷。

### 3.2 作者的四角色映射把“使”放错了位置，丢掉了最有价值的推论

传统的"使"是**引经报使**：剂量最轻，负责把药力引到病位、调和诸药。它对应代码里的
**路由与胶水**，而不是"干杂活的实现者"。作者把"具体实现者"排在最底、最不重要的位置，
等于把"使药剂量最轻"这条推论丢掉了——反而容易接受"胶水层最庞大"的现状。

按传统含义重新映射到 Athena：

| 角色 | Athena 中的对应 | 剂量直觉 |
| --- | --- | --- |
| 君 | `language/` 下的教学实现、各分类手册文档 —— 真正治病的东西 | 最重 |
| 臣 | `ChapterCatalog`、`FunctionRegistry`、`LearningStore`、`AiService` | 次重 |
| 佐 | `ContentLoader`、`SourceLocator`、`markdown_renderer`、`chart_scale` | 中 |
| 使 | `MainWindow` 及各 feature page —— 把用户点击引到正确的函数 ID | **最轻** |

按这个映射体检：`mainwindow.cc` 曾长期是全项目最大的单文件（ADR 0014 记录时约 2650 行，
提取对话框前仍有 2324 行），而它在"运行一个知识点"这条主用例里只是**使**。
**使药剂量最大，配伍就错了**——这正是 ADR 0014 要逐步拆分它的原因，也是用作者自己的
模型能得出的结论。

### 3.3 这个模型说不出依赖方向

一副药在锅里同煮，药材之间没有"谁调用谁"。代码有，而且方向错了会致命：循环依赖、
下层反向调用上层、领域模型里冒出 GTK 控件指针。君臣佐使无法表达"佐不许反过来认识君"。

`AGENTS.md` 的"依赖方向"和 `ARCHITECTURE.md` 第 5 节正是这个模型补不上的部分。

> **修正：角色回答"谁重要"，依赖方向回答"谁可以认识谁"。两者正交，都要有。**

具体例子：2026-08-21 提取 `LearningDialogs` 时，真正保证边界正确的不是"它是佐"，
而是两条方向约束——它不持有 `MainWindow`；需要回写星级和刷新进度页时，用调用方传入的
`function<bool(int)>` 回调，而不是反向调用窗口。

### 3.4 这个模型说不出接口与契约

药材在锅里是弥散混合的；代码之间靠明确接口通信。决定长期可维护性的，往往不是角色划分，
而是**什么东西跨越边界、以什么形式跨越**。

Athena 最成功的几处设计恰恰是契约驱动的，它们在君臣佐使里没有对应物：

- `resources/athena.json` 是分类/章节/知识点的唯一数据源；
- 稳定函数 ID `cpp.Reference.reference_basics`，不从中文标题推导，不随数组顺序变化；
- 生成产物带 `DO NOT EDIT`，人工代码与生成代码物理隔离。

> **修正：定完角色之后，还要单独回答"边界上传什么"。** 拆分 `LearningDialogs` 时，
> 这个答案就是 `DialogTopic` 结构体——跨界的是一份纯数据，不是一堆 GTK 控件指针。

### 3.5 这个模型说不出生命周期、所有权和时间

方剂是静态配比，程序是活的：谁创建谁、谁先销毁、异步回调回来时对象还在不在。
本项目真实踩过的坑几乎全在这一维度，没有一个能从"君臣佐使"推导出来：

- 对话框用 `make_managed` 创建 + 异步回调持有指针 = use-after-free，改为强制
  `set_hide_on_close(true)` 并延迟到事件循环下一轮再 `delete`；
- 后台线程回传前必须检查 `m_ui_alive`，否则窗口已析构还去更新控件；
- `open_learning_store()` 必须排在 `setup_category_sidebar()` 之前，否则首屏统计恒为 0；
- 手册页不能进 `m_active_page_names`，否则切分类会连 WKWebView 一起销毁。

> **修正：所有权与时序是独立的第三个维度。** RAII、`unique_ptr`、存活标志、构造顺序，
> 这些都不是"角色"能覆盖的。

### 3.6 别让“具体实现者干杂活”贬低了真正的君

作者的排序把"具体实现者"放在最底层。但在 Athena 里，真正创造价值的是 `language/` 下的
教学实验和手册正文——**那才是君，整个 UI 都是为它服务的**。

把"具体实现"当成最低等的杂活，实际风险是：在架构上持续投入，在内容上持续欠账。当前
cpp 分类 12 个章节只有 3 个接入了实现（TypeSemantics、Reference、RAII），
da、dp 两个分类连知识点都还没定义——这就是"君药剂量不足"的表现。

## 4. 建议的完整框架：三个正交维度

君臣佐使只覆盖第一个维度。判断一处代码组织是否合理，三问缺一不可：

| 维度 | 问题 | 本项目的载体 |
| --- | --- | --- |
| 角色与剂量 | 在这条用例里谁是主角？篇幅给对了吗？ | 本文档 |
| 依赖方向 | 谁可以认识谁？箭头有没有反向？ | `AGENTS.md`、`ARCHITECTURE.md` 第 5 节 |
| 生命周期与所有权 | 谁创建、谁销毁？异步回来时还在吗？ | `AGENTS.md` C++ 编码规则、代码内注释 |

## 5. 新增或拆分模块时的四问

1. **用例**：这段代码服务于哪条用例？在这条用例里它是君还是使？篇幅与角色相称吗？
2. **方向**：它需要认识谁？被谁认识？有没有出现下层反向调用上层？
3. **契约**：边界上传递什么？能不能只传纯数据、不传 GTK 控件指针？
4. **生命周期**：谁持有它？它比谁活得久？异步回调回来时它还在吗？

以 2026-08-21 提取 `LearningDialogs` 为例走一遍：

1. **用例**："查看运行历史""做一次 AI 自测"。在这两条用例里对话框是臣（承担主要工作），
   `MainWindow` 退为使（只负责把当前行的知识点交出去）。
2. **方向**：`MainWindow` → `LearningDialogs` → `ContentLoader`/`LearningStore`/`AiService`，
   单向；模块不持有窗口。
3. **契约**：入参是 `DialogTopic` 纯数据；出参是 `function<bool(int)>` 回调。
4. **生命周期**：`m_dialogs` 由窗口在 `open_learning_store()` 之后创建、与窗口同生命周期；
   对话框自身用 `new` + 延迟 delete；异步回调靠 `m_ui_alive` 与 `dialog_alive` 双重判活。

结果：`mainwindow.cc` 从 2324 行降到 1397 行，使药的剂量降下来了。
