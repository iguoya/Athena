# 代码组织：借政府组织结构理解程序结构

本文档记录本项目作者对编程组织的整体看法，以及针对这套看法的评注、修正和补充。
它是**背景观念**，帮助理解 `AGENTS.md` 和 `docs/ARCHITECTURE.md` 里那些规则为什么
这么定；它本身不是可机械校验的硬规则，遇到冲突以 `AGENTS.md` 和 ADR 为准。

## 1. 作者的看法

作者对编程的整体角度是：**一个国家体制内的上下层组织结构，和应用程序的组织结构有相似、
可对应的地方。** 代码各部分应当各司其职，分为四类角色：

| 角色 | 作者的定义 | 政府对应 |
| --- | --- | --- |
| 组织者 | 负责全局的系统和方向的判断、原则的制定，不管细节 | 中央 |
| 协调者 | 分管一个大方向、指导执行；协调上下各方反馈、制定方案 | 省部委 |
| 辅助者 | 有工具倾向，负责专业化工作和通用工作 | 卫生、交通、教育等职能条线 |
| 具体实现者 | 负责各种具体杂活、细节的实现 | 县乡 |

### 1.1 这份类比的定位

类比在工程里的正确用法是**帮你提问**，不是**替你证明**：

- 有用的时候：它给你一个陌生的角度去看熟悉的代码。"顶层窗口是不是把县乡的活干了"
  这个问题，比"这个类是不是太大了"更容易让人看清病灶在哪。
- 越界的时候：它不能证明某个设计是对的。方案对不对，最终由能不能构建、测试过不过、
  依赖有没有成环、生命周期清不清楚来判定。
- 该收手的信号：当讨论从"这段代码的行为是什么"滑向"这个类到底算辅助者还是实现者"，
  说明类比已经不产生新信息了，换第 6 节那三个维度去问。

## 2. 为什么这个类比不牵强

这不是随意比附，它撞上了两条软件工程里已有的正式结论。

**一、层级结构是复杂系统的通解。** Herbert Simon 在《The Architecture of Complexity》
（1962）里论证：复杂系统普遍呈现层级结构，因为分层的系统比同等规模的非分层系统演化得
更快、更能容错。政府分省部委县乡，和软件分层分模块，是**同一个约束下的同一个解**——
单点处理能力有限，超出以后只能分层、分治、授权。

**二、组织结构确实会烙进软件结构。** Conway 定律（1967）：设计系统的组织，其产出的设计
必然复刻该组织的沟通结构。这几乎是对作者判断的直接印证。

但第二条要小心：**Conway 定律是描述，不是规范。** 它说的是"组织结构会变成系统结构"这个
事实，不是"照着组织结构设计系统就对"。业界后来发展出"逆康威操作"——为了得到想要的架构，
反过来去调整团队结构。这条定律更像**警告**：如果不主动设计，组织的毛病会原样长进代码里。
第 4 节列的那些盲区，正是这些毛病。

## 3. 这套看法讲得对的地方

### 3.1 它不是一条四级梯子，而是条块结构

容易被忽略的是：**组织者、协调者、实现者是纵向层级（块），辅助者是横向职能条线（条）**，
条线跨越所有层级存在。这比线性排序丰富，也更贴近代码。

映射到 Athena，作者的目录结构其实已经是按这个思路长出来的：

**块（纵向层级，控制流从上往下）**

| 政府层级 | Athena |
| --- | --- |
| 中央 | `MainWindow`：分类导航、页面切换、模块生命周期 |
| 省部委 | 各 feature 模块：`ProgressPage` 主管学习进度、`LearningDialogs` 主管设置与自测，规划中的 `HandbookPage`、`CodeChapterPage`。**各自对一个方向从头负责到尾** |
| 县乡 | `language/` 下各章节类的成员函数：真正把实验跑出来 |

**条（横向职能，被各层复用）**

| 职能条线 | Athena |
| --- | --- |
| 卫生、交通、教育…… | `registry/` 配置与注册、`storage/` 持久化、`render/` 渲染、`services/` 外部服务、`content/` 内容读取 |

这个结构最有价值的三条推论：

- **各司其职**：`storage/` 不碰渲染，`render/` 不碰 SQLite，`registry/` 不碰 GTK。
- **不越级**：决策层不该亲自去写 SQL 或拼 HTTP 请求体——这正是 `MainWindow` 长期的病症。
- **条线跨层复用**：职能模块要能被任何一层调用。代码在这一点上比政府更省事——不必像
  卫健委那样每级设一个对口机构，一份实现各层共用即可。**代价是这份实现必须对调用者
  一无所知**：无状态、不持有上层引用、不感知自己被哪一层调用。`content/`、`render/`、
  `storage/` 能脱离 GTK 单独测试，正是因为守住了这一条。

### 3.2 协调者与辅助者的分界：是否主导一个方向

部委本身也是职能机构，光看级别分不开协调者和辅助者。真正的分界是
**是否主导一个业务方向、对结果负责**：

- **协调者**拥有一个方向并对它负责，但职责是**指导执行，不是亲自动手**。
  `LearningDialogs` 对"一次自测能不能完整跑通、分数能不能落库"负责，它决定流程、决定
  失败时怎么提示——但它自己不写一行 SQL，不拼一次 HTTP 请求：存取交给 `LearningStore`，
  网络交给 `AiService`，Markdown 转换交给 `markdown_renderer`。
- **辅助者**只提供通用能力，不对任何业务结果负责。`ContentLoader` 只管把字节读出来，
  谁调用、读来干什么，它一概不知道也不该知道。

这条分界有直接后果：协调者可以有业务判断和流程状态，辅助者应当尽量无状态、可被任意层
复用。反过来说，**如果一个协调者开始自己写 SQL、自己拼请求体，它就在替辅助者干活**
——这正是拆分前 `mainwindow.cc` 的状态。

### 3.3 "原则的制定"在代码里落在哪里

作者对组织者的定义里，"原则的制定"这一条最有分量，也最值得单独说：
**它在代码里主要不由某个类承担。**

一个类无法制定原则，它只能遵守或违反原则。Athena 里真正在"制定原则"的是三样东西：

| 组织者的职能 | Athena 中的载体 |
| --- | --- |
| 制度 / 单一数据源 | `resources/athena.json`：分类、章节、知识点的唯一出处 |
| 成文原则 | `AGENTS.md`、`docs/decisions/` 下的 ADR |
| 强制执行 | `scripts/generate_project.py check`：ID 唯一性、标识符合法性、路径存在性，不合规直接非零退出 |

这带出一个重要推论：**架构不是某个顶层类，而是一组约束。** `MainWindow` 更像中办国办
——负责日常运转协调，而不是"中央"本身。这也解释了本项目为什么把校验前置到 Python 生成
器、把 `ChapterCatalog` 降格为"只解码"：原则由制度和校验保证，运行时代码只管遵守。

作者是从组织直觉自己推到这里的，而这正是现代架构观的核心之一，见第 7 节。

## 4. 这套看法的盲区

### 4.1 角色是相对于"某件事"的，不是部门的固有身份

同一个部门在不同任务里角色不同：财政部在预算编制里是主办，在防汛救灾里只是配合保障。
代码同理：`LearningStore` 在"保存熟练度"这件事里是主角，在"AI 自测出题"里只是个存 Key
的配角。

组织模型在这里格外危险：**部门是常设机构，一旦设立就长期存在。** 把角色钉死成模块的固有
属性，最常见的后果就是产生一个**永久的中央**，也就是上帝类。

> **修正：先说清楚"在哪件事里"，再谈谁是主角。** 同一个模块在不同用例里换角色是正常的，
> 不是设计缺陷。也不必强行把每个模块塞进四个格子——分不清是辅助者还是实现者的时候，
> 说明这个划分对当前问题已经不产生新信息了。

### 4.2 条块结构自带的三个老毛病，代码里同样会犯

政府条块结构的经典问题，在代码里有精确对应，可以直接拿来当检查项：

- **条块分割**：职能条线之间互不通气，各自造一份轮子。Athena 的小型版本：
  "读源文件 + 定位成员函数 + 截取全文"这段逻辑，运行历史、AI 自测、实验快照三处都需要，
  却长期各写各的散在 `mainwindow.cc` 里，2026-08-21 才收敛成 `load_member_source_text()`。
- **双重领导**：一个部门既受同级政府领导，又受上级对口部门指导。代码里对应一个模块同时
  被两个不同抽象层次约束，往往是循环依赖和"改一处崩两处"的温床。判断方法很简单：
  数一数这个类被多少个不同层次的调用者直接使用，超过一个就要警惕。
- **层层加码与中间层膨胀**：每加一级都要付成本。拆分大类时最容易顺手造出**纯转发的空转
  中间层**——只是把参数原样传下去，不做任何决策。这种层不减少复杂度，只增加跳转次数。
  ADR 0014 里"不以行数作为唯一目标"就是防这个。

### 4.3 请示汇报在代码里就是循环依赖

这是这套模型最需要警惕的一条。机关运作靠**请示汇报**：下级遇到拿不准的事向上级请示，
上级批复。这在组织里是美德，在代码里是灾难——下层为了"请示"必须持有上层的引用，
依赖箭头立刻成环。

正确的代码做法不是请示汇报，而是：**上级下发一张回执单，下级填好交回，全程不需要知道
上级是谁。** 这就是回调与依赖倒置。

具体例子：2026-08-21 提取 `LearningDialogs` 时，自测评分要更新星级、刷新学习进度页。
若按请示汇报的思路，对话框应当持有 `MainWindow` 并调用它——那就是环。实际做法是
`MainWindow` 传入一个 `function<bool(int)>` 回调，对话框只管把分数填进去，
不知道也不关心谁在处理。

> **修正：依赖方向是独立的一维，且只能单向。** 见 `AGENTS.md` 的"依赖方向"和
> `ARCHITECTURE.md` 第 5 节。

### 4.4 上级信息更多，上层知识更少——最锋利的一条差别

> **政府里上级信息更多**（原则上可要求下级把情况全部上报）；
> **软件里上层知识更少**（只知道抽象接口，对下层实现一无所知）。

"上级"在两个系统里含义几乎相反：一个是权力大且可以无所不知，一个是控制调用顺序但对
内部一无所知。信息隐藏是软件的立身之本，而科层制恰恰允许上级穿透任何下级的内部。

**照体制直觉写代码，最容易写出"上层什么都知道"的紧耦合系统**：窗口直接读页面的控件、
页面直接改服务的内部状态。Athena 里守住这条的做法是跨界只传纯数据（`DialogTopic`），
不传控件指针。

### 4.5 说不出接口与契约

部门之间靠公文往来，但可以打电话、可以开会、格式可以商量。代码不行——决定长期可维护性
的，往往不是角色划分，而是**什么东西跨越边界、以什么形式跨越**。

Athena 最成功的几处设计恰恰是契约驱动的，它们在组织模型里没有对应物：

- `resources/athena.json` 是分类/章节/知识点的唯一数据源；
- 稳定函数 ID `cpp.Reference.reference_basics`，不从中文标题推导，不随数组顺序变化；
- 生成产物带 `DO NOT EDIT`，人工代码与生成代码物理隔离。

> **修正：定完角色之后，还要单独回答"边界上传什么"。** 拆分 `LearningDialogs` 时，
> 这个答案就是 `DialogTopic` 结构体——跨界的是一份纯数据。

### 4.6 说不出生命周期、所有权与并发

机构是常设编制，程序却是活的：谁创建谁、谁先销毁、异步回调回来时对象还在不在。而且
**政府只有一个中央、串行决策，代码里一个类却可以有成千上万个实例并发运行**。

本项目真实踩过的坑几乎全在这一维度，没有一个能从角色划分推导出来：

- 对话框用 `make_managed` 创建 + 异步回调持有指针 = use-after-free，改为强制
  `set_hide_on_close(true)` 并延迟到事件循环下一轮再 `delete`；
- 后台线程回传前必须检查 `m_ui_alive`，否则窗口已析构还去更新控件；
- `open_learning_store()` 必须排在 `setup_category_sidebar()` 之前，否则首屏统计恒为 0；
- 手册页不能进 `m_active_page_names`，否则切分类会连 WKWebView 一起销毁。

> **修正：所有权与时序是独立的第三个维度。** RAII、`unique_ptr`、存活标志、构造顺序，
> 这些都不是"角色"能覆盖的。

### 4.7 级别高低不等于价值贡献，也不等于代码体量

职权上把执行层排在最底是合理的——控制流确实从上往下走。但排序容易连带出价值判断：
底层 = 不重要 = 杂活。

这个副作用在组织模型自己内部就有答案：**中央级别最高，但离群众最远；县乡级别最低，
却是唯一直接面对群众、真正把事办成的一层。**

代码同理，而且还要再加一条组织模型给不了的判据——现实中的机关往往是中间层最庞大，
代码不能学这个：

> **控制流的顶端，应该是代码量的末端。** 顶层薄、核心厚；反过来就是上帝类。

按这条体检：`mainwindow.cc` 曾长期是全项目最大的单文件（ADR 0014 记录时约 2650 行，
提取对话框前仍有 2324 行），而它的职责本该只是导航——**决策层越级办事**，亲自装配对话框
控件树、拼提示词、解析自测 JSON，把职能部门和执行层的活全干了。这正是 ADR 0014 要逐步
拆分它的原因。

同一条判据也照出内容欠账：用户打开 Athena 不是为了看标签栏切换，是为了 `language/` 下
那段能跑、能改、能观察结果的教学代码。而 cpp 分类 12 个章节只有 3 个接入了实现
（TypeSemantics、Reference、RAII），da、dp 两个分类连知识点都还没定义。
拆 `MainWindow` 是对的，但它不产出任何一个新知识点。

### 4.8 政府防的是人不可靠，代码防的是复杂度

组织结构里有大量设计是为了防止人的偏私、懈怠和舞弊——监察、审计、任期、回避、层层签字。
代码不会偷懒也不会舞弊，把这类机制搬进来只增加成本、不增加价值（层层审批 = 层层转发）。

反过来，软件的结构主要是为了对抗**人类理解力的极限**和**变更的成本**，这在组织里对应
较弱。两个系统的目标函数不同，因此：**可以借它的分工形态，不要借它的管控手段。**

## 5. 得失小结：该借什么，不该借什么

| 该借的 | 对应的软件概念 |
| --- | --- |
| 层级分解、逐级授权 | 分层架构；Simon 论证的复杂系统通解 |
| 各司其职 | 单一职责（SRP） |
| 只管大局、不管细节 | 抽象层次一致性（SLAP） |
| 条块二维（层级 × 职能） | layer × module 双维分解 |
| 分管一个方向、指导执行 | 编排与实现分离 |
| 原则由制度制定、由校验强制 | 架构即约束；适应度函数 |

| 不该借的 | 借了会得到什么 |
| --- | --- |
| 请示汇报 | 循环依赖 |
| 上级可穿透下级内部 | 破坏信息隐藏，紧耦合 |
| 层层审批 | 纯转发的浅层，只增跳转不减复杂度 |
| 常设机构（不死不灭） | 忽略生命周期与所有权 |
| 单一实例、串行决策 | 忽略多实例与并发 |
| 监察回避等防人机制 | 代码不会偷懒，这类成本纯属浪费 |
| 中间层最庞大 | 上帝类 |

## 6. 建议的完整框架：三个正交维度

角色划分只覆盖第一个维度。判断一处代码组织是否合理，三问缺一不可：

| 维度 | 问题 | 本项目的载体 |
| --- | --- | --- |
| 角色与体量 | 在这件事里谁是主角？篇幅给对了吗？ | 本文档 |
| 依赖方向 | 谁可以认识谁？箭头有没有成环？ | `AGENTS.md`、`ARCHITECTURE.md` 第 5 节 |
| 生命周期与所有权 | 谁创建、谁销毁？异步回来时还在吗？ | `AGENTS.md` C++ 编码规则、代码内注释 |

## 7. 更进一步的理论坐标

这套看法大致相当于软件工程 1970 年代的结构化分解水平：**按"谁指挥谁"分解**。
后来的发展主要在三个方向上超过了它，且都能直接用在本项目上。

**7.1 按"变化的原因"分解，而不是按层级或流程分解。** Parnas《On the Criteria To Be
Used in Decomposing Systems into Modules》（1972）明确反对按处理步骤划分模块，主张每个
模块隐藏一个**可能会变的决策**。判据从"它归谁管"换成"**什么会跟它一起变**"。

用这条重审 Athena：现有目录划分其实已经基本合格——换 SQLite 只动 `storage/`，换
Markdown 库只动 `render/`，换 AI 服务商只动 `services/`，换配置格式只动生成器。
说明作者的直觉在实践中产出了正确结果，即使表述不够精确。反例也很清楚：
`mainwindow.cc` 里手册、进度、代码页、运行流程混在一起，是四个**不同的变化原因**
挤在同一个模块，所以每次改动都牵连全局。

**7.2 深模块优于浅模块。** Ousterhout《A Philosophy of Software Design》（2018）：
好模块是**接口小、实现深**；只做转发的浅模块是负债，因为调用方要理解的东西没变少，
却多了一层跳转。这直接反驳"层级越完备越好"，也是拆分 `MainWindow` 时最该拿在手里的
判据——每提取一个模块都要问：**它是否真的把一批复杂度关进了小接口后面？**
`LearningDialogs` 合格（三个方法藏起近千行控件装配与异步流程），一个只把参数原样传下去
的页面类就不合格。

**7.3 架构是一组可验证的约束，不是一张组件图。** 这一条作者已经摸到了——"组织者负责
原则的制定"就是这个意思。本项目的 `scripts/check.sh` 与 `generate_project.py check`
正是把架构约束写成可执行检查的做法（业界称适应度函数）。继续往这个方向走，比继续细化
角色划分更有回报。

**结论：这套看法不必抛弃，但应当降级使用。** 做分解决策时用 7.1 的标准（什么会一起变），
判断该不该加层时用 7.2（接口是否变小、复杂度是否真被藏起来）；组织结构的类比留作
**沟通与自查的比喻**——"这一级是不是越位了""胶水是不是比正事还重"，这类问题它问得比
术语更快、更准，这也是它真正的价值所在。

## 8. 新增或拆分模块时的四问

1. **变化原因**：这段代码会因为什么而变？跟它一起变的东西是不是都在同一个模块里？
2. **方向**：它需要认识谁？被谁认识？有没有出现下层反向"请示"上层？
3. **契约**：边界上传递什么？能不能只传纯数据、不传 GTK 控件指针？
4. **生命周期**：谁持有它？它比谁活得久？异步回调回来时它还在吗？

以 2026-08-21 提取 `LearningDialogs` 为例走一遍：

1. **变化原因**：对话框的控件布局、AI 提示词措辞、自测评分规则——这三样都只在"设置与
   自测"这件事上变，和手册排版、进度统计无关，因此应当独立成模块。
2. **方向**：`MainWindow` → `LearningDialogs` → `ContentLoader`/`LearningStore`/`AiService`，
   单向；模块不持有窗口，不向上请示。
3. **契约**：入参是 `DialogTopic` 纯数据；出参是 `function<bool(int)>` 回执。
4. **生命周期**：`m_dialogs` 由窗口在 `open_learning_store()` 之后创建、与窗口同生命周期；
   对话框自身用 `new` + 延迟 delete；异步回调靠 `m_ui_alive` 与 `dialog_alive` 双重判活。

结果：`mainwindow.cc` 从 2324 行降到 1397 行。
