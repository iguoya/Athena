# 代码角色分工：两个中式模型及其边界

本文档记录本项目作者对代码组织的思维模型，以及针对这些模型的评注、修正和补充。
它是**背景观念**，帮助理解 `AGENTS.md` 和 `docs/ARCHITECTURE.md` 里那些规则为什么
这么定；它本身不是可机械校验的硬规则，遇到冲突以 `AGENTS.md` 和 ADR 为准。

## 1. 原始表述

作者的感悟：代码开发中各部分应当各司其职，有组织者、协调者、辅助者、具体实现者。

| 角色 | 作者的定义 |
| --- | --- |
| 组织者 | 只管大局方向，不管细节 |
| 协调者 | 类似参谋角色，负责协调上下各方反馈、制定方案 |
| 辅助者 | 有工具倾向，更多负责专业化工作和通用工作 |
| 具体实现者 | 负责各种具体杂活、细节的实现 |

作者明确指出这套划分有两个来源：**中药方剂的君臣佐使配伍理论**，以及**中国政府的
大体组织架构**。这两个来源不是一回事，分开看才用得准——这是本文档的主线。

### 1.1 这份类比的定位

作者本人的说明是：这只是他对中药配方原则和政府组织原则的粗浅理解，感觉与代码组织有
相似、可对应的地方。本文档按这个定位来写，**不打算把两套理论完整搬进软件工程**。

类比在工程里的正确用法是**帮你提问**，不是**替你证明**：

- 有用的时候：它给你一个陌生的角度去看熟悉的代码。"顶层窗口是不是把县乡的活干了"
  这个问题，比"这个类是不是太大了"更容易让人看清病灶在哪。
- 越界的时候：它不能证明某个设计是对的。方案对不对，最终由能不能构建、测试过不过、
  依赖有没有成环、生命周期清不清楚来判定，不由"这样配伍更合理"来判定。
- 该收手的信号：当讨论从"这段代码的行为是什么"滑向"这个类到底算佐还是算使"，
  说明类比已经不产生新信息了，换第 5 节那三个维度去问。

## 2. 两个来源，各自擅长什么

### 2.1 政府组织架构模型：擅长职能划分与控制流

作者给出的对应是明确的：**中央政府是君——负责全局的系统判断、方向判断和原则的制定；
省部委是臣——各自分管一个大方向、指导执行；卫生交通教育这类职能是佐；县乡是使——
直接办事的末端。**

这里有一个容易被忽略的结构：**它不是一条四级梯子，而是条块结构**。君、臣、使是纵向层级
（块），佐是横向职能条线（条），条线跨越所有层级存在。这比线性排序丰富，也更贴近代码。

映射到 Athena，作者的目录结构其实已经是按这个思路长出来的：

**块（纵向层级，控制流从上往下）**

| 政府层级 | Athena |
| --- | --- |
| 中央（君） | `MainWindow`：分类导航、页面切换、模块生命周期 |
| 省部委（臣） | 各 feature 模块：`ProgressPage` 主管学习进度、`LearningDialogs` 主管设置与自测、规划中的 `HandbookPage`、`CodeChapterPage`。**各自对一个方向从头负责到尾** |
| 县乡（使） | `language/` 下各章节类的成员函数：真正把实验跑出来 |

**条（横向职能，被各层复用）**

| 职能条线 | Athena |
| --- | --- |
| 卫生、交通、教育…… | `registry/` 配置与注册、`storage/` 持久化、`render/` 渲染、`services/` 外部服务、`content/` 内容读取 |

**臣与佐怎么分？** 部委本身也是职能机构，光看级别分不开。真正的分界是
**是否主导一个业务方向、对结果负责**：

- **臣**拥有一个方向并对它负责，但它的职责是**指导执行，不是亲自动手**。
  `LearningDialogs` 对"一次自测能不能完整跑通、分数能不能落库"负责，它决定流程、决定
  失败时怎么提示——但它自己不写一行 SQL，不拼一次 HTTP 请求：存取交给 `LearningStore`，
  网络交给 `AiService`，Markdown 转换交给 `markdown_renderer`。
- **佐**只提供通用能力，不对任何业务结果负责。`ContentLoader` 只管把字节读出来，谁调用、
  读来干什么，它一概不知道也不该知道。

这条分界在代码里有直接后果：臣可以有业务判断和流程状态，佐应当尽量无状态、可被任意层复用。
反过来说，**如果一个"臣"开始自己写 SQL、自己拼请求体，它就在替佐干活**——这正是拆分前
`mainwindow.cc` 的状态。

### 2.1.1 "原则的制定"在代码里落在哪里

作者对君的定义里，"原则的制定"这一条最值得单独说：**它在代码里主要不由某个类承担。**

一个类无法制定原则，它只能遵守或违反原则。Athena 里真正在"制定原则"的是三样东西：

| 君的职能 | Athena 中的载体 |
| --- | --- |
| 制度/单一数据源 | `resources/athena.json`：分类、章节、知识点的唯一出处 |
| 成文原则 | `AGENTS.md`、`docs/decisions/` 下的 ADR |
| 强制执行 | `scripts/generate_project.py check`：ID 唯一性、标识符合法性、路径存在性，不合规直接非零退出 |

这带出一个重要推论：**架构不是某个顶层类，而是一组约束。** `MainWindow` 更像中办国办
——负责日常运转协调，而不是"中央"本身。这也解释了本项目为什么把校验前置到 Python 生成
器、把 `ChapterCatalog` 降格为"只解码"：原则由制度和校验保证，运行时代码只管遵守。

这个模型最有价值的三条推论：

- **各司其职**：`storage/` 不碰渲染，`render/` 不碰 SQLite，`registry/` 不碰 GTK。
- **不越级**：决策层不该亲自去写 SQL 或拼 HTTP 请求体——这正是 `MainWindow` 长期的病症。
- **条线跨层复用**：职能模块要能被任何一层调用。代码在这一点上比政府更省事——不必像
  卫健委那样每级设一个对口机构，一份实现各层共用即可。**代价是这份实现必须对调用者
  一无所知**：无状态、不持有上层引用、不感知自己被哪一层调用。`content/`、`render/`、
  `storage/` 能脱离 GTK 单独测试，正是因为守住了这一条。

### 2.2 中药方剂模型：擅长主次与剂量

方剂的君臣佐使是**贡献模型**，不是职权模型。《素问·至真要大论》讲"主病之谓君，
佐君之谓臣，应臣之谓使"——君药是**针对主病主证**的那一味，不是"管着其他药"的那一味。
方剂里药材之间没有指挥关系，一起在锅里煮。

它比政府模型多出来的东西是**剂量**：君药用量最大，使药用量最轻。映射到代码：
**核心逻辑应当在篇幅上占主导，胶水应当最少。** 这条政府模型给不了——现实中的机关反而
常常是中间层最庞大。

另外两个方剂概念在代码里有很好的对应，值得单独拿出来：

- **佐制**（抑制君药的毒性烈性）→ 代码里的守卫与降级：`query_git_source_state()` 失败时
  静默返回空、AI 返回的 JSON 解析失败时退化为纯文本原样显示、`LearningStore` 打不开时
  应用照常运行只是不保存。这些不是主功能，但没有它们主功能会伤人。
- **引经报使**（把药力引到病位）→ 代码里的路由与适配：`FunctionRegistry` 把稳定 ID
  `cpp.Reference.reference_basics` 引到具体成员函数，这就是标准的引经药。

## 3. 两个来源会给出方向相反的答案

这是一次真实分歧的记录。同样用君臣佐使看 Athena，两种读法给出两张几乎对调的表：

| 角色 | 按**职权轴**（政府模型）：谁指挥谁 | 按**贡献轴**（方剂模型）：谁治主病 |
| --- | --- | --- |
| 君 | `athena.json` + `AGENTS.md`/ADR + 校验器（定原则）；`MainWindow` 代行日常协调 | `language/` 教学实现、手册正文 |
| 臣 | 各 feature 模块 —— 省部委，分管一个方向、指导执行 | `ChapterCatalog`、`LearningStore`、`AiService` |
| 佐 | `content/`、`render/`、`storage/` 等职能条线 | 同左，外加各处守卫与降级路径（佐制） |
| 使 | `language/` 下的具体实现 —— 县乡，直接办事 | `MainWindow`、`FunctionRegistry` —— 引经报使 |

两端对调，中间的"佐"反而一致。原因是两张表量的根本不是同一件事：职权轴问"控制流从哪
发起"，答案自然是顶层窗口在最上；贡献轴问"用户为什么打开这个软件"，答案是教学实验和
手册内容，UI 只是送达手段。

**两种读法都成立，但不能混用。** 危险恰恰在混用的那一刻：

> 如果按职权轴把 `MainWindow` 认作君，又顺手继承方剂模型"君药用量最大"的直觉，
> 就等于给"顶层窗口是全项目最大的文件"发了许可证。

作者自己的定义其实已经堵住了这条路——"组织者**只管大局方向，不管细节**"——只是没有
点破：**在职权轴上，君的"剂量"是决策权重和影响半径，不是代码行数；行数恰恰应该最少。**

两根轴合起来才是最有用的判据：

> **控制流的顶端，应该是代码量的末端。** 顶层薄、核心厚；反过来就是上帝类。

按这条体检，两根轴给出同一个诊断，只是措辞不同。`mainwindow.cc` 曾长期是全项目最大的
单文件（ADR 0014 记录时约 2650 行，提取对话框前仍有 2324 行）：

- 职权轴的说法：**越级办事**——决策层本该只定方向，却亲自装配对话框控件树、拼提示词、
  解析自测 JSON，把职能部门和执行层的活全干了。
- 贡献轴的说法：**使药过量**——引经的胶水膨胀成了全方最重的一味。

诊断措辞不同，处方一样，这正是 ADR 0014 要逐步拆分它的原因。

## 4. 两个模型共同的盲区

### 4.1 角色是相对于"某一方 / 某一件事"的，不是模块的固有身份

方剂里同一味药在不同方中角色不同：甘草在甘草汤、炙甘草汤里是君药（方名即由它而来），
在绝大多数方剂里却是使药，只负责调和诸药。代码同理：`LearningStore` 在"保存熟练度"
这条用例里是主角，在"AI 自测出题"这条用例里只是个存 Key 的配角。

政府模型在这里比方剂模型更危险：部门是常设机构，一旦设立就长期存在。把角色钉死成模块
的固有属性，最常见的后果就是产生一个**永久的君**，也就是上帝类。

> **修正：先说清楚"在哪条用例里"，再谈谁是君。** 同一个模块在不同用例里换角色是正常的，
> 不是设计缺陷。也不必强行把每个模块塞进四个格子——分不清是佐还是使的时候，说明这个
> 划分对当前问题已经不产生新信息了，该换用下面三个维度去问。

### 4.2 条块结构自带的三个老毛病，代码里同样会犯

政府条块结构的经典问题，在代码里有精确对应，可以直接拿来当检查项：

- **条块分割**：职能条线之间互不通气，各自造一份轮子。Athena 的小型版本：
  "读源文件 + 定位成员函数 + 截取全文"这段逻辑，运行历史、AI 自测、实验快照三处都需要，
  却长期各写各的散在 `mainwindow.cc` 里，2026-08-21 才收敛成 `load_member_source_text()`。
- **双重领导**：一个部门既受同级政府领导，又受上级对口部门指导。代码里对应一个模块同时
  被两个不同抽象层次约束，往往是循环依赖和"改一处崩两处"的温床。判断方法很简单：
  数一数这个类被多少个不同层次的调用者直接使用，超过一个就要警惕。
- **层层加码与中间层膨胀**：每加一级都要付成本。拆分大类时最容易顺手造出**纯转发的空转
  中间层**——只是把参数原样传下去，不做任何决策。这种层不减少复杂度，只增加跳转次数。
  ADR 0014 里"不以行数作为唯一目标"就是防这个。

### 4.3 政府模型会**反向鼓励**循环依赖

这是两个模型里最需要警惕的一条。机关运作靠**请示汇报**：下级遇到拿不准的事，向上级请示，
上级批复。这在组织里是美德，在代码里是灾难——下层为了"请示"必须持有上层的引用，
依赖箭头立刻成环。

方剂模型没有这个问题（药材之间本来就不互相调用），但它同样表达不出"佐不许反过来认识君"。

正确的代码做法不是请示汇报，而是：**上级下发一张回执单，下级填好交回，全程不需要知道
上级是谁。** 这就是回调与依赖倒置。

具体例子：2026-08-21 提取 `LearningDialogs` 时，自测评分要更新星级、刷新学习进度页。
若按请示汇报的思路，对话框应当持有 `MainWindow` 并调用它——那就是环。实际做法是
`MainWindow` 传入一个 `function<bool(int)>` 回调，对话框只管把分数填进去，
不知道也不关心谁在处理。

> **修正：依赖方向是独立的一维，且只能单向。** 见 `AGENTS.md` 的"依赖方向"和
> `ARCHITECTURE.md` 第 5 节。

### 4.4 两个模型都说不出接口与契约

药材在锅里弥散混合；部门之间靠公文往来但格式随意。代码不行——决定长期可维护性的，
往往不是角色划分，而是**什么东西跨越边界、以什么形式跨越**。

Athena 最成功的几处设计恰恰是契约驱动的，它们在两个模型里都没有对应物：

- `resources/athena.json` 是分类/章节/知识点的唯一数据源；
- 稳定函数 ID `cpp.Reference.reference_basics`，不从中文标题推导，不随数组顺序变化；
- 生成产物带 `DO NOT EDIT`，人工代码与生成代码物理隔离。

> **修正：定完角色之后，还要单独回答"边界上传什么"。** 拆分 `LearningDialogs` 时，
> 这个答案就是 `DialogTopic` 结构体——跨界的是一份纯数据，不是一堆 GTK 控件指针。

### 4.5 两个模型都说不出生命周期、所有权和时间

方剂是静态配比，机构是常设编制，程序却是活的：谁创建谁、谁先销毁、异步回调回来时对象
还在不在。本项目真实踩过的坑几乎全在这一维度，没有一个能从角色划分推导出来：

- 对话框用 `make_managed` 创建 + 异步回调持有指针 = use-after-free，改为强制
  `set_hide_on_close(true)` 并延迟到事件循环下一轮再 `delete`；
- 后台线程回传前必须检查 `m_ui_alive`，否则窗口已析构还去更新控件；
- `open_learning_store()` 必须排在 `setup_category_sidebar()` 之前，否则首屏统计恒为 0；
- 手册页不能进 `m_active_page_names`，否则切分类会连 WKWebView 一起销毁。

> **修正：所有权与时序是独立的第三个维度。** RAII、`unique_ptr`、存活标志、构造顺序，
> 这些都不是"角色"能覆盖的。

### 4.6 县乡级别最低，却是唯一直接面对群众的一层

职权轴上把执行层排在最底是合理的——控制流确实从上往下走。但排序容易连带出价值判断：
底层 = 不重要 = 杂活。

这个副作用在政府模型自己内部就已经有答案了：**中央级别最高，但离群众最远；县乡级别最低，
却是唯一直接面对群众、真正把事办成的一层。** 级别高低从来不等于价值贡献高低。

代码同理。用户打开 Athena 不是为了看标签栏切换，是为了 `language/` 下那段能跑、能改、
能观察结果的教学代码，和手册里的正文。它在职权轴上是使（县乡），在贡献轴上是君
（主治），这两件事不矛盾——**这也正是本文档 3 节那两根轴看起来相反、实则相容的原因。**

现实数据：cpp 分类 12 个章节只有 3 个接入了实现（TypeSemantics、Reference、RAII），
da、dp 两个分类连知识点都还没定义。架构在持续投入，内容在持续欠账——**君药剂量不足**。
拆 `MainWindow` 是对的，但它不产出任何一个新知识点。

## 5. 建议的完整框架：三个正交维度

角色划分（无论用哪个模型）只覆盖第一个维度。判断一处代码组织是否合理，三问缺一不可：

| 维度 | 问题 | 本项目的载体 |
| --- | --- | --- |
| 角色与剂量 | 在这件事里谁是主角？篇幅给对了吗？ | 本文档 |
| 依赖方向 | 谁可以认识谁？箭头有没有成环？ | `AGENTS.md`、`ARCHITECTURE.md` 第 5 节 |
| 生命周期与所有权 | 谁创建、谁销毁？异步回来时还在吗？ | `AGENTS.md` C++ 编码规则、代码内注释 |

## 6. 新增或拆分模块时的四问

1. **用例**：这段代码服务于哪件事？在这件事里它是主角还是引经？篇幅与角色相称吗？
2. **方向**：它需要认识谁？被谁认识？有没有出现下层反向"请示"上层？
3. **契约**：边界上传递什么？能不能只传纯数据、不传 GTK 控件指针？
4. **生命周期**：谁持有它？它比谁活得久？异步回调回来时它还在吗？

以 2026-08-21 提取 `LearningDialogs` 为例走一遍：

1. **用例**："查看运行历史""做一次 AI 自测"。在这两件事里对话框承担主要工作，
   `MainWindow` 只负责把当前行的知识点交出去。
2. **方向**：`MainWindow` → `LearningDialogs` → `ContentLoader`/`LearningStore`/`AiService`，
   单向；模块不持有窗口，不向上请示。
3. **契约**：入参是 `DialogTopic` 纯数据；出参是 `function<bool(int)>` 回执。
4. **生命周期**：`m_dialogs` 由窗口在 `open_learning_store()` 之后创建、与窗口同生命周期；
   对话框自身用 `new` + 延迟 delete；异步回调靠 `m_ui_alive` 与 `dialog_alive` 双重判活。

结果：`mainwindow.cc` 从 2324 行降到 1397 行。

## 附录：术语出处

本文借用了不少中医方剂学的词。为避免把比喻当成论据，这里标明哪些是原术语、哪些是
本文档为讲代码而造的说法。

**方剂学原有术语**（含义与本文用法一致）：

- **君臣佐使**：方剂配伍的基本结构，语出《素问·至真要大论》"主病之谓君，佐君之谓臣，
  应臣之谓使"。
- **君药 / 臣药 / 佐药 / 使药**；君药针对主病主证且用量较大，使药用量最轻。
- **佐助药 / 佐制药 / 反佐药**：佐药的三种细分，分别是协助治疗兼证、抑制君药毒烈之性、
  以性质相反之药防止格拒。
- **引经报使**：引导药力到达特定病位，相关药物称引经药。
- **调和诸药**：使药的另一职能，甘草为典型。
- **主病主证 / 兼证 / 配伍 / 剂量**。
- **异病同治**：不同病症采用相同治法（与之对应的是同病异治）。
- **药有个性之特长，方有合群之妙用**：徐灵胎《医学源流论》，讲单味药与组方的关系。

**本文为讲代码而造的说法**（不是中医术语，勿当原文引用）：

- "职权轴 / 贡献轴"、"控制流的顶端应该是代码量的末端"——软件判据。
- "使药过量""君药剂量不足""越级办事"——借方剂和机关的词描述代码病症的措辞。
- 把"佐制"对应到守卫与降级、把"引经报使"对应到路由与适配——是本文的映射，不是中医原有
  的引申。
