# Athena 学习工作台参考提案

- 状态：参考提案，尚未实施
- 目的：探索如何通过页面布局、内容组织和代码模块共同实现“思想指导行动，行动验证并深化思想”
- 约束：本文不替代 `AGENTS.md`、`docs/ARCHITECTURE.md` 或已经接受的 ADR；其中的名称、
  字段和交互都只是候选方案，只有经过评审并写入 ADR 后才成为实施方向

## 1. 背景

Athena 的目标不是让学习者只读一套 C++ 文档，也不是只浏览和运行一组代码。

单纯阅读文档容易停留在被动理解，注意力难以保持，也不容易把抽象知识转化为实际判断；
单纯阅读代码则容易失去知识体系和全局框架，陷入语法、变量和实现细节。更合适的学习方式
是在同一个知识点内形成循环：

```text
建立思想与判断框架
        ↓
形成对具体问题的预期
        ↓
编写或运行短小实验
        ↓
观察实际结果
        ↓
比较预期与结果
        ↓
修正、深化并迁移理解
        └──────────────→ 回到新的思想框架
```

学习文档负责讲清概念体系、语义边界、适用条件、常见误区和思维模型；教学代码负责把
思想变成可操作、可观察和可验证的实验。文档不是源码说明书，代码也不是孤立的技巧集合。

## 2. 设计目标

本提案尝试实现以下目标：

1. 学习者随时知道当前知识点在整个 C++ 知识体系中的位置。
2. 阅读过程包含问题、预测、实验、对照和反思，避免长时间被动阅读。
3. 每个实验回答一个明确的知识问题，而不是一次展示大量无关语法。
4. 代码展示保持聚焦，但仍能查看真实完整源码，不把 Athena 变成 IDE。
5. 实验反馈能够推动学习者修正理解，也能暴露文档的遗漏和边界。
6. 页面模块之间只通过稳定知识点 ID 和小数据对象协作，保持 `MainWindow` 为轻量协调者。
7. 不适合单次实验表达的理论内容继续由手册承担，不为了形式统一而强行代码化。

## 3. 两层学习结构

### 3.1 宏观层：知识地图

宏观层回答“我在哪里、为什么要学、接下来能做什么”。初期只需要表达三类关系：

```text
requires      前置知识
contrasts     对比项或容易混淆的知识
leads_to      后续知识或应用方向
```

例如：

```text
对象与生命周期
    └── requires → 引用基础
                       ├── contrasts → 指针
                       ├── leads_to → const 引用
                       ├── leads_to → 返回引用
                       └── leads_to → 转发引用
```

知识地图的首要用途是建立全局位置、导航和迁移关系，不应演变成庞大但无法辅助学习的装饰性
关系图。

### 3.2 微观层：知识点学习闭环

单个可实验知识点采用以下阶段：

1. **问题**：本节究竟要解决什么，而不是只给出一个术语。
2. **思想**：说明动机、核心语义、思维模型以及与相邻概念的差异。
3. **预测**：要求学习者在看到结果前作出编译、行为、生命周期或输出判断。
4. **行动**：运行只验证一个主要命题的短小实验。
5. **对照**：并列展示原有预期、实际结果和产生差异的原因。
6. **反思**：记录原有理解哪里不完整，哪些边界需要修正。
7. **迁移**：改变一个条件，在新场景中重新判断，避免只记住固定输出。

这是一种指导顺序，不意味着 UI 必须强制锁住步骤。预测可以跳过，但界面应明确提示；
理论知识也可以通过思想实验、反例或情境判断完成闭环，不要求每项内容都生成 C++ 函数。

### 3.3 对不同 C++ 知识点的适用性

这套方法抽象的是人的学习过程，而不是引用、生命周期或某一种 C++ 特性的表现形式，因而
可以覆盖大多数 C++ 知识点。应当统一的是“知识位置 → 核心问题 → 思想框架 → 预期 →
行动 → 证据 → 反思 → 迁移”的认知骨架；应当允许变化的是行动方式、证据类型和页面呈现。

“行动”不等于只能调用一个向 `ostream` 输出文本的成员函数。不同知识点适合不同证据：

| 知识点类型 | 适合的行动 | 主要观察对象 |
|---|---|---|
| 引用、值语义、移动语义 | 运行短代码 | 对象值、构造析构、生命周期 |
| 类型推导、模板、Concepts | 预测类型并编译 | 推导类型、约束匹配、编译结果 |
| 重载、隐式转换 | 预测函数选择 | 重载决议、歧义和诊断信息 |
| RAII、智能指针 | 操作资源和所有权 | 析构顺序、引用计数、资源释放 |
| 异常安全 | 在不同阶段注入异常 | 状态保持、资源释放和保证等级 |
| 并发 | 改变同步和线程交错条件 | 状态轨迹、同步关系和竞态 |
| STL 算法与容器 | 改变输入或操作序列 | 数据变化、迭代器和复杂度趋势 |
| 数据结构与算法 | 单步执行并调整规模 | 状态轨迹、步骤数和空间占用 |
| 编译、链接与模块 | 修改多文件关系并构建 | 编译/链接诊断和构建产物 |
| API 与工程设计 | 对比两个设计方案 | 所有权、依赖方向、扩展和修改代价 |
| 纯理论与原则 | 情境判断或思想实验 | 推理过程、适用边界和权衡 |

因此，页面的知识地图、学习主线、行动证据和反思迁移四个角色可以保持稳定，实验室内部则
根据知识点选择不同的表达方式。不能把所有内容都压缩成“源码 + 运行按钮 + stdout”。

### 3.4 统一骨架不等于统一模板

本提案不要求每个知识点机械具备预测输入框、运行按钮、stdout、反思文本和迁移问题。
更合适的规则是：学习闭环在认知意义上完整，但各阶段可以采用不同形式，也允许轻量化。

- 简单语法知识可以只做一次判断和一次运行。
- 编译期知识应展示类型、约束或诊断，不必伪造运行输出。
- 生命周期知识适合使用对象和资源状态时间线。
- 算法知识适合展示步骤轨迹和输入规模变化。
- 工程设计适合使用场景比较和修改影响分析。
- 纯理论内容可以通过反例、情境选择和思想实验完成验证，不强行生成函数。
- 已经非常直观的实验不要求重复填写长篇反思。

统一的意义在于让每个知识点都回答“为什么、我预期什么、证据是什么、理解如何变化”，
不是让所有页面拥有相同数量的控件。

## 4. 页面布局候选

建议把代码知识点页面逐步演化为学习工作台：

```text
┌─────────────────────────────────────────────────────────────────────┐
│ C++ › 类型系统 › 引用 › const 引用          本知识点位置 / 掌握程度 │
├──────────────┬──────────────────────────────┬───────────────────────┤
│ 知识地图      │ 学习主线                     │ 实验室                │
│              │                              │                       │
│ 前置知识      │ 1. 本节要回答的问题           │ 我的预测              │
│ 相关知识      │ 2. 为什么需要这个能力         │ ○ 能编译  ○ 不能编译 │
│ 后续知识      │ 3. 核心语义与思维模型         │                       │
│ 常见混淆      │ 4. 适用边界与常见误区         │ 聚焦后的真实源码       │
│              │ 5. 实验前先做判断             │                       │
│ ○ 普通引用    │                              │ [运行实验]            │
│ ● const 引用 │ ─── 实验检查点 ───           │                       │
│ ○ 转发引用    │                              │ 实际输出              │
│              │ 6. 结果为什么如此             │ 预期 / 实际对照        │
│              │ 7. 改变条件会怎样             │                       │
├──────────────┴──────────────────────────────┴───────────────────────┤
│ 我的反思：原来的理解是什么？实验改变了什么？还能迁移到哪里？       │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.1 左侧知识地图

左侧展示前置、对比和后续关系。它不是传统章节目录的简单改名，而是用来防止知识点孤立。
初期可以继续复用现有章节导航，只在当前知识点附近显示少量直接关系。

### 4.2 中间学习主线

中间是文档主体，但不写成连续堆叠的长篇说明。适合实验的段落按以下节奏展开：

```text
提出问题 → 解释思想 → 要求预测 → 插入实验检查点 → 解释结果 → 改变条件再判断
```

不应为了视觉效果把每一段都切成独立卡片；重点是形成认知节奏，而不是增加容器和装饰。

### 4.3 右侧实验室

实验区只提供验证当前知识点所需的信息：

- 当前实验要验证的问题；
- 学习者的预测；
- 聚焦后的真实成员函数；
- 运行按钮和实际输出；
- 预期与实际结果的差异；
- 一个或两个条件变体。

默认不展示整章所有实现，避免代码淹没知识点；同时保留“查看整章源码”入口，继续满足真实
源码可见的项目原则。

### 4.4 底部反思区

反思区关注认知变化，而不是要求写长篇笔记：

```text
我原来认为……
实验实际说明……
需要补充的边界是……
这个结论还能用于……
```

最值得持久化的是预测与实际结果不一致的地方，因为这通常代表真正发生了学习。

### 4.5 窄窗口适配

三栏布局只适合足够宽的桌面窗口。窗口变窄时，建议保留知识点标题和阶段状态，将内容改成：

```text
学习主线 / 实验室 / 知识关系
```

三个局部标签或顺序页面，避免把三栏同时压缩到无法阅读。知识地图在窄窗口中可以退化为
当前知识点附近的关系列表。

## 5. 内容配置候选

`resources/athena.json` 继续作为分类、章节、知识点和稳定 ID 的唯一数据源。可考虑为
`subchapter` 增加可选的学习结构字段：

```json
{
  "name": "const_reference",
  "title": "const 引用",
  "description": "理解 const 引用的只读语义及临时对象绑定规则。",
  "learning": {
    "question": "const 引用为什么可以安全绑定临时对象？",
    "document": "resources/articles/cpp/reference_overview.md",
    "prerequisites": [
      "cpp.Reference.reference_basics"
    ],
    "contrasts": [
      "cpp.Reference.return_by_reference"
    ],
    "experiment": {
      "prediction": "绑定临时对象后，它会在什么时候销毁？",
      "observe": [
        "引用能否继续读取值",
        "引用是否允许修改对象"
      ],
      "reflection": "const 限制的是引用接口，还是对象本身？"
    }
  }
}
```

这里的自然语言只定义知识问题、观察目标和反思方向，不保存大段正文，也不复制实现代码。
真实课程代码仍由 `implementation.header` 和 `subchapter.name` 定位。

如果担心一次扩展过多，第一阶段可以只引入：

```text
question
prediction
observe
reflection
```

前置、对比和后续关系在第二阶段再加入。

## 6. Markdown 实验检查点候选

学习文档可以主动声明“讲到这里需要采取什么行动”，而不是由代码反向生成文档：

```markdown
## const 引用解决什么问题

函数只需要读取参数，但又不希望发生复制时，可以使用 const 引用。

:::prediction
临时对象绑定到 const 引用后，会在完整表达式结束时立即销毁吗？
:::

:::experiment cpp.Reference.const_reference
观察临时对象的可访问时间，以及通过引用进行修改是否能通过编译。
:::

## 为什么会得到这个结果

这里解释生命周期延长和 const 访问路径。
```

这些指令只是候选格式。实施前需要明确解析失败行为、稳定 ID 校验、HTML 输出和未知指令
处理策略，并通过 ADR 固化。普通 Markdown 仍应保持可读，不能让文档脱离 Athena 后完全
无法理解。

## 7. 代码模块候选

建议保持 `MainWindow` 的轻量协调边界，引入章节或知识点范围内的学习工作台协调者：

```text
MainWindow
└── LearningWorkspacePage
    ├── KnowledgeMapPane
    ├── LessonPane
    ├── ExperimentLab
    └── ReflectionPane

GTK-independent
├── LearningUnitCatalog
├── LearningSession
├── LessonAssembler
├── KnowledgeGraph
├── FunctionRegistry
├── SourceLocator
├── ExperimentRunner
└── LearningStore
```

### 7.1 MainWindow

只负责打开分类或章节、创建和缓存页面、跨章节导航以及模块生命周期，不感知预测文本、
实验阶段、文档位置或知识关系。

### 7.2 LearningWorkspacePage

负责同步知识地图、学习主线、实验区和反思区，并通过稳定知识点 ID 协调子模块。它不执行
具体实验、不解析原始 JSON，也不直接处理 SQLite 细节。

### 7.3 LearningSession

学习过程应成为 GTK 无关、可以单元测试的状态，而不是散落在按钮回调中的控件状态：

```cpp
enum class LearningPhase {
    Orient,
    Understand,
    Predict,
    Experiment,
    Compare,
    Reflect,
    Transfer
};

struct LearningSession {
    string knowledge_id;
    LearningPhase phase;
    string prediction;
    optional<ExperimentResult> result;
    string reflection;
};
```

实际实现时应避免为了展示流程而强制用户机械完成每一步。状态模型主要用于组织界面、保存
有价值的认知反馈，并保证流程可以脱离 GTK 测试。

### 7.4 模块协作

```text
KnowledgeMapPane ──知识点 ID──┐
LessonPane       ──学习动作───┼→ LearningWorkspacePage
ExperimentLab   ──实验结果───┤
ReflectionPane  ──反思内容───┘
                                  │
                                  ├→ ExperimentRunner
                                  ├→ LearningSession
                                  └→ LearningStore
```

页面之间不互相持有 GTK 控件；跨章节动作继续经 `MainWindow`，同一工作台内部通过小数据
对象和回调协作。

### 7.5 证据类型与呈现器

可以在领域层引入少量稳定的证据类型，而不是按章节硬编码页面分支：

```cpp
enum class EvidenceKind {
    RuntimeOutput,
    CompileResult,
    TypeDeduction,
    Diagnostic,
    StateTransition,
    ResourceLifetime,
    PerformanceComparison,
    DesignTradeoff,
    ThoughtExperiment
};
```

`EvidenceKind` 只表达主要学习证据，不规定具体 GTK 控件树。实验区可以通过独立呈现器适配：

```text
ExperimentLab
├── RuntimeOutputView
├── CompileResultView
├── TypeDeductionView
├── DiagnosticView
├── StateTransitionView
├── LifetimeTimelineView
├── PerformanceComparisonView
├── DesignTradeoffView
└── ThoughtExperimentView
```

呈现器只接收结构化数据，不直接调用具体课程类，也不反向更新 `MainWindow`。新增证据形式时，
优先增加新的结果类型和呈现模块，不在 `LearningWorkspacePage` 中堆叠章节名称判断。

典型使用方式包括：

- **类型推导**：先预测 `auto`、引用和 `const` 属性，再展示编译器确认的类型关系。
- **模板与 Concepts**：展示哪个约束不成立以及关键诊断，不把编译失败伪装成运行失败。
- **RAII**：用时间线展示构造、所有权转移、异常、栈展开和析构释放。
- **容器迭代器**：对比扩容前后容器状态以及迭代器有效性。
- **设计原则**：在增加第二前端、第二实现或新需求后，比较两个方案的依赖和修改范围。

### 7.6 实验执行模型的渐进演化

当前统一成员函数签名适合运行时输出型知识点：

```cpp
void method(ostream& output) const;
```

它应继续作为简单实验的低成本路径，不需要立即废弃。但预期编译失败、多文件链接、模板
诊断、结构化生命周期事件、性能对比和并发轨迹无法长期只用一段字符串准确表达。

当第二种、第三种证据形式通过真实知识点验证后，可以通过新的 ADR 设计统一结构化模型：

```cpp
struct ExperimentRequest {
    string knowledge_id;
    map<string, string> parameters;
};

struct ExperimentEvent {
    string type;
    string title;
    string detail;
};

struct ExperimentResult {
    bool succeeded;
    string output;
    vector<ExperimentEvent> events;
    optional<string> diagnostic;
};
```

这只是方向示例，不是当前接口决策。迁移时应保持简单输出实验的编写成本，避免为了未来
可能性提前重写所有已实现章节。

## 8. 学习记录候选

可以考虑保存：

```text
知识点 ID
├── 是否完成关键阅读
├── 实验前预测
├── 实际结果摘要或运行历史引用
├── 是否识别预测差异
├── 一句话反思
└── 自测掌握程度
```

不建议为了数据量保存每次滚动位置、每次点击或阅读时长排行榜。这些数据难以解释学习质量，
也会增加存储和界面复杂度。

## 9. 可继续探索的学习模式

### 9.1 反事实实验

一次只改变一个条件，建立语义边界：

```text
const T&  → 能否绑定临时对象？
T&        → 会发生什么？
T&&       → 又有什么不同？
```

### 9.2 错误驱动学习

先展示常见错误判断或危险代码，让学习者定位问题，再展示诊断和正确方案。C++ 的生命周期、
所有权、异常安全和未定义行为尤其适合这种模式。

### 9.3 概念迁移

知识点结束后连接到真实工程场景：

```text
const 引用
    → 避免复制
    → API 参数设计
    → 生命周期约束
    → range-for
    → 模板转发中的引用折叠
```

迁移关系用于建立全局理解，不要求立即实现所有后续实验。

## 10. 精简版先行方案

完整学习工作台涉及知识关系、文档检查点、状态模型、多种证据呈现和新的页面模块，不适合
一次照搬。更稳妥的起点是在现有 `CodeChapterPage` 上验证最小学习闭环：

```text
理解核心问题 → 可选地形成预测 → 运行现有实验 → 对照结果 → 获得反思提示
```

精简版不改变 Athena 当前的主要页面结构和执行模型，只增加能让“运行代码”变成“验证
思想”的少量信息和控件。

### 10.1 精简版布局

保留现有知识点、源码和结果三栏，在顶部增加两行学习引导，在结果区增加预测与对照：

```text
┌─────────────────────────────────────────────────────────────────────┐
│ const 引用                                            [说明文档]     │
│ 理解 const 引用的只读语义以及临时对象绑定规则                       │
├─────────────────────────────────────────────────────────────────────┤
│ 核心问题：const 引用为什么可以绑定临时对象？                        │
│ 实验观察：运行前先判断临时对象会在什么时候销毁。                    │
├──────────────┬──────────────────────────────┬───────────────────────┤
│ 知识点列表    │ 真实源码                     │ 实验与结果            │
│              │                              │                       │
│ 引用基础      │ void const_reference(...)    │ 运行前想一想           │
│ const 引用   │ {                            │ [输入我的预测……]      │
│ 参数传引用    │     ...                      │                       │
│ 返回引用      │ }                            │ [运行实验]             │
│              │                              │                       │
│              │                              │ 实际输出               │
│              │                              │ ...                   │
│              │                              │                       │
│              │                              │ 对照提示               │
│              │                              │ 结果与原判断有何不同？ │
└──────────────┴──────────────────────────────┴───────────────────────┘
```

只增加四个学习元素：

1. **核心问题**：明确当前知识点究竟要解决什么。
2. **实验观察点**：告诉学习者运行时需要注意什么现象。
3. **运行前预测**：可选输入，不填写也能运行，不增加提交按钮。
4. **运行后对照**：并列显示原预测、实际输出和一句反思提示，不自动评分。

完整理论、语义边界和常见误区继续通过现有“说明文档”按钮进入手册阅读；精简版不把
WebView 嵌入代码页，也不立即实现文档与实验的双向联动。

### 10.2 控件与交互

- 核心问题和观察点使用普通 `Gtk::Label`，不是按钮或链接。
- “说明文档”继续使用现有按钮和手册跳转。
- 预测使用单行 `Gtk::Entry`；它是思考辅助，不是必须提交的答案。
- 运行继续使用现有 GTK 按钮，运行完成后可以改为“再次运行”。
- 实际输出继续显示在现有结果框。
- 对照和反思先用只读文本，不增加对话框、评分或数据库写入。
- 切换知识点时第一版可以直接清空预测；是否保留到当前会话以后根据真实使用决定。

整个流程就地完成，不增加“下一步”“确认预测”“揭晓答案”等向导式按钮，也不弹出新的
学习对话框。

### 10.3 最小配置扩展

建议只给 `subchapter` 增加一个可选 `learning` 对象：

```json
{
  "name": "const_reference",
  "title": "const 引用",
  "description": "理解 const 引用的只读语义及临时对象绑定规则。",
  "learning": {
    "question": "const 引用为什么可以绑定临时对象？",
    "prediction": "运行前判断临时对象会在什么时候销毁。",
    "observation": "观察 const 引用存在期间是否仍然能够读取对象。",
    "reflection": "实际结果改变了你对对象生命周期的哪个理解？"
  }
}
```

四个字段只承担学习引导：

```text
question       核心问题
prediction     运行前思考方向
observation    实验中观察什么
reflection     运行后思考方向
```

没有 `learning` 的旧知识点保持现有页面和行为。配置中不增加前置关系、知识图谱、证据类型、
大段正文或重复代码。

### 10.4 最小代码改动

精简版不引入 `LearningWorkspacePage`，只扩展已有模块：

```text
MainWindow
└── CodeChapterPage
    ├── 现有知识点列表
    ├── 新增学习引导区
    ├── 现有源码区
    └── 现有结果区
        ├── 新增预测输入
        ├── 现有运行按钮
        ├── 现有输出
        └── 新增对照与反思提示
```

可以增加一个小数据结构：

```cpp
struct LearningPrompt {
    string question;
    string prediction;
    string observation;
    string reflection;
};
```

`SubchapterMeta` 可选持有 `LearningPrompt`，`CodeChapterPage` 在切换知识点时更新控件。
`MainWindow` 不感知新增字段，也不增加新的服务类或页面间依赖。

### 10.5 执行方式保持不变

精简版继续使用当前执行链：

```text
构建 Athena 时预先编译教学成员函数
        ↓
用户点击运行
        ↓
ExperimentRunner 即时调用真实 FunctionRegistry 入口
        ↓
重新产生输出、耗时、源码快照和运行历史
```

因此不引入本机编译器检测、动态编译、编译诊断目录或结构化证据模型。预先编译与即时运行
并不冲突：编译发生在构建应用时，真实执行发生在用户点击时。

### 10.6 第一版明确不做

- 不创建完整 `LearningWorkspacePage`。
- 不实现知识地图和知识点依赖关系。
- 不增加 Markdown 自定义实验指令。
- 不把 WebView 嵌入代码页。
- 不引入 `LearningSession` 状态机。
- 不持久化预测和反思，不修改 SQLite 格式。
- 不增加 `CompilationRunner` 或任意代码即时编译。
- 不支持多种 `EvidenceKind` 和专用证据呈现器。
- 不修改 `ExperimentRunner`、`FunctionRegistry` 和现有实验函数签名。
- 不要求一次补齐所有章节的学习引导字段。

### 10.7 小范围验证

建议只选择两个性质不同的知识点试用：

```text
cpp.Reference.const_reference
cpp.TypeSemantics.auto_deduction
```

前者偏运行时行为和生命周期，后者偏类型判断。第一版仍都使用当前预编译即时运行方式，
只验证以下问题：

1. 核心问题是否比单独的 `description` 更能建立学习方向？
2. 运行前预测是否真的促使学习者思考，而不是增加负担？
3. 原预测与实际输出并列后，是否更容易发现理解偏差？
4. 反思提示是否有帮助，还是显得重复？
5. 新增区域是否明显挤压源码和结果空间？

只有真实使用证明这套最小闭环有效后，才进入后续完整工作台阶段。

## 11. 完整方案的分阶段落地建议

### 第一阶段：在精简版基础上增强代码页

风险最低，优先验证学习闭环是否真正有帮助：

1. 顶部增加核心问题和知识位置。
2. 运行按钮附近增加预测提示。
3. 结果区增加预期与实际对照。
4. 实验后增加一个反思或迁移问题。
5. 根据精简版使用结果决定是否引入 GTK 无关的最小 `LearningSession`。
6. 为少量已实现知识点手工编写完整闭环，进行真实使用验证。

### 第二阶段：学习工作台与知识关系

1. 引入 `LearningWorkspacePage`。
2. 拆分 `KnowledgeMapPane`、`LessonPane`、`ExperimentLab` 和 `ReflectionPane`。
3. 扩展配置契约并由生成器校验稳定知识点关系。
4. 支持文档中的实验检查点。
5. 完成宽窗口三栏和窄窗口顺序布局。
6. 用两个性质不同的知识点验证证据抽象，例如运行时输出与编译诊断，避免只根据引用类
   知识设计接口。

### 第三阶段：深化学习反馈

1. 反事实实验。
2. 错误驱动案例。
3. 跨章节迁移关系。
4. 预测与反思的持久化。
5. 根据真实使用结果评估哪些数据值得进入熟练度计算。
6. 按实际课程需求增加生命周期、状态轨迹、性能或设计权衡呈现器，不追求一次覆盖全部
   `EvidenceKind`。

## 12. 风险与边界

- 不要一次引入完整知识图谱、复杂状态机和大量新字段；先验证最小闭环。
- 不要把预测步骤做成妨碍快速实验的强制表单。
- 不要用大量卡片、徽章和动画掩盖内容结构。
- 不要把源码编辑、任意编译参数和调试器加入学习工作台，使其变成 IDE。
- 不要把所有知识点强制转换成“运行函数并查看 stdout”，也不要为追求统一而伪造不符合
  知识性质的实验形式。
- 不要因为某个知识点难以实验就降低理论内容质量或强行编写无意义函数。
- 不要让 Markdown 自定义指令只能被 Athena 读取而失去普通文本可读性。
- 不要让知识关系、反思记录和学习阶段反向进入 `MainWindow`。
- 不要在确认配置契约和 ADR 前实施不可逆的数据格式变化。

## 13. 需要进一步验证的问题

在决定实施前，至少应通过小范围原型回答：

1. 学习主线和实验室并排，是否比现有源码/结果布局更易理解？
2. 预测输入是自由文本、选项还是只提供思考提示？
3. 哪些知识点适合保存预测，哪些只需要即时思考？
4. 反思是否需要持久化，还是只作为当前会话提示？
5. 知识地图显示多少关系才不会增加认知负担？
6. Markdown 实验检查点是否值得引入自定义语法？
7. 宽窗口与窄窗口布局在 macOS 和 Ubuntu 上是否都能稳定工作？
8. 学习闭环是否提升真实理解，而不只是增加点击步骤？
9. 第一批证据类型应该覆盖哪些差异明显的 C++ 知识点，才能验证抽象不是为单一章节定制？
10. 哪些证据可以复用统一结果模型，哪些应保持专用数据结构和呈现器？

如果原型验证通过，应新增 ADR，明确最终采用的配置字段、状态模型、模块边界、迁移策略和
验证要求，再进入正式实现。
