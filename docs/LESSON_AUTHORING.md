# 学习页编写范式

这份文档讲**怎么为一章选择表达手段**，不是一套要照填的模板。

`cpp.TypeSemantics` 是目前唯一写完的章，它的节结构（四种写法对照、逐步演示的
对象图、值类别矩阵）是**那些知识点的性质**决定的，不是通用骨架。下一章如果
照着它的目录抄一遍，抄到的是形状，不是它为什么长这样。

> 相关约束见 `AGENTS.md`（GTK 与 Blueprint 规则、学习内容分层）、
> [ADR 0028](decisions/0028-outline-process-experiment-layering.md)（三层分工）、
> [ADR 0031](decisions/0031-knowledge-type-drives-teaching-actions.md)（知识类型
> 决定教学动作）、[ADR 0033](decisions/0033-live-visuals-and-interaction.md)
> （数据驱动与互动优先）。

## 1. 先判断，再选手段

写一节之前，先回答三个问题。答案不同，这一节该有的东西就不同。

**这个知识点是什么类型（ADR 0031）？**

| 类型 | 教学动作 | 落到页面上 |
|---|---|---|
| 概念 | 正例反例并排，辨析边界 | 对照块、分类矩阵、误区 callout |
| 技能 | 示范加变式练习 | 代码块 + 逐步演示 + 换条件再判断 |
| 策略 | 在情境里选择并说明依据 | 几个情境并列，先自己判断再看说明 |

**它能不能用一次运行观察到？**

能，就一定要有实验入口，并且让读者**先预测再运行**。不能（比如"什么时候该给一组
值独立类型"这种判断），就不要硬造一个跑起来没有信息量的实验——改用情境选择。

**它的难度与掌握目标是多少？**

`familiar` 的知识点不必配齐全套：讲清它解决哪类问题、边界在哪就够了，
剩下的留到真正需要时再回来。`master` 的才值得上逐步演示和多组对照。

## 2. 可用的手段

按"信息量 / 成本"排，不是按顺序都用一遍。

| 手段 | 什么时候用 | 怎么做 |
|---|---|---|
| 正文段落、要点清单 | 陈述规则、列边界 | `lesson::prose` / `lesson::bullets` |
| callout | 点出要害、标记误区、给选择建议 | `lesson::callout`，五种语气见下 |
| 带标题的内容区 | 把一节切成几个可独立读的块 | `lesson::section` |
| 代码块 | 展示真实写法，尤其是几种写法的对照 | `.blp` 里用 `native-lesson-code` 样式 |
| 静态 SVG | 概念示意、不随数据变的关系图 | `lesson::figure`，图放 `resources/articles/<分类>/images/` |
| **数据驱动的图** | 先修关系、评级、实时熟练度 | `Gtk::DrawingArea` 自绘，数据取自 `ChapterCatalog` |
| 逐步演示 | 一个语义过程要分步看清楚 | `DrawingArea` + 步进控件，默认静止 |
| 学习单元 | 讲解中间插一次预测 | `LearningUnit` + `LearningUnitView`，**不写库** |
| 随堂考核 | 一节末尾的多题小测 | `Checkpoint` + `CheckpointView`，**按正确率落库** |
| 实验入口 | 判断需要真实输出来检验 | 按钮触发 `open_experiment` |

callout 的五种语气（`lesson::CalloutKind`）：`Why` 解释为什么、`Key` 点出要害、
`Note` 补充说明、`Trap` 常见误区、`Use` 怎么选。语气对应配色，别混用。

## 3. 组件怎么用

结构模板在 `resources/ui/lesson_blocks.blp`，API 在 `ui/lesson_blocks.h`。
它们只负责那些**结构完全同构、只有文字不同**的块——`type_semantics` 里这类块
占了两千多行的将近一半。

```cpp
#include "ui/lesson_blocks.h"

// host 是这一节在 .blp 里预留的容器
auto& body = lesson::section(host, "为什么要区分这两种写法");
lesson::prose(body, "先说结论：它们在……");

auto& trap = lesson::callout(body, lesson::CalloutKind::Trap, "常见误区");
lesson::bullets(trap, {
    "以为两者等价——它们在窄化检查上规则不同",
    "以为编译器会提醒——这一步没有任何检查",
});

lesson::figure(body, "/app/articles/cpp/images/xxx.svg", 380, "图注说明看什么");
```

**什么时候不要用它们**：对象图、值类别矩阵、知识点路线图这类需要 Cairo 自绘、
或者结构由运行时数据决定的部分，各写各的。硬套模板会把有教学信息量的差异磨平，
那比多写几行更糟。

## 4. 一节的收尾

回顾与自查的**职责**要落实，形式不固定。一节已经有随堂考核时，不要再补一段
小结——考核逐题判分给解析，功能已经落实，再写一段概括是形式化重复。

判断标准是"有没有地方让读者回头确认自己掌握了什么"，不是"有没有一个叫
「小结」的标题"。

## 5. 不要做的事

- **不要每节都配齐同一套组件**。一节该有什么由它的知识点性质决定；
  `familiar` 档的知识点配上逐步演示和三组对照，是浪费读者的注意力。
- **不要把 `type_semantics` 的节标题抄过来**。"边界一/边界二""三个区分"
  是那些知识点恰好有那么多个边界，不是通用小节名。
- **不要为了凑格式加内容**。缺一个块不是欠账，读者卡住才是。
- **不要把能由数据算出来的画成静态图**。先修关系、难度、掌握目标、熟练度
  都在 `athena.json` 和学习库里，画成 SVG 就等着漂移（ADR 0033、0036）。
- **不要在一章里重复表达同一个维度**。大纲那张路线图用配色编码掌握目标，
  导览那张就用文字标难度——两个维度各占一个通道。
