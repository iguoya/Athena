# ADR 0168：相对成熟的应用按同一标准进入发布

- 日期：2026-10-17
- 状态：已接受（使用者：只要相对成熟完善，都可以进入发布流程，不要区别对待）
- 关系：延伸 [ADR 0081](0081-unified-release.md)；取代 [ADR 0151](0151-chinese-chess-app.md) 与 [ADR 0153](0153-snake-app.md) 后果里「发版清单不加入，等稳定后再说」这两句。两篇原文不改。

## 背景

统一发版是一个 `v*` tag、一份 Athena Release。Tauri 应用进 `release.yml` 的同一矩阵，C++ 旧窗口、驾考、拾阶各走自己的打包作业，最后合成一次发布。

0151、0153 在应用刚立项时写了「先不进发版清单」。课和壳已经能独立安装之后，这两句变成了点名排除：同样成熟的 gtkmm 可以进，贪吃蛇和中国象棋不行。使用者要求取消这种区别。

## 决策

1. **进不进发布，只看是不是相对成熟的可安装应用。** 壳能打出安装包，课或查阅内容已经在用，就进矩阵。不按应用名字、技术栈来历或「等以后再说」单独留在外面。
2. **还不算成熟的，同一条标准挡在外面。** `lifecycle: archived` 的空壳，以及课表仍全部是 `planned` 占位的应用（当前是端侧 AI），不进。有了真实内容，按第 1 条加，不另写豁免。
3. **打包作业按技术栈分，名单不按技术栈分。** Tauri 应用进 `tauri-apps` 矩阵（Windows NSIS、macOS DMG、Linux DEB）。Meson / Flutter / 带签名更新器的应用继续用现有作业。Qt、Electron 等还没有对应作业的，补作业之前不假装已经在发，补上之后用同一条成熟度标准。
4. **中文界面名不进安装包里的二进制名。** `productName` 可以是中文（窗口标题），`mainBinaryName` 用 `athena-<id>`。贪吃蛇、中国象棋与北极星、地球同一做法。
5. **发布清单里的应用必须已经在 `ci.yml` 的手动选择项里**（`scripts/check.py` 结构卫生第 6 条）。新进发布的手册类四门课同时补进 CI 的 Tauri 矩阵。

## 后果

- 本版 Tauri 矩阵在北极星、数学工具之外，加入：gtkmm、C++ 教程、中国象棋、贪吃蛇、设计模式、数据结构、算法、数学、408、软件设计师、嵌入式、赛历、九州、地球、协作观察台，以及四本手册精读（Selinger、Siefken、Octave、SymPy）。
- 0151、0153 里「等稳定后再说」不再有效。棋盘和蛇的原生程序仍由各自的 `--native` 检查，安装包打的是教程壳，与 gtkmm 发壳、原生演示另验是同一分工。
- 机器课（Qt）、魔方、C GUI Lab、启动器本身还没有安装包作业，不在这次矩阵里。这是作业还没接上，不是成熟度例外。
