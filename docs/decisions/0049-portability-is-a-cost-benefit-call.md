# ADR 0049：跨平台是成本收益判断，成本过高的整体排除

- 日期：2026-09-15
- 状态：已接受
- 范围：**整个仓库**
- 关系：限定 [ADR 0047](0047-portable-by-default.md)「跨平台优先」的边界；
  [ADR 0048](0048-menubar-launcher-stays-macos-only.md) 是按本文格式写成的第一例

## 背景

ADR 0047 把跨平台写成「选型的硬指标，不是加分项」。这句话管住了该管的事——别为
省事写平台分支、别用只在一个平台可用的库、验证与构建入口三平台都要能跑。但它在
执行中被读成了「三个平台必须对称」，于是出现两种都不划算的做法：

**一是把有真实收益的平台专属功能当成欠账。** 审视仓库时，`launcher/macos` 那个
679 行的菜单栏启动器被列为待砍项，理由是它与跨平台的 Slint 版功能重叠。但菜单栏
常驻、全局热键、预热是 macOS 上每天都在用的收益，为对称砍掉它们，是拿真实便利换
一张整齐的架构图（ADR 0048 已否决这个建议）。

**二是为不受控的上游问题挂永久探测位。** `apps/cpp` 在 Windows 上编不过，卡在
MSYS2 的 giomm 2.86 与 glib 2.90 头文件冲突——本仓库这边没有障碍，倒在 gtkmm
自己的头文件上。CI 里为它留了一个 `continue-on-error` 的 job「持续探测，上游修好
就会自动变绿」。可是 `apps/cpp/AGENTS.md` 本来就写着「当前支持 macOS 与 Ubuntu」：
这个 job 每次 CI 烧掉一段 runner 时间，不产生任何决策价值，只制造一种「我们还在
努力支持 Windows」的假象。

## 决策

**1. 跨平台仍是默认，但判据是成本收益，不是对称性。**

一个软件、一个工具，甚至一个完整的项目，如果跨平台的成本很高，就把它**整体排除
在跨平台之外**，让它在专用平台上发挥最大优势。排除的粒度可以很大——不只是某个
函数里的平台分支。

判断时问三件事：

1. **移植成本有多高？** 成本高到要跟上游的缺陷缠斗，是该排除的信号，不是该硬扛的
   挑战。自己能修的是成本，等别人修的是不确定性。
2. **收益是什么？** 在专用平台上它带来什么别处拿不到的优势。
3. **排除之后那个平台还能不能完成同样的事？** 能，就写明降级路径；不能，就诚实
   声明不支持。

**2. 被排除的东西必须明确写下来。**

ADR 里写清成本、收益与降级；应用文档里写明哪个平台不支持；CI 里**不留假装在支持
的探测位**。含糊比排除更糟——它让人以为支持，直到真去用才发现不行。

**3. 不受影响的部分。**

排除某个组件的某个平台，不等于放松 ADR 0047 的其余约束。仍然成立的是：

- 没被排除的地方，不许为省事写平台分支，优先选把差异自己吃掉的抽象；
- **验证与构建入口始终三平台可跑**（这是开发基础设施，不是功能）；
- 能在构建期解决的不留到运行期。

## 当前的排除清单

| 组件 | 排除 | 成本 | 那个平台怎么办 |
|---|---|---|---|
| `apps/cpp`（GTK4） | Windows | 卡在 MSYS2 giomm/glib 头文件冲突，**上游问题，不受我们控制** | 不支持；`AGENTS.md` 早已声明只支持 macOS 与 Ubuntu |
| `launcher/macos`（菜单栏） | 非 macOS | 整套 AppKit/SwiftUI 实现，无从移植 | 跨平台 Slint 版功能完整，只少菜单栏常驻、全局热键与预热（ADR 0048） |
| `apps/dsa` 的实验编译器 | MSVC `cl.exe` | 命令行参数是另一套，要为它单独写一份编译调用 | Windows 上装 MSYS2/MinGW 或 LLVM 即可，`g++` / `clang++` 都认 |

**仍然按三平台对待的**：`launcher/core` 与 `launcher/gui`、三个 Tauri 应用、
`apps/c`（Qt）、以及全部验证入口。

`apps/c` 与 `apps/cpp` 的对比正好说明判据是成本而不是喜好：两者都是原生 GUI 应用，
但 Qt 在 Windows 上是一等公民、`aqtinstall` 一条命令装得上，成本低就留着；GTK4 在
MSYS2 上要等上游修头文件，成本高且不由我们决定，就排除。

## 后果

- CI 去掉 `cpp-windows`，流水线跑得更快，红绿也重新代表真实结论——留下的 job
  绿了就是真的支持，不再有「实验性、不阻塞」这种中间状态需要每次解释。
- 代价：上游哪天修好了 gtkmm 的头文件冲突，不会再自动被发现。这是可接受的——
  真要重新评估 Windows 支持，本来也需要一次有意识的决定，而不是某天 CI 悄悄变绿。
- ADR 0047 的「已知待清理项」按本文重新梳理：已完成的标掉，被排除的写明排除。
