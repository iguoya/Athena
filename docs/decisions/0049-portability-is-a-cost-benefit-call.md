# ADR 0049：跨平台是成本收益判断，成本过高的整体排除

- 日期：2026-09-15
- 状态：已接受
- 范围：**整个仓库**
- 关系：限定 [ADR 0047](0047-portable-by-default.md)「跨平台优先」的边界；
  [ADR 0048](0048-menubar-launcher-stays-macos-only.md) 是按本文格式写成的第一例

## 背景

ADR 0047 把跨平台写成「选型的硬指标，不是加分项」。这句话管住了该管的事——别为
省事写平台分支、别用只在一个平台可用的库、验证与构建入口三平台都要能跑。但它在
执行中被读成了「三个平台必须对称」，于是出现两种都不划算的做法：

**一是把有真实收益的平台专属功能当成欠账。** 审视仓库时，`launcher/macos` 那个
679 行的菜单栏启动器被列为待砍项，理由是它与跨平台的 Slint 版功能重叠。但菜单栏
常驻、全局热键、预热是 macOS 上每天都在用的收益，为对称砍掉它们，是拿真实便利换
一张整齐的架构图（ADR 0048 已否决这个建议）。

**二是为看不懂的失败挂永久探测位。** `apps/cpp` 在 Windows 上编不过，报的是
giomm / gtkmm 头文件里的类型冲突。CI 里为它留了一个 `continue-on-error` 的 job
「持续探测，上游修好就会自动变绿」，却没人去查那个「上游问题」到底是什么——
后来查清是 MSYS2 的包版本脱节（见下方实测更正），既不是上游未修，也不是平台
不兼容。一个没人读的探测位，烧 runner 时间之余还固化了一个错误认知。

## 决策

**1. 跨平台仍是默认，但判据是成本收益，不是对称性。**

一个软件、一个工具，甚至一个完整的项目，如果跨平台的成本很高，就把它**整体排除
在跨平台之外**，让它在专用平台上发挥最大优势。排除的粒度可以很大——不只是某个
函数里的平台分支。

判断时问三件事：

1. **移植成本有多高？** 成本高到要跟上游的缺陷缠斗，是该排除的信号，不是该硬扛的
   挑战。自己能修的是成本，等别人修的是不确定性。
2. **收益是什么？** 在专用平台上它带来什么别处拿不到的优势。
3. **排除之后那个平台还能不能完成同样的事？** 能，就写明降级路径；不能，就诚实
   声明不支持。

**2. 被排除的东西必须明确写下来。**

ADR 里写清成本、收益与降级；应用文档里写明哪个平台不支持；CI 里**不留假装在支持
的探测位**。含糊比排除更糟——它让人以为支持，直到真去用才发现不行。

**3. 不受影响的部分。**

排除某个组件的某个平台，不等于放松 ADR 0047 的其余约束。仍然成立的是：

- 没被排除的地方，不许为省事写平台分支，优先选把差异自己吃掉的抽象；
- **验证与构建入口始终三平台可跑**（这是开发基础设施，不是功能）；
- 能在构建期解决的不留到运行期。

## 当前的排除清单

| 组件 | 排除 | 成本 | 那个平台怎么办 |
|---|---|---|---|
| `apps/cpp`（GTK4） | Windows | MSYS2 仓库里 glibmm 包滞后于 glib 包（2.86 vs 2.90），**发行渠道的版本脱节，上游早已修复**（详见下方补记） | 暂不支持；等 MSYS2 跟进即可，不需要改我们的代码 |
| `launcher/macos`（菜单栏） | 非 macOS | 整套 AppKit/SwiftUI 实现，无从移植 | 跨平台 Slint 版功能完整，只少菜单栏常驻、全局热键与预热（ADR 0048） |
| `apps/dsa` 的实验编译器 | MSVC `cl.exe` | 命令行参数是另一套，要为它单独写一份编译调用 | Windows 上装 MSYS2/MinGW 或 LLVM 即可，`g++` / `clang++` 都认 |

**仍然按三平台对待的**：`launcher/core` 与 `launcher/gui`、三个 Tauri 应用、
`apps/c`（Qt）、以及全部验证入口。

> **2026-09-15 实测更正。** 此前「`apps/cpp` 在 Windows 上编不过」被笼统记成一句
> 「卡在上游」，实际跑一遍才发现里面混了三类东西，其中两类是我们自己的代码：
>
> 1. `main.cc` 用 `setlocale(LC_MESSAGES, ...)`——`LC_MESSAGES` 是 POSIX 扩展，
>    MSVC / UCRT 的 `<clocale>` 没有这个宏。已改用 `LANGUAGE` 环境变量。
> 2. 26 处 `M_PI`——同样是 POSIX / glibc 扩展。已改用 C++20 的
>    `std::numbers::pi`。日志里那一串 `'yaw' is not captured` 是它的级联报错，
>    随之消失。
> 3. 清掉上面两类后**只剩三个**错误，全部是 `giomm` / `gdkmm` 的
>    `using XxxClass = struct _XxxClass` 撞上 glib 的 `G_DECLARE_FINAL_TYPE`
>    生成的 typedef。根因见下——是包版本脱节，不是平台能力问题；gtkmm 本身在
>    Windows 上是被支持的（GIMP、Inkscape 都这么发）。
>
> **这也不是「Windows 问题」，更不是 glib 的平台兼容问题。** glib 是基础设施，
> 它在三个平台上都能跑；真正脱节的是**发行渠道里两个包的版本**。
>
> 三方对照：本地 macOS 是 glib 2.88.3 + glibmm 2.88.1（匹配），CI Ubuntu 是
> glib 2.88.0 + glibmm 2.86.0（够近），都编得过；MSYS2 是 **glib 2.90.0 +
> glibmm 2.86.0**——glib 往前走了两个版本，glibmm 没跟上。
>
> 上游其实早就修好了。glibmm 2.89.0（2026-08-10）的发行说明写得很清楚：
>
> > Emblem and DBus::ActionGroup: Don't derive gtkmm__Gxxx types.
> > The underlying C classes are final types since GLib 2.89.2.
>
> 也就是说：glib 2.89.2 起把这几个类改成 final type，glibmm 2.89.0 随即调整了
> 包装方式，2.90.0（2026-09-13）已是稳定版。**我们撞上的是 MSYS2 仓库里
> glibmm 包滞后一个多月的窗口，不是上游未解决的问题。**
>
> **也试过在下游用宏抹平，失败了，失败的方式说明了为什么抹不平。** 直觉做法是把
> glibmm 前置声明里的 `struct _GDBusActionGroupClass` 重定向到 glib 生成的名字。
> 实测：原来的三个 `conflicting declaration` 确实消失，换成三个
> `using typedef-name 'GDBusActionGroupClass' after 'struct'`。根因在
> `G_DECLARE_FINAL_TYPE` 的定义里——
>
> ```c
> typedef struct { ParentName##Class parent_class; } ModuleObjName##Class;
> ```
>
> 它生成的是**匿名结构体的 typedef**，不存在具名的 `struct GDBusActionGroupClass`，
> 这正是 final type 的本意。旧版 glibmm 的包装需要具名 Class 结构，两者是类型模型
> 的差异，宏改不出来。而这件事上游正是靠**改包装方式**解决的（不再 derive
> `gtkmm__Gxxx`），所以下游抹不平是必然的。垫片已回滚。
>
> **也试过「不追新、钉住配套版本」，同样实测失败——MSYS2 此刻没有自洽的组合。**
> 把 glib2 从 2.90.0 降到 2.88.3（仓库里还留着旧包）之后，换成 pkg-config 报错：
>
> ```
> Package dependency requirement 'gio-2.0 >= 2.89.3' could not be satisfied.
> Package 'gio-2.0' has version '2.88.3', required version is '>= 2.89.3'
> ```
>
> 也就是说 **gtkmm 4.20 反过来要求 glib >= 2.89.3**。查仓库里的可用版本：
> `glibmm-2.68` 最高只到 **2.86.0-4**（没有 2.89/2.90），而 `gtkmm-4.0` 已经到
> 4.20.0。于是两头都堵：用 glib 2.90 则 glibmm 的头文件冲突，降 glib 则 gtkmm
> 的 pkg-config 要求不满足。唯一剩下的路是**连 gtkmm 一起降到 4.18**，那是三个
> 包的连锁降级，且每次 MSYS2 更新都要重新对一遍——正是本 ADR 所说的「跟上游
> 版本缠斗」。钉版本那一步已回滚。
>
> **连 gtkmm 一起降到 4.18 也试了，同样失败，失败点一字不差**（三个包都降到位：
> glib 2.88.3 / glibmm-2.68 2.86.0-4 / gtkmm-4.0 4.18.0-3，报的还是
> `gio-2.0 >= 2.89.3 could not be satisfied`）。降级尝试全部回滚。
>
> **查包的发布日期之后，这件事的性质才算清楚——它是一个几天的滚动更新窗口，
> 不是任何一方的缺陷。**
>
> | 包 | 版本 | MSYS2 发布 |
> |---|---|---|
> | `glibmm-2.68` | 2.86.0-4 | **2026-05-10** |
> | `glib2` | 2.88.3-1 | 2026-07-30 |
> | `glib2` | **2.90.0-1** | **2026-09-09** |
> | `gtk4` | 4.24.0-1 | 同属新一代 |
>
> 而上游 glibmm 适配 final type 的版本 2.89.0 发布于 2026-08-10，稳定版 2.90.0
> 发布于 **2026-09-13**——距我们撞上它只有两天。也就是说：**MSYS2 在 9 月 9 日
> 把 glib 升到 2.90，而能配套的 glibmm 上游 9 月 13 日才出，下游自然还没打包。**
> 我们正好落在这个窗口里。
>
> 据此更正两处更早的判断：
>
> - ~~「MSYS2 的 glibmm 包自相矛盾——.pc 要求新 glib 却没有新代码」~~。不成立。
>   那个 `gio-2.0 >= 2.89.3` 的下限来自**新一代的 gtk4 / gtkmm**（gtk4 4.24 与
>   glib 2.90 同代），不可能来自 2026 年 5 月打的 glibmm 包。降 glib 会失败正是
>   因为 gtk4 这一代要求它。
> - ~~「上游不修就是修不了」~~。上游早已修好，只是发布得太近。
>
> **再追一层，责任是清楚的：缺的是包依赖声明里的版本约束。**
>
> 「这一层本该由 pkg-config 和包管理器兜住，怎么会让应用开发者操心」——顺着这个
> 问题去看 MSYS2 的 `mingw-w64-gtkmm-4.0/PKGBUILD`：
>
> ```bash
> depends=("${MINGW_PACKAGE_PREFIX}-cairo"
>          "${MINGW_PACKAGE_PREFIX}-cairomm-1.16"
>          "${MINGW_PACKAGE_PREFIX}-glibmm-2.68"   # 没有任何版本约束
>          "${MINGW_PACKAGE_PREFIX}-gtk4"          # 同样没有
>          "${MINGW_PACKAGE_PREFIX}-pangomm-2.48")
> ```
>
> 于是 pacman 认为「装了任意版本的 glibmm-2.68 就算满足」，把 2026 年 5 月的
> 2.86.0 和 9 月的 glib 2.90 装在了一起，**安装阶段一声不吭**。假如这里写的是
> `glibmm-2.68>=2.89`，pacman 会直接拒绝（仓库里还没有满足的版本），使用者当场
> 就知道原因；现在的结果是包装上了、编译时才在别人的头文件里炸，错误信息
> （`conflicting declaration ... GDBusActionGroupClass`）完全看不出跟版本有关。
>
> 所以准确的责任划分是：**glib 走在 C++ 绑定前面几天，是滚动发行版的常态，
> 无可指摘；把不自洽的组合放进系统而不报警，则是打包层的依赖声明漏了约束。**
> 这不该由应用开发者靠逐个降级去试错——那正是包管理器存在的意义。
>
> **gtkmm4 的跨平台没有问题。** MSYS2 打包 glibmm 2.89+ 之后这一格自己就绿，
> 我们一行代码都不用改。真要推动，可做的是向 MSYS2 报一个「gtkmm-4.0 4.20 的
> glibmm 依赖缺少最低版本」的 issue——那是外部动作，需要单独决定。
>
> **所以出路只剩两条**：等 MSYS2 把 `glibmm-2.68` 更新到 2.89+（一个包的事，
> 上游源码 2026-08-10 就有了），或换一个版本同步的分发渠道（vcpkg、gvsbuild）。
> 两条都不需要改我们的代码。gtkmm 本身不是瓶颈——查过上游 meson.build，
> 4.18 与 4.20 对 glibmm 的最低要求都只是 >= 2.75.0。

> 2026-09-15 补记：[ADR 0051](0051-platform-priority-macos-windows-first.md) 之后
> Windows 升为优先平台，上表第一行因此从「次要平台的一处排除」变成「优先平台上的
> 一个缺口」。但查清根因之后，这个缺口的性质也变了：**不是「上游不修就修不了」，
> 而是「MSYS2 的包跟上就好了」**——上游 glibmm 2.89.0 早已修复，我们的代码不需要
> 任何改动。所以 ADR 0051 里那个「要不要换界面技术」的待决问题，现在没有紧迫性。

`apps/c` 与 `apps/cpp` 的对比原本被用来说明判据是成本而不是喜好。查清根因后这个
对比要打个折扣：Qt 那边确实是 `aqtinstall` 一条命令装得上、当天就打通；GTK4 这边
的障碍**不是技术成本，而是 MSYS2 的包版本脱节**，我们这侧无事可做，也无成本可付。
真正的教训是：把「暂时装不上匹配的依赖」当成「这个技术栈成本高」，会导致错误的
选型结论。

> 2026-09-15 验证：`apps/c` 的 Windows 构建当天就打通并转为正式门槛，代价只是两处
> 配置修正（aqt 的模块参数、让 CMake 用 MSVC 而不是 runner 上的 MinGW）。「成本低」
> 这个判断落到了实处，两者的差别不是猜的。

## 后果

- ~~CI 去掉 `cpp-windows`~~ —— 2026-09-15 查清根因后又加了回来，理由变了：它现在
  监测的是一个**具体且预期会变**的条件（MSYS2 把 glibmm 更新到 2.89+），一变绿就是
  「可以支持 Windows 了」的信号。本条原意仍然成立——不留的是**没人读、不产生决策
  价值**的探测位，而不是所有红格子。
- `apps/cpp/meson.build` 增加了 glib 与 glibmm 的配套版本检查：错配时在**配置期**
  说清楚是版本问题，而不是到编译期吐一堆 `conflicting declaration`。这次绕远路的
  直接原因就是那串错误看不出跟版本有关。
- ADR 0047 的「已知待清理项」按本文重新梳理：已完成的标掉，被排除的写明排除。
