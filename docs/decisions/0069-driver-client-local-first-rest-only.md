# ADR 0069：驾考客户端本地优先、统一走 REST API（落地 ADR 0068 决策 2、4）

- 日期：2026-10-02
- 状态：已接受；完成 ADR 0068 决策 2（本地层）、决策 4（离线队列）的客户端侧；
  收紧 0068 决策 3 中「内网内客户端仍可直连 PG」一句——该通道退役
- 影响：`subjects/driver`（数据层、同步、界面、测试）；`practice/nas_admin`（表结构
  管理职责）；CI（driver 作业不再需要 PostgreSQL）
- 延续：ADR 0067（中心 PG 权威）、0068（三层存储、令牌、幂等）、0037（一个应用一个库）、
  0047（跨平台）、0057（完整开发机基线）
- 关联：`practice/nas_admin/docs/driver-api.md`（接口契约）

## 背景

ADR 0068 定了三层存储与离线队列，状态表里明确标着「决策 2 的本地 SQLite 层、决策 4
（客户端）未实现；当前 driver 仍是内网直连 PG、纯在线」。同时 0068 把一个取舍留到了
客户端接入时定：**客户端要同时认识两种后端（内网直连 PG / 外网走 API），还是统一走
API**——原则是不让两种后端各自长出不同的语义。

服务端此时已经就绪：`/api/driver/v1` 覆盖了 `ProgressStore` 的全部数据面（七类追加型
资源、成就、试卷草稿、已读标记），幂等上传与游标拉取都已部署路由器并测试通过。

## 决策

1. **统一走 REST API，内网直连 PG 的通道退役。** 理由：
   - 一条代码路径，语义天然一致——双后端意味着每个业务操作两套实现（SQL 与 HTTP），
     正是 0068 担心的「各自长出不同语义」的结构性来源。
   - 客户端不再持有数据库口令：丢一台设备只丢一个可撤销的令牌（0068 决策 3 的初衷，
     内网直连保留一天，这个风险就多存在一天）。
   - 内网走 `http://192.168.6.1:5000/api/driver/v1`，外网走 Cloudflare 域名（外网另带
     Access Service Token 头）。配置存主、备两个端点，按序尝试；做题是单人低频操作，
     局域网内多一跳 HTTP 的延迟无感。通路断了由本地队列兜住（见决策 2），不再是故障。
2. **本地优先（local-first）：本地 SQLite 是界面的唯一数据面。** 本地库放用户数据目录
   （`AthenaDriver/local.db`），不进仓库；丢了可由全量拉取重建（权威在中心 PG，ADR
   0068 决策 2 的「缓存，可丢可重建」）。断网照常做题；PG 不可达不再是禁用理由——
   0067 第 5 条的「纯在线」在客户端正式终结。
3. **写入走「本地事务 + 待发送队列」，上传幂等、拉取增量。** 每次写入在同一事务里落
   业务表与 outbox（记了题必有队列，不会出现「做了题没记录可同步」）。同步器把队列按
   资源分批（≤500，服务端上限）上传，服务端按业务键去重；拉取按每资源的 id 游标增量，
   合并规则与 0068 一致：事件取并集（业务键唯一索引 + INSERT OR IGNORE）、成就取更早
   时间、草稿按 `saved_at` 新者胜。可变数据（草稿的保存与删除、成就、全部已读）在
   outbox 里按键折叠，同 key 只留最新，上传按入队顺序保序。
4. **待同步状态可见。** 界面常驻显示待发送条数与最近错误（0068 后果的明确要求）；
   队列里发不出去的记录（服务端判 invalid，属程序缺陷而非网络问题）单独标出并停止
   重试，不无限空转也不静默丢弃。
5. **`point_photos` 表退役，照片登记随仓库走。** ADR 0068 已定照片文件随仓库
   （`progress/points/`），登记记录（哪张照片、说明文字）也改成同目录的清单文件
   （`photos.json`），与照片文件同走 git / `launcher sync` 通道，不再进任何数据库。
   API v1 本就不含照片，这样照片在多设备间没有「文件到了、登记没到」的缺口。
6. **表结构管理移交服务端。** 客户端 `_ensureSchema`（DDL）随直连通道一起退役；今后
   表结构变更由 `nas_admin` 侧提供迁移工具，客户端只依赖既有表。多客户端各自 DDL
   本就有「版本不一致的客户端互踩」的风险，集中后此风险消失。
7. **客户端测试不再依赖 PostgreSQL。** 数据层是本地 SQLite，测试各用临时库文件即可；
   同步器的契约测试用本机 `HttpServer` 假一个 API。CI driver 作业删除三平台的
   PostgreSQL 安装步骤（撤销为 0068 决策 5 加的那部分），本机开发也不再需要 PG——
   `check.py` 里的 PG 预检一并移除。0068 决策 5 的精神（测试不碰生产库、并发安全、
   公开约定值）不变，实现手段从「每人一个 PG」简化为「每人一个 SQLite 文件」。
8. **凭据仍不进仓库，配置可跳过。** 客户端配置（端点、设备令牌、可选 Access 头）存
   用户数据目录 `api.json`（POSIX 600）或环境变量 `ATHENA_DRIVER_API`（JSON 串，CI 与
   脚本用）。没配置时不拦启动：界面照常用，数据只在本机，配置屏可从界面再次进入——
   离线产生的队列在配置好令牌后自然补发。这与 0068 决策 1「缺配置弹对话框、不写默认
   值」一致，但不把「没配令牌」当成「不能做题」。

## 后果

- 客户端 `postgres` 依赖、连接固定 zone 的 `PinnedConnection`（fake-async 兼容层）、
  `ProgressUnavailable` 的「禁用做题」语义一并退役；同步不可达降级为状态栏提示。
- 首次在新设备配置令牌后做一次全量拉取（游标从 0），本地缓存即为中心数据的完整副本。
- 服务端 `not_initialized`（表未建）只对全新部署出现：初始化动作改由 nas_admin 侧
  工具承担（本仓库后续补），不再依赖「先用客户端在内网连一次」。
- 本地 SQLite 与中心 PG 的表结构保持同名同列（`photos.json` 之外的十张表），方言差异
  （`::int` 转型、`IDENTITY` → `AUTOINCREMENT`）关在 `progress.dart` 一处。
- 队列里尚未发出的记录，本地库损坏时一并丢失——界面可见的待发条数就是风险敞口；
  正常在线时敞口趋近于零。
