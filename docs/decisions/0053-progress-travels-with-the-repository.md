# ADR 0053：进度库随仓库走，不留在本机

- 日期：2026-09-16
- 状态：已接受；修订 ADR 0037 第 1 条（库放哪），不改它的其余部分
- 范围：**整个仓库**所有学习应用（`apps/*`）
- 依赖：ADR 0037（各应用自管进度库）、ADR 0052（激励与统计是同一条回路）、
  ADR 0047（跨平台优先）、ADR 0057（基线是一台开发机）

## 背景

ADR 0037 把进度库放在**本机**用户数据目录（`AthenaDSA/learning.db` 这类），
并且明确接受了一条代价：「用户在两处分别记录的进度不会自动合并」。那句话讨论的是
**同一台机器上两个应用之间**不共用，没有考虑**同一个人换一台机器**。

使用者提出的正是后者：换台电脑把仓库 clone 下来，代码、内容、教案全在，
掌握度、连续日、战绩、错题本却是空的。

这不只是不方便，它和 ADR 0052 直接冲突。那份 ADR 要求激励只展示由记录派生的量，
并且「记了却不给使用者看，等于没记」。如果记录本身不跟人走，那么换机器之后连续日
从 1 开始、里程碑重新解锁、掌握度回到未知——回路在最外层断了。

数据量不构成障碍：四个应用当前分别是 20–48 KB。

## 考虑过的其他方案

### 1. 把数据目录放到云同步盘（iCloud / OneDrive / Dropbox）

改动最小，只改路径。但 SQLite 放在按需下载、会在后台替换文件的同步盘上有公认的
损坏风险（文件锁不跨设备生效，冲突时会留下 `learning 2.db`）。而且三个平台的同步盘
各不相同，路径解析要按平台分叉——正是 ADR 0047 要避免的那种分支。**否决。**

### 2. 免费云数据库（Turso / Cloudflare D1 / Supabase 等）

使用者明确说「如果有个稳定的互联网免费数据平台，数据存那里也可以，不奢求」。
Turso、D1 兼容 SQLite，看起来改动不大，实则要在六个应用里换驱动、管一份不能进仓库
的密钥、并处理离线——离线时仍需本地库兜底，于是又回到同步问题，比 git 复杂一圈。

**而 GitHub 私有仓库已经就是那个「稳定的免费数据平台」**：仓库、SSH 密钥、推送习惯
都已存在，`git push` 就是上传，还附带版本历史、离线可用、跨平台和零维护。
引入第二个后端不增加能力，只增加要维护的东西。**否决。**

### 3. 事件日志 + 按设备分片 + 重放（SQLite 降为派生缓存）

作答写成追加式 JSONL，每台机器写自己的分片，git 合并零冲突，SQLite 由日志重建。
它能解决**并发写**。但使用者是一个人，顺序使用（一台机器用完推上去，换另一台先拉
下来），并发写不存在。为不存在的问题付六套日志读写和重放层的代价，违反 ADR 0057
「少一条兜底路径，就少一处会悄悄退化的地方」。**否决**（真出现多人或多机并发时再议）。

## 决策

### 1. 进度库放在应用自己目录下的 `progress/`，进版本库

```
apps/<id>/progress/learning.db
```

仍然**一个应用一份库**，各自建表、各自迁移、互不读写——ADR 0037 的核心主张不变，
变的只是库在哪。不共用表、不共用文件、不做跨应用汇总。

### 2. 「在工作树里」的判据是应用根目录下有 `app.json`

工作树里有 `app.json`，打包发行副本里没有（Tauri 只把 `content/` 打进 Resources，
Flutter 打的是 assets）。据此二选一：

| 情况 | 库的位置 |
|---|---|
| 应用根目录下有 `app.json`（仓库工作树） | `<app_root>/progress/learning.db` |
| 没有（打包副本） | 本机用户数据目录，`Athena<App>/learning.db`（0037 的原路径） |

不去判断路径是否可写，也不让应用问自己「我是不是在仓库里」——那两种写法都要猜。
发行副本回落到用户数据目录不是兜底凑合，而是**正确行为**：拿到发行包的人没有仓库，
也不该往别人的仓库里写。

`apps/cpp` 是例外中的例外：它的教学内容一律从 GResource 读，运行期不按文件路径找
随程序分发的东西，所以它没有「应用根目录」这个概念。为它单独加环境变量
`ATHENA_CPP_ROOT`（由启动器在 `app.json` 的 dev 声明里传，见 ADR 0046），
拿不到就回落到用户数据目录。**这不放松「内容只从 GResource 读」**：内容必须与
二进制同版本，进度是使用者自己的东西，两者性质不同。

### 3. SQLite 的伴生文件不进版本库

`*.db-wal`、`*.db-shm`、`*.db-journal` 是未落盘的日志和共享内存，跟着提交会让库在
别的机器上打不开。根 `.gitignore` 排除它们。

### 4. diff 必须可读

`.gitattributes` 里进度库用 `-text diff=sqlite`（不是 `binary`——那个宏会把 diff
一起关掉），配一个把库 dump 成 SQL 的 textconv（`scripts/db-textconv.py`，用 Python
自带的 `sqlite3` 模块，不依赖 `sqlite3` 命令行，Windows 上没有它）。

理由不是好看：万一两台机器都动过、要在冲突里二选一，总得看得见各自记了什么。
textconv 是本机配置、不随仓库走，由 `athena-dev sync` 首次运行时配好。

### 5. 同步用 `athena-dev sync`，只碰 `progress` 路径

```sh
athena-dev sync
```

它做三件事：配好 textconv（幂等）、把各应用 `progress/` 下的变更提交成一个
`progress:` 开头的提交、推送。

**提交只含进度路径**，不连带使用者手上的代码改动（用 `git commit -- <路径>`，
索引里别的东西保持原样）。推送是分支级的，没法只发某几个提交，所以规矩是：
待推送的提交全是 `progress:` 提交才自动推，否则把别的提交列出来交回使用者自己决定。
远端有新提交导致推送被拒时，如实报错并提示 `git pull --rebase`，不自作主张 rebase。

### 6. 冲突的处理方式是二选一，并且承认会丢

单人顺序使用不会冲突。但如果在 A 机答了题没推、又在 B 机答了题，git 会报二进制
冲突，只能选一边，另一边的记录就没了。这个代价写在这里，不用代码去救——救它就是
方案 3 的复杂度。textconv 保证你至少看得见自己在选什么。

## 后果

- 换机器 `git clone` 之后，掌握度、连续日、战绩、错题本都在，ADR 0052 的回路
  在最外层闭合。
- **仓库从此承载个人学习数据。** 如果将来要把仓库公开，这些库必须先处理（移出或
  清空），因为里面是使用者自己的作答历史。这是本 ADR 引入的新约束。
- 每次同步多一个 `progress:` 提交。库很小（几十 KB），压缩后增量更小，但历史会
  变长；`git log` 想只看代码时用 `git log -- . ':!apps/*/progress'`。
- ADR 0037 第 1 条的路径描述被本 ADR 取代，其余（自建、自迁移、不假设外部进程
  先跑过、`--store` 接受并忽略、ID 前缀）全部继续有效。
- 各应用 `AGENTS.md` 里的进度库位置要同步改；发行包的行为没有变化。
- 本机用户数据目录下的旧库不再被读取。迁移就是把文件拷到 `apps/<id>/progress/`，
  一次性动作，不写迁移代码。
