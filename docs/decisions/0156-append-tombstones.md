# ADR 0156：事件表用墓碑表达删除——只标记、不实质删除

- 日期：2026-10-14
- 状态：已接受（使用者 2026-10-14：「append 表没法表达删除，尽量使用增量机制，标记删除，不进行实质删除」）
- 关系：补充 ADR 0155 决策 5。0155 写的是「`append` 按业务键取并集、已有则忽略」，事件因此只增不减；
  本条让事件也能被删除，而不破坏并集的幂等与收敛性。`lww` 的规则不变

## 背景

0155 的 `append` 把「删除」排除在外：应用里真的 `DELETE` 了一条事件（例如 gtkmm 的「重置本章作答」），
同步代理看到的是「行没了」，却不会推出去，服务端和别的设备上这条记录都还在，新装的机器还会拉回来。
重置只在本机生效，与使用者的预期不符。

## 决策

1. **墓碑**：事件的删除是一条新增的事实——同一业务键上带 `deleted` 的一行。服务端把存活的事件标成
   已删，**原 `data` 保留不清**（可审计、可恢复；`lww` 的删除仍清 `data`）。
2. **单向且幂等**：存活 → 已删，不可逆。已删的事件再收到任何写入（重复墓碑、迟到的存活副本、旧设备
   带着旧库同步）一律忽略，不分配新序号。所以多设备、乱序、重复推送都收敛到同一结果，
   且不需要比较时间戳。
3. **客户端**：同步代理扫描时，把事件表里本地消失的行记成墓碑待推送；拉到别处的墓碑时，
   本机存活就删掉，已是墓碑就不动。代理不会让应用重写已删的键（同一业务键重新出现不会复活，
   本机会保留它但不再同步——事件的业务键含作答时间，正常使用碰不到）。
4. **护栏**：事件表在本地**整张为空**时不推断为「全删」。库被重建、重装、从空备份还原时表是空的，
   这表示「本机没有数据」，不是「用户删光了」，否则会把中心的历史整批标成墓碑并传给所有设备。
   代价：用户把某张事件表删到一行不剩，这次删除不会传播；这是有意取舍，墓碑没有真删数据，
   误判可恢复，漏传只需再留一行或手动处理。
5. **应用侧不必改**：沿用 `DELETE`，由同步代理翻译成墓碑；不要求应用加软删除列，也不改 `app.json` 的声明。

## 后果

- 服务端行数只增不减（墓碑占位）；单人规模可忽略。
- 若同步误把事件标成墓碑，中心库里数据还在，把 `deleted` 清回即可恢复；协议本身没有「取消墓碑」，
  因为那会让收敛性依赖时间戳。
- 受益的第一个功能是 gtkmm 的「重置本章作答」，之后任何带删除的事件表自动具备。
