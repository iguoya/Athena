# ADR 0171：增量发版——应用各有自己的版本号，只构建有改动的应用

- 日期：2026-10-20
- 状态：已接受（使用者逐条确认；落地前 0081 原样有效，落地后的第一次发版是 10.1.0）
- 修订：[ADR 0081](0081-unified-release.md) 决策 1 的「全量构建」、决策 2「版本号一个体系」、决策 3「版本号来源」，以及后果里「给拾阶推急修也要全量发版」。0081 原文不改。
- 关系：延伸 [ADR 0168](0168-release-mature-apps-uniformly.md)——进不进发布仍只看成熟度，本篇只改「发布时构建谁、版本号怎么记」。

## 背景

0081 定下一个 `v*` tag、全量构建、一个 Release、一个版本号体系。那时发布的是三个应用。现在 Tauri 矩阵有二十多个应用、每个四个平台，一次发版近百个作业；而 v10.0.0 以来真正动过的 Tauri 应用只有七个左右。

统一的版本号对单个应用也没有语义：没动过的应用每次发版都换一个新数字，动过的应用看不出这次改了多少。使用者的判断是，同一时期不同应用本来就处在不同状态，所有应用打同一个版本不符合现实。

0081 要解决的问题——发版入口只有一个、Release 页不散落、更新器有固定地址——仍然成立，本篇保留它们。

## 决策

1. **一个 tag 仍是一次发版。** 发版号（tag 的版本）写在仓库根 `VERSION`，升级规则不变：有 ⚠️ 条目升主版本，带新功能升次版本，只有修复升修订号。入口仍是 `scripts/release.py`。
2. **每个应用有自己的真实版本号，写在各栈原生清单里**：Tauri 应用是 `tauri.conf.json`，驾考是 `pubspec.yaml`，旧 cpp 窗口是 `meson.build`。CI 不再用 tag 改写它们，只校验。`Cargo.toml` 的版本不动：它一变 `Cargo.lock` 就跟着变，会污染依赖图判断。版本只增不减。
   - 10.0.0 已发布的应用从 `10.0.0` 往上接（它们的安装包是按 tag 写入的 10.0.0，倒退会让已装副本与拾阶更新器认为这是旧版）。
   - 新应用首发取自己的起点：`pocket-cube-solver` 首发 `1.0.0`。
3. **只构建有改动的应用。** 改动集由 `prepare` 在本地算：
   - 应用目录加依赖图——pnpm 用 `--filter "...[上个 tag]"` 取变更包及其下游，Rust 侧按 cargo workspace 的依赖，不在工作区里的应用（驾考、旧 cpp 窗口）按路径。
   - **只有锁定的工具链版本（Node、pnpm、Tauri CLI）变了，才算所有 Tauri 应用都有改动。** 改 `release.yml` 本身不算。
   - **凡是被重新构建的应用必须升版本**，包括只是共享包变了、自己没改的，否则新旧两个安装包会同名同版本。
   - 升多少全自动：看只动了该应用及其依赖路径的提交，有 feat 升 minor，有 ⚠️ 或 `!` 升 major，其余 patch；保留命令行手动覆盖作为出错时的退路。
4. **CI 以版本号变化为准。** `release.yml` 先跑一个 plan 作业：对比各应用清单与上个 tag，版本不同的才进矩阵，用 `fromJSON` 动态展开。应用清单（原来手写的静态矩阵）改为一份数据文件。依赖图只在本地 `prepare` 里算，CI 不重复算，也没有第二份计划文件；重发 tag（移 tag 修复）时结果稳定，因为以提交里的清单为准。
5. **Release 页只放这次构建的应用。** 安装包按应用自己的版本命名；发布说明列出「本次发布」的应用与版本，另有一张「未变化的应用，最新版在 vX.Y.Z」的表，由各应用清单版本最后一次变化的 tag 推出。不复制旧安装包进新 Release。
6. **不做每个应用独立 tag 与 Release 页**（0081 对三套入口的否决保留）。**不提供强制全量的手段**；全量只会是依赖图的自然结果（上面的工具链变更）。拾阶的 `latest.json` 仍只在拾阶被重新构建时更新，没有就保持上一版（0081 决策 4、5 原样）。
7. **时机**：增量机制做完之前，0081 原样生效，不在旧机制上凑数。机制做完后的第一次发版就是增量发版（10.1.0）。

## 后果

- 安装包文件名与内容版本一致，应用的版本号有语义；发版成本从近百个作业降到有改动的应用数。
- 没改动的应用长期不重新构建，发版时没人验证它们还能不能打出安装包。日常验证靠 `ci.yml` 的全量跑（ADR 0064）。Rust 工具链现在是浮动的 `stable`，没改动的应用也不会随新 Rust 重编；是否锁定成固定版本另议，不在本篇。
- `release.yml` 只在打 tag 时才跑，没法单独试。因此计划计算做成独立脚本，`prepare`、`readiness` 与 CI 共用；`ci.yml` 加一个「发布计划演练」，发版前就能验证展开的矩阵对不对。
- 需要改动：`scripts/release.py` 与 `release_readiness.py`（算改动集、升版本、写 `VERSION`；`readiness` 增加「有改动但没升版本」的红灯）、`release.yml`、`scripts/check.py` 结构卫生里对静态矩阵的两条检查（改为读数据文件）、旧 cpp 窗口的 CI 校验（由「meson 版本等于 tag」改为「等于它自己清单里的版本」）、`CHANGELOG.md` 文件头关于「每次发版都全量构建」的约定、`docs/RELEASE-TODO.md`，以及各应用清单的 10.0.0 回填（一个不改行为的提交；回填期间旧 `release.yml` 仍用 tag 覆盖版本，所以无害）。
- 驾考的 `pubspec.yaml` 写 `10.0.0+构建号`；旧 cpp 窗口的 `meson.build` 是它自己的版本，不再等于发版号。
