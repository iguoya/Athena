# ADR 0044：常驻菜单栏的启动器，主程序也只是其中一项

- 日期：2026-09-14
- 状态：已接受
- 影响：新增 `launcher/`；新增仓库根 `app.json`；`apps/*/app.json` 增加
  `icon.symbol`；`scripts/dev-run.sh` 改用绝对路径 exec

## 背景

ADR 0032 把各学科做成 `apps/` 下的独立进程，入口是主程序首页学科图谱上的
领域节点；ADR 0041 / 0042 又把启动路径定成各应用的 `scripts/dev.sh`（热更新，
不碰打包产物）。这条链走下来，日常打开一个学科要付三段时间：

1. 主程序 Athena 自己起来（gtkmm + GResource + SQLite + 图谱布局）；
2. 在图谱上找到那个节点并点下去；
3. 被启动的应用自己构建并起窗口——`tauri:dev` 要跑 cargo 与 vite，
   `apps/c` 要跑 cmake 增量，这一段是数量级最大的。

第 1、2 段的代价还有一个隐含前提：**主程序成了打开别的东西的必经之路**，
哪怕今天根本不学 C++。而第 3 段说明，"启动快"这件事换任何图形技术都解决不了，
它只能靠**不重复启动**来解决——dev server 本来就是常驻服务。

## 决策

1. **新增 `launcher/`：一个常驻 macOS 菜单栏的启动器**，Swift + AppKit/SwiftUI，
   `LSUIElement`（无 Dock 图标、无主窗口）。选原生不是因为渲染快，而是因为
   **形态对**：它一直在内存里，点击延迟趋近于零，状态栏图标、全局快捷键、
   登录自启都是系统一等公民，且不引入任何第三方运行时。
2. **启动器与主程序、各独立应用平级**，自己不承载任何学习内容，不读
   `resources/athena.json`，不碰各应用的进度库。它只做三件事：列出来、
   拉起来、把已经在跑的提到前面。
3. **主程序也是清单里的一项。** 仓库根放一份 `app.json`（与 `apps/*/app.json`
   同构，`match` 指明进程落在 `builddir/`），C++ 教程从此和别的学科一样，
   在同一张列表里被点开，不再是打开其他应用的枢纽。
4. **清单沿用 `app.json`，新增应用不改启动器代码**（ADR 0032 第 6 条）。
   启动器多读两处：`icon.symbol`（SF Symbol）与可选的 `match`；主程序忽略它们。
5. **启动一律走 dev 脚本**（ADR 0041 / 0042）。打包副本会让人不知不觉对着
   旧版本工作，启动器不提供任何指向 `.app` / `bin/` 的入口。
6. **状态从系统实况读，不自己记账**：窗口进程按可执行文件路径前缀匹配
   `NSRunningApplication`，构建期的那一串靠一次 `ps` 识别，再加上启动器
   自己 spawn 的子进程。这样启动器重启、应用被别处启动、进程崩溃三种情况
   都不会让状态说谎。
7. **预热是可选的、每个应用自己设的**：登录后启动器把勾选的应用悄悄拉起来，
   窗口一出现就 `hide()`，点击时 `unhide()` + `activate()`。真正的提速来自
   这里，而不是界面渲染。
8. **主程序图谱入口保留不变。** ADR 0032 第 5 条拒绝的是"在图谱旁边再造
   第二套学科导航"；启动器不是学科导航，它是操作系统层面的"打开哪个程序"，
   两者回答的是不同问题。

## 后果

- 打开任一学科不再需要先启动主程序；主程序的启动时间只有真要学 C++ 时才付。
- 启动器只做 macOS 一份。Linux 上仍按各应用的 `scripts/dev.sh` 和主程序图谱
  启动——启动器是开发回路工具，不随 `.app` / DMG 分发，因此不受跨平台约束。
- 启动器自己是编译产物，`install.sh` 装出来的 `.app` 会停留在安装那一刻。
  这与第 5 条的理由并不矛盾：启动器不承载学习内容，改动频率低；但改了
  `launcher/` 的源码要重新跑一次 `install.sh`，日常调试用 `scripts/dev.sh`。
- 代价是多了一个常驻进程和一份 Swift 代码。它有意保持得很小：没有配置文件、
  没有数据库、没有自己的窗口，全部状态就是 `UserDefaults` 里的预热名单。
