# ADR 0054：内容工作宁增勿删，参考不得用来重划结构

- 日期：2026-09-16
- 状态：已接受
- 适用范围：仓库里所有应用的学习内容、路线图、章节与知识点

## 背景

`apps/atlas` 首版有七张图：两张学科入口（计算机科学与技术、电子信息技术，来源指向
高校培养方案）和五个方向（航天工程高精度实时系统、大模型、机器人、嵌入式软件、
硬件与异构计算）。

使用者当时说的是：「实时控制**特别是**某所的技术体系**作为重要参考**。」

这句话被执行成了重划主干。ADR 0005 第 1 条把取舍标尺直接定为军工院所研制体系，
第 2 条规定「主干六对地图」。七张图塞不进这个格式，于是：

- 两张学科入口的 `id`（`computer-practice`、`electronic-practice`）被岗位专题沿用，
  `title`、`summary`、`nodes` 整体替换——「计算机科学与技术 · 实践主干」变成
  「实时软件与数据路径」，节点从「程序构建与调试、数据结构与并发」变成「有界队列
  与并发调度」这类岗位动作；
- 「中国航天工程 · 高精度实时系统」被拆进弹箭与 GNC 两张新图；
- ADR 0004 又把每个节点里的 `practice` 抽成独立的「实操地图」，于是同一个能力域
  在侧栏出现两次，使用者后来抱怨的「人为割裂成两个菜单项」就是这么来的。

**这件事在界面上和 diff 里都不像删除。** 沿用 `id` 让 git、校验器和 code review
全部把它显示成「这张图被编辑了」；只有使用者看得出「那张图没了，位置上站着另一个
东西」。追查时甚至有人拿「地图 id 集合一个没少」当作「一张都没删」的证据——那只能
证明壳还在。

更糟的是这些改动都发生在 `apps/atlas` 首次入库**之前**，没有任何版本历史。原内容
最后是从 git 悬空对象（`git fsck --unreachable`）里捞回来的，属于运气：只要跑过一次
`git gc`，它就永久消失了。

使用者的结论是一句话：**宁增勿删。**

## 决策

1. **参考只能校准深度，不能决定有哪些东西。** 使用者说「参考 X」「向 X 看齐」时，
   允许的动作是给**已有**条目补充深度、验收口径和取舍依据；不允许据此重划结构、
   删条目、改条目定位或改条目的名字。要动结构，先问。
2. **新方向用新增表达。** 需要一个新视角就新加一张图/一章/一节，不在旧的上面
   覆盖。旧的看起来过时也先留着——可以淡化、降级、移到参考层、在界面上退一层，
   但不删。判断「过时」的通常是执行者，而承担后果的是使用者。
3. **一个 `id` 只装一个东西，`id` 不得改嫁。** 要换定位就新起 `id`。沿用 `id`
   替换内容是这次事故能一路蒙过 git、校验器和人眼的唯一原因。
4. **动内容之前先入库。** 新应用、新内容目录在第一次实质改动前，必须先提交一版
   原样。没有基线的改动等于不可回退，出事时连「改成什么样了」都对不出来。
5. **删除必须显式。** 确实要删，就在提交信息里写清删了什么、为什么、以及在哪能
   取回（分支、tag 或 `refs/recovered/*`）。悄悄替换比删除更难追。

## 后果

- 内容会积累冗余，侧栏和目录会变长。这是有意接受的代价：冗余可以事后整理，
  丢失不可逆。需要收敛时用降级和分组，不用删除。
- 结构调整变慢——因为要先问。这也是有意的：结构是使用者的判断，不是执行者的。
- 这次事故的原内容固定在 `refs/recovered/atlas-pre-adr0005`（旧 `atlas.json`、
  三版 README、两版 `AGENTS.md`、两版 ADR 0001），是正式提交，`gc` 不会回收。
- `apps/atlas` 已按本 ADR 退回七张图，`practice` 回到节点内部（提交 `a090625`）；
  ADR 0004、0005 中被推翻的部分在各自文件里标注。
