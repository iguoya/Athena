# ADR 0073：学习者目录全局化；tiger 以规范 ID 收编（修订 ADR 0072 决策 3）

- 日期：2026-10-02
- 状态：已接受；修订 ADR 0072 决策 3（「首用户 ID 就是字面量 tiger」作废），其余各条
  继续有效
- 影响：`subjects/driver`（注册表位置、收编流程）；`practice/nas_admin`（迁移脚本、后台
  库里的全局用户目录）；将来接入中心 PG 的其他学习应用（共用同一套 ID）
- 延续：ADR 0071（隔离机制）、0072（ID 与显示名分离）、0037（一个应用一个库——用户
  目录不是应用数据，不违反该条）

## 背景

ADR 0072 把 ID 与显示名分开，但为了零迁移让首用户的 ID 就等于字面量 `tiger`。两个问题：

1. **不够规范**：ID 应当与名字毫无关系，tiger 改名后的新绑定关系才真正不怕任何变动；
   5079 条存量记录以规范 ID 绑定，比以「碰巧是用户名」绑定正确。
2. **用户系统是应用共有的**：学习者是「这个人」，不是「驾考里的一个人」。将来别的学习
   应用接入中心 PG（各应用自己决定，ADR 0062），认的应该是同一套用户——不然家里第二
   个人在每个应用里都要重新「起名续用」一遍。

## 决策

1. **本机注册表放应用无关的目录：`Athena/users.json`**（macOS
   `~/Library/Application Support/Athena`、Windows `%APPDATA%/Athena`、Linux
   `~/.local/share/athena`），与各应用自己的数据目录（如 `AthenaDriver/`）平级。所有
   应用读写同一份：谁是这台机器的学习者、上次用谁。应用的本地库、照片、API 配置仍各
   归各（ADR 0032 构建隔离、ADR 0062 约束不继承——共用的只有「人」这一层）。
2. **中心建全局用户目录：后台库里的 `athena_users(id, name, created_at)`。** 用户目录是
   仓库级设施，放在 nas_admin 的库（后台本来管着设备令牌这类跨应用凭据）。暂不开放
   API——当前唯一消费方是迁移脚本与后台自己；别的应用接入时再按需提供。
3. **tiger 以规范 ID 收编，由迁移脚本一次完成**（`driver_migrate_users.py` 扩展）：
   生成 `u_` + 16 位十六进制随机 ID 并打印；driver 库全部表的 `user` 值
   `tiger → u_xxx`（含 achievements / exam_drafts 主键列）；各表 `user` 列的
   DEFAULT 同步改为 `u_xxx`——尚未升级的旧客户端（直连 PG 写入不带 user）继续落到
   正确归属；`athena_users` 登记 `(u_xxx, tiger)`。幂等：重复跑或已收编则跳过。
4. **客户端不再自动猜首用户。** 旧单用户 `local.db` 存在时，选择页提示「输入迁移脚本
   打印的学习者 ID」走续用入口收编；其他机器同理（续用同一个 ID）。tiger 的规范 ID
   生成一次、靠人分发一次，客户端零猜测。
5. 各应用库的 `user` 列语义升级为「全局学习者 ID」；`X-Athena-User` 同。0071 的隔离
   机制不变。

## 后果

- 迁移脚本输出 tiger 的 ID 后需要人工分发一次（各台电脑续用输入、本机收编输入）——
  这是「ID 生成一次、处处一致」的必要代价，比客户端各自猜测后再对账便宜。
- `users.json` 的位置变更对存量无感（多用户版本尚未发行）；`Athena/` 目录从此是仓库
  级约定，各应用文档与 `docs/REPOSITORY.md` 将来提及。
- 0072 决策 3 作废；0072 的「续用输入 ID」入口从备选变成 tiger 收编的必经之路。
