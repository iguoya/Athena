# ADR 0032：异构学习应用作为独立进程共处一个仓库

- 日期：2026-09-10
- 状态：已接受；`apps/CLanguage` 骨架与链路已打通，窗口后端待 LVGL 源码就位

## 背景

C 语言的学习需要"看见内存里发生了什么"，适合用面向嵌入式风格的图形库自己画，
和主程序的 GTK 技术栈没有共同点；它的构建也更适合用 CMake。把它塞进主程序，
两边的依赖、构建和界面会互相牵制；完全分成两个仓库，又会让内容和学习数据割裂。

需要的是：**同一个仓库里，两个平级的独立应用**，主程序能把另一个启动起来。

## 决策

1. **`apps/<Name>/` 一个目录一个独立应用**，自带构建系统、依赖、界面技术和内容。
   目录名按领域取（`CLanguage`），不带实现技术（不叫 `c-lvgl`）——手段会换，领域不会。
2. **构建完全隔离。** 主程序的 `meson.build` 不引用 `apps/` 下任何路径，
   `scripts/check.sh` 也不构建它们；反过来，应用不 include 主程序的任何头文件。
   第三方依赖各拉各的，不进主程序的 pkg-config 依赖表。
3. **内容体系各自独立。** 应用不读 `resources/athena.json`，自己的章节和文档放在
   自己的 `content/` 下。共用的是**方法而不是格式**：ADR 0028 的大纲三层分工、
   0029 的难度与掌握目标、0031 的知识类型这些规范照着用，但字段名、文件格式和
   渲染方式各自定。复用规范零成本，复用 schema 会立刻产生耦合。
4. **唯一共享的基础设施是学习库。** 同一个 SQLite 文件，**路径由主程序解析一次后
   通过 `--store` 传给被启动方**，两边不各写一套平台数据目录规则。表结构的 owner 是
   主程序，应用只读写 `knowledge_progress` 的约定两列，不建表、不迁移。知识点 ID
   以自己的分类前缀打头（C 语言用 `c.`），与 `cpp.*`、`practice.*` 同表共存。
5. **入口就是首页路线图上原有的那个节点，不另造。** 学科图谱里本来就有「C 语言编程」
   这样的领域节点，此前是灰显的「规划中」。给 `DomainKind` 增加 `ExternalApp`：节点
   照常可点，点击时按 `app_id` 找到 `apps/<id>/app.json`，`spawn` 成独立进程。
   领域在路线图上的位置、依赖关系和说明都不变，变的只是"点开之后打开什么"。
   在图谱旁边再加一块应用入口是重复的第二套导航，明确不做。
6. **发现靠 `app.json`。** 主程序扫描 `apps/*/app.json` 拿到标题、图标和可执行文件
   位置；新增一个应用不需要改主程序任何代码。可执行文件不存在时节点仍可点，
   点击给出构建命令。
7. **依赖未就位时要能降级。** `apps/CLanguage` 的 CMake 在 `vendor/lvgl` 或 SDL2 缺失时
   编译占位实现——能启动、能连学习库、不开窗口，用来先验证链路。

## 后果

- 被启动的应用崩溃不影响主程序，换掉窗口库主程序也一行不用改。
- 代价是主程序看不到应用内部的进度明细（它不知道对方有哪些知识点）。真需要时，
  让应用把自己的知识点清单也写进共用库，主程序读它——这是可推迟的决定。
- macOS 打包时应用产物要放进 `Contents/Resources/apps/<Name>/`，路径解析需要一处
  统一处理；当前用 `ATHENA_SOURCE_ROOT` 定位，与主程序既有的源码定位方式一致。
- AI 自测暂不共用。应用要用的话，要么自己调 API，要么把请求转交主程序——都等
  实验内容成型后再定。
