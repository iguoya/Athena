# ADR 0043：「内容必须有出处」跨应用统一规范

- 日期：2026-09-14
- 状态：已接受
- 统一：`apps/mathematics` ADR 0019、`apps/c` ADR 0003、`apps/english` ADR 0007–0009
- 依赖：ADR 0032（异构独立应用）

## 背景

三个独立应用在同一周里各自得出了同一条结论——**教案和题目必须能指到出处，
不能凭印象写**——并各写了一份 ADR。精神一致，落地却分了叉：

| | mathematics | c | english |
|---|---|---|---|
| 引用方式 | **内联**：`source` 写在每题里 | 引用 catalog | 引用 catalog |
| 来源登记表 | **无** | `catalog.json`，对象形式 | `catalog.json`，数组 + license + checked_on |
| 参考材料落本地 | **无**，只存链接 | 有 | 有 |
| 自造/改编分级 | `kind: verbatim/adapted/authored` | **无** | `relation: adapted` 等 |
| 自造配额 | **有**（一节内不过半） | 无 | 无 |
| 机械检查 | 19 处 | **一处都没有** | catalog 完整性 + 词表全表校验 |

**每一家都有一块别家缺的，也都有一块别家已经做对的。** 尤其刺眼的是
`apps/c` 的 ADR 0003 白纸黑字要求「教案、随堂、课后每条都有 `source_refs`」，
却没有任何检查兜底——这正是 mathematics ADR 0019 第 7 节反复强调的那条：
**这类缺陷必须靠机械检查兜住，不能靠写的时候自觉。**

再放任下去，三个应用会长出三套不兼容的「有出处」机制，彼此的经验无法互相
校正——而它们本来在解决同一个问题。

## 决策

### 1. 规范统一，schema 不共用，但共有概念用同一个名字

主仓库 `AGENTS.md` 早已定调：应用之间**共用教学规范，不共用配置 schema**。
本 ADR 遵守这一条——它规定的是**必须满足什么**，不是必须长什么样。各应用的
目录结构、加载代码、检查脚本仍归自己。

**2026-09-15 补充：字段名统一。** 原先各应用给同一个概念起了不同的名字——
出处列表一边叫 `source_refs` 一边叫 `source`，关系一边叫 `relation` 一边叫
`kind`，定位一边叫 `locator` 一边叫 `loc` 一边叫 `ref`。检查器靠
`content-contract.json` 把它们映射到一起，能跑，但读代码的人每换一个应用就要
重学一遍词汇表。共有的概念应该有共有的名字：

| 概念 | 统一字段名 | 说明 |
|---|---|---|
| 一个条目的出处列表 | `source_refs` | 数组。即使只有一条来源也用数组 |
| 与原材料的关系 | `relation` | 取值见第 2 节第 3 条 |
| 指向 catalog 的来源 id | `source_id` | 没有 catalog 的应用可省 |
| 原文位置（节号、页码、定义名） | `locator` | |
| 可点开的链接 | `url` | `english` 另有 `locator_url`，指向定位处而非来源首页 |
| 为什么选它 / 改了什么 | `note` | `authored` 时写为什么没有现成的可用 |

**要守住的分寸：统一的是名字，不是定义。** 每个应用仍然各写各的
`content-contract.json`、各写各的加载代码和类型；只是填进去的名字一致。抽出一份
共享的 schema 文件让各应用引用，那就成了 `AGENTS.md` 明令禁止的耦合——命名统一
是零成本的规范复用，共享定义不是。

数据结构上的差异照旧不强求：`mathematics` 没有 catalog，来源直接写在 `site` 里；
`english` 的变式共享母题来源（第 6 节）。这些是内容治理方式的不同，不是命名问题。

### 2. 五条硬要求

任何应用里**判分或计入掌握度**的条目（题、考核、例题），都要满足：

1. **能指到出处。** 每条自带来源标记，不能只在页面顶部挂一个泛化的「参考资料」。
2. **出处可核对。** 要么是能打开的 URL，要么是仓库内的本地文件路径。
   **凭印象写的出处比自造更糟**——按图索骥扑一次空，之后所有出处都不可信了。
3. **关系要分级，而且分两类。** 每条标明与原材料的关系：

   - **内容来源**（至少要有一条）：`verbatim` / `quoted`（照用原文）、
     `adapted`（改编）、`authored`（自造）。
   - **补充说明**（可选，不能顶替内容来源）：`selection_basis`（为什么选这份
     材料）、`exam_alignment`（对应考纲哪一条）等。

   分两类是 `english` 的实践逼出来的：它实际用了 `quoted` 506 处、`adapted`
   168 处、`selection_basis` 35 处、`exam_alignment` 13 处。后两个根本不是
   「这段内容出自哪」，混进同一个枚举，就没法要求「每条至少有一个内容来源」了。
   字段名可以叫 `kind` 也可以叫 `relation`。
4. **自造是例外，要说明理由，并受配额约束。** `authored` 必须写清为什么外部
   材料覆盖不到；同一节内不得过半。
5. **机械检查兜住以上四条。** 每个应用的内容检查脚本必须实现，并纳入其
   `npm run build` / `check` 流程。

### 3. 参考材料落到本地

`apps/c` 与 `apps/english` 已经这么做了（`content/sources/reference/`），
实践证明有用：写题时能实时对照，不必每次上网，也能用全表校验而不是拿子集充数。
**mathematics 尚未落地，属于待补**。

作者已明确表态：这是自用学习软件，不以「会不会商业化」决定保不保存；公开能查到、
写题用得上的材料就存到本地。但**进入题库的条目必须绑定可核对的具体原文**，
参考目录不能只当事后贴上的泛化标签。

### 4. 推荐形态（不强制，但新写的建议照此）

`english` 那套最成熟，建议作为新内容的参照：

```json
// content/sources/catalog.json —— 来源登记，一处定义
{"sources": [{
  "id": "tatoeba-sentences", "kind": "corpus", "title": "…", "publisher": "…",
  "url": "…", "license": "CC BY 2.0 FR", "license_url": "…",
  "checked_on": "2026-09-14", "local_path": "reference/…"
}]}

// 题目里 —— 只引 id，加定位
"source_refs": [{
  "source_id": "tatoeba-sentences", "relation": "adapted",
  "locator": "Sentence 263227 · contributor CK", "locator_url": "…",
  "note": "改了什么"
}]
```

比内联式好在三点：来源信息不重复、改一处全改、`source_id` 能校验是否存在。
`license` 与 `checked_on` 也值得跟进——前者说明能怎么用，后者记录这条是哪天
实地核对的。

### 5. 跨应用检查器

主仓库 `scripts/check-app-sources.mjs` 扫描 `apps/*/content/`，按第 2 节逐条
核对，输出每个应用的达标情况。

- 它**只读不写**，不参与任何应用的构建，不造成 ADR 0032 禁止的依赖——那条禁的是
  运行时与构建期耦合，开发期的横向检查不在其列。
- 检查器靠 `apps/*/content-contract.json` 认路：那份文件声明「本应用的来源字段
  叫什么、关系分级的取值写在哪、catalog 在哪」。字段名按第 1 节统一之后，各应用
  的契约内容已经高度一致，但**契约文件本身仍归各应用自己**——它声明的是事实，
  不是从别处继承的配置。
- 判分条目的标记字段（`itemMarkers`）**不在统一之列**：`english` 的题面叫
  `prompt`，`mathematics` 有 `stem` / `given` / `statement` 三种，那是各应用内容
  模型的自然产物，强行统一要动几百处内容且伤害表达。
- 没有 `content-contract.json` 的应用会被报为**未接入**，而不是默默跳过——
  沉默地通过是最坏的结果。

### 6. 变式共享母题的来源

一道题的变式（`english` 的 `variants`）自己不写来源，共享母题的。这是合理设计，
检查器按「祖先链上最近的一条」继承。

**这一条是被误报逼出来的**：检查器第一版不认继承，把 471 条变式报成「没有来源
标记」，english 看上去只有 617/1088 达标；补上继承之后是 1088/1088。
误报多了人就会把整项检查一起忽略，所以宁可先把继承这类合理情形认全，再收紧。

### 7. 反面案例：AI 现场出题不能计入掌握度

`apps/cpp` 曾经让 AI 依据知识点说明和源码实时生成选择题，并直接据此判定星级
熟练度（cpp ADR 0015，2026-08-21）。2026-09-16 整条路径被移除，判分输入换成
本节要求的有出处静态题库，AI 退回讲解与答疑（cpp ADR 0054 第 3 条）。废止的
理由写在 ADR 0015 自己的后果一节里：「AI 生成的题目仍可能存在波动，单次结果
不能等同于严格考试」。

这不是 `apps/cpp` 一个应用才有的教训：第 2 节第 1、2 条已经要求「每条自带来源
标记」「来源可核对」——现场生成的题目两条都满足不了，本来就不该通过检查。补
这一节是因为「AI 出题」这个具体形态足够有诱惑力（不用找题、覆盖面自动铺开），
值得单独点名，避免后来的应用重新踩一遍才自己发现。**`authored`（自造）例外仍然
成立，区别在于自造题是人写的、落盘的、可审查可版本化的一条内容；AI 现场生成是
运行时行为，同一学员两次触发可能拿到不同的题，无法复核也无法版本化，不满足第
2 节第 5 条「机械检查兜住」的前提。**

## 后果

- 三份应用级 ADR 继续有效，本 ADR 是它们的**公约数**，冲突时以本 ADR 为准。
- `apps/c` 需要补内容检查脚本——它现在完全靠自觉。
- `apps/mathematics` 需要补 `catalog.json` 与本地参考材料，并把 10 处内联
  `source` 迁到引用式。
- `apps/english` 基本已满足，缺的是 `authored` 配额。
- 三个应用都要加 `content-contract.json` 才能被检查器认出。
- **本 ADR 落地时，`apps/c` 与 `apps/english` 正在被另外的会话改写**，因此
  首版检查器对它们只报告不阻断，等那两边的工作收尾再收紧为硬性失败。

## 首次运行的结果（2026-09-14）

```
c            有问题（只报告）：6/6 条有出处，但关系全部缺失
dsa          未接入 —— 缺 content-contract.json
english      达标（只报告）：1088/1088 条有出处
mathematics  达标：25/78 条有出处，存量豁免 53
```

三条实质发现：

1. **`apps/c` 的每条 `source_refs` 都没有 relation**，只有 `{id, loc}`。
   于是分不出题干是照抄 Beej 原文还是中文改写——而它引的 DIS 是 NC-ND 授权
   （不可派生），一旦某条实际是 verbatim 复制就越界了，现在数据里看不出来。
   它的 ADR 0003 写了「题干用中文改写、不整段复制」，但没有任何检查兜住。
2. **`apps/mathematics` 78 条里 53 条没出处**：35 条是已知的存量练习题，
   另外 **18 条是前置诊断题——那是从来没标过出处的真缺口**，不是历史包袱。
3. **`apps/dsa` 的内容里一个来源字段都没有**，暂未接入。它的条目以代码实验为主，
   「有出处」怎么落到实验上，需要它自己先想清楚再写契约。
