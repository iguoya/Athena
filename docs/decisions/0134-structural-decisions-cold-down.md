# ADR 0134：结构稳定性——`id` 一经入库不改名，结构性决定先草拟冷静再落 ADR

- 日期：2026-10-11
- 状态：已接受（tiger 2026-10-11：批准评审建议落地——「每次组织语义震荡都要付出真实成本……这类决定值得在第一版就花十分钟的纠结，省掉之后半天的连锁修改」）
- 关系：与 [ADR 0129](0129-prefer-quality-over-quantity.md) 互补——0129 管「要不要留」，本篇管「定下来就不折腾」；
  `id` 不改嫁（0054 第 3 条，0129 保留）管的是 id 下的**内容**，本篇约束的是 id **本身**；
  [ADR 0080](0080-reorg-exemption-when-intent-changes.md) 的豁免语义不变

## 背景

1. 0089–0128 约四十篇 ADR 集中在两天内，其中大量是对前一天决定的反转或再反转：
   改名链 0097→0100（softcert→software-designer→software，两天两改名）、0110→0112
   （network 改名又改回）、挂靠 0092→0095→0099（先取消又恢复）、0124→0126（software 的
   圈归属当天反转）。ADR 的修订关系完整、机制健康，但震荡本身有真实成本。
2. 一次 `id` 改名牵动：目录、`app.json` 的 id/binary/进程名、REPOSITORY.md 结构树与名字表、
   根 README 应用表、ci.yml 选择项、跨应用文档引用、并行代理的认知同步。0097→0100 的
   连锁在 c-plus-plus、data-structures 等应用的文档里留下了滞后数日的旧名（2026-10-11
   才补齐）。多代理并行放大了每一次震荡：拿旧名干活的一方在提交时才发现世界变了。
3. 反转的成因不是信息不足，而是**拍板与复核之间没有间隔**：当天决定、当天执行、当天推翻，
   ADR 序列成了草稿本。

## 决策

1. **`id` 与目录名一经入库不改名。** 起名时用足十分钟纠结（全称还是单词、会不会与
   既有缩写冲突），定稿后接受「不完美但稳定」。仅当名字本身有实质错误（误导、拼写错误、
   与外部商标冲突）才允许改名，且必须新立 ADR、逐项列明牵动面（见背景 2 的清单）并一次改齐。
   已写入进度库的知识点前缀不改（既有规则，继续有效）。
2. **结构性决定先草拟、冷静期过后再落 ADR。** 结构性决定指：新增/退役/合并应用、`id`
   与目录名、`parent` 挂靠、`group` 圈归属。流程：先在
   [docs/STRUCTURE-PROPOSALS.md](../STRUCTURE-PROPOSALS.md) 草拟一节（主张、备选、
   牵动面），**落 ADR 与执行之间隔一次复看**——提交 ADR 前重读一遍草稿，仍认为该改才动手。
   大多数「当天反转」会在重读草稿这一步完成，不再消耗 ADR 编号与连锁执行。
3. **使用者显式豁免。** 使用者明说「立即执行」时不受冷静期约束——冷静期防的是未经复核
   的顺手拍板，不是给决策加审批层。
4. **紧急修正不受限。** 已落地的结构性决定被发现有错（执行后才暴露的问题），直接修订
   原 ADR，修订关系照旧；本篇不追求「一次就对」，追求「反转发生在草稿层而不是执行后」。

## 后果

- ADR 序列回归「只增不改」的本义：一篇 ADR 落库即代表一次复核过的决定，而不是讨论的
  第一轮发言。
- STRUCTURE-PROPOSALS.md 从「一次性侦查处置记录」恢复为它的本名所暗示的角色：结构提案
  的草稿层；已关闭的 2026-10-08 侦查记录保留在文首归档。
- 改名类任务的连锁清单有了权威出处（背景 2），下次（万一）改名时照单核对，不再靠回忆。
