# ADR 0058：内容驱动 UI——用有限的块类型承载全部讲解，不按章手写整页

- 日期：2026-09-20
- 状态：已接受
- 统一：`apps/dsa`（块类型架构，已验证）与 `apps/cpp` 的反面案例（按章手写整页）
- 依赖：ADR 0028（学习内容三层）；不改变 AGENTS.md「共用规范、不共用 schema」的边界

## 背景

`apps/dsa` 用一套有限的内容块类型（`lead` / `compare` / `steps` / `predict` /
`practice` / `callout` / `summary` / `quiz`）承载全部讲解，配置数据驱动渲染。
结果：整个前端 4357 行就撑起了 7 章 15 个知识点、113 个讲解块、127 道题和 20 个
实验案例——新增一个知识点的边际成本是「往配置里加一条」。

`apps/cpp` 走的是另一条路：`content: article` 时代之前的历史遗留是一章一份手写
`.blp`，单章 2988 行。结果 74 个知识点里只有 7 个真正写完——不是内容难写，是每
写一节都要先设计并实现一整份专属界面，界面产能成了内容覆盖率的瓶颈。

两个应用面对的是同一类问题（把知识点讲清楚），却因为 UI 组织方式不同，覆盖速度
相差一个数量级。这不是偶然：`apps/design-patterns/README.md` 已经把这条列为「给
未来应用的建议」第一条，说明这个教训具备跨应用的普适性，值得从「给未来应用的建议」
提升为约束现有应用的规范。

## 决策

**编写学习页时，优先设计一套有限、可复用的内容块类型，用配置数据驱动渲染，而不是
每一章/节手写一份专属界面。** 判据很简单：**这一节和隔壁那一节如果只是文字不同，
就不该各写一份界面。** 新增章节前先问「现有的块类型能不能表达这节内容」，答案是
能就复用，不是先复制一份现成页面再改文字。

字段名、块类型的具体集合、渲染方式各应用自定（沿用 AGENTS.md「共用规范不共用
schema」的边界）——本条约束的是**方法论方向**，不是某个具体 schema。

**例外**：内容需要专属可视化或交互、无法用通用块表达时（例如按 `requires` 实时
布局的知识图谱、需要专属渲染管线的曲面演示），专属实现仍然合理——那部分受
ADR 0056（可视化与交互是内容本身）约束，不受本条约束。本条约束的是「讲解正文的
容器」，不是「确有专属价值的可视化」。

## 后果

**得到**：新增知识点的边际成本从「设计并实现一整页」降到「往配置里加一条」，内容
覆盖率不再受界面产能限制。

**付出**：已经用整页硬编码写成的历史内容（如 `apps/cpp` 现有的已完成章节）不必
推倒重来——按 ADR 0054「宁增勿删」，存量内容原样保留，新内容照本条方法论写，旧
内容视精力渐进迁移，不强制一次性重写。块类型集合需要跟着内容需要生长，设计时留
扩展空间，但不必一次性穷举所有可能的表达形式。
