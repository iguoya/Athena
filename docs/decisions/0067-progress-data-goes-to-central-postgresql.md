# ADR 0067：进度数据直连中心 PostgreSQL（driver 先行）

- 日期：2026-10-02
- 状态：已接受；修订 ADR 0053（对已迁移的应用不再适用，对未迁移应用继续适用）
- 影响：`subjects/driver` 的数据层；软路由 PostgreSQL（192.168.6.1:5432）；`launcher sync`
- 延续：ADR 0037（各应用自管库——「一个应用一个库」在中心侧的延续）、0047（跨平台）、
  0057（基线是完整开发机）、0062（约束不继承——其他应用不强制跟进）
- 关联：`practice/nas_admin`（中心 PG 与后台面板的载体，同日落地）

## 背景

ADR 0053 把进度库定为「SQLite 随仓库走、`launcher sync` 用 git 提交推送」。单人、
同步习惯好时它工作正常，但「多平台异地」场景下有两个结构性问题：

1. **分叉无法合并**：两台机器各自做题、各自提交，SQLite 是二进制文件，git 只能报
   冲突，丢掉哪一边都是丢学习记录。
2. **同步是手动仪式**：忘了 pull 就做题、忘了 push 就换机器，都会制造上一条的分叉。
   driver 自己也长过一套 GitHub JSONL 同步（`lib/sync.dart`），本质还是同一类
   「事后搬运」方案。

同一时期，仓库里长出了新的基础设施：软路由（ImmortalWrt，192.168.6.1）上常驻
PostgreSQL 17，`practice/nas_admin` 已验证「本机与路由器共用同一个库」的形态
（pg_hba 放行 192.168.6.0/24 密码连接）。内网直连、外网走隧道的通路也已存在
（cloudflared 在路由器上常驻）。使用者据此提出本 ADR 的核心原则：**个人数据与
项目数据区隔；内网优先直连，离开内网走外网**。

## 决策

1. **个人数据与项目数据区隔**：个人使用记录与统计（做题、考试、成就、通知、草稿、
   笔记）存中心 PG；项目本身的数据（题库、课程内容、图片）照旧随仓库走，不进数据库。
2. **一个应用一个库**：中心 PG 里每个应用一个 database（driver 用 `athena_driver`）、
   一个账号，互不干扰——ADR 0037「各应用自管库、不共用」在中心侧的延续。
3. **driver 先行，其他应用不强制**：第一批只迁移 `subjects/driver`（它有多平台异地
   的真实场景）。其他学习应用是否跟进各自决定（ADR 0062）；未迁移的应用继续适用
   ADR 0053。
4. **连接策略：内网优先，外网兜底**：应用按序尝试内网直连（192.168.6.1:5432），
   不通则走隧道端点。隧道当前用 cloudflared（token 模式，已在跑）；国内体验不稳时
   可换 frp + 国内轻量 VPS——只动「隧道一跳」，应用与库都不动。
5. **纯在线，诚实降级**：应用不再写本地 SQLite。PG 不可达（内网不通且隧道断）时
   做题功能禁用并明确提示，不悄悄降级成「暂存内存、重启丢失」。这是明确的取舍：
   双写缓存加冲突合并的复杂度，正是本决定要甩掉的东西。
6. **旧通道退役**：driver 的 GitHub JSONL 同步不再接线，代码保留作参考；已有做题
   记录一次性迁移进 PG；`learning.db` 迁移后退役，`launcher sync` 不再收集已迁移
   应用的进度路径（对未迁移应用照旧）。

## 后果

- 做题依赖「到中心的通路」：内网几乎零成本，外网依赖隧道质量；通路断时 driver
  不能记录做题。
- 中心是单点：软路由或 PG 宕机时所有平台都不能记录。缓解待办：PG 定期
  `pg_dump`（记在 driver 的 AGENTS 待办里）。
- 「进度库」从此有两种形态（中心 PG / SQLite 随仓库），以应用为单位各自适用，
  索引用状态标注区分，不合并叙述。
