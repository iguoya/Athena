# ADR 0030：知识点级前置依赖

- 日期：2026-09-10
- 状态：已接受；`type_semantics` 章已声明依赖，其他章节留空待写到时再补
- 补充：ADR 0001 的章节级 `prerequisites`

## 背景

`athena.json` 原来只有章节级 `prerequisites`，粒度太粗。真实的学习顺序发生在知识点
之间：`object_lifetime` 要先有 `initialization`，`decltype` 的规则表离不开值类别。
这些关系此前只存在于作者的脑子里和页面的先后顺序里，配置不知道，程序也用不上。

缺了它，两个问题回答不了：**我现在能学什么**（前置已达标的知识点），以及
**我卡在这里是因为哪一步没打牢**（沿依赖回溯）。项目已经有知识图谱和逐知识点的
熟练度，缺的正是这层边。

## 决策

1. **新增 `subchapter.requires`。** 同章内写知识点名，跨章写完整函数 ID；
   生成器统一展开成完整 ID，并把标题一并写进运行时 Catalog，界面不必反查。
2. **生成器做四项校验**：引用必须存在、不能自引用、不能重复、整体不能成环
   （三色 DFS，报错给出成环路径）。
3. **跨章依赖必须与章节 `prerequisites` 同向**：依赖目标只能在本章，或本章的
   （传递）前置章节里。若 A 章的知识点依赖 B 章、而 B 章的前置又是 A 章，
   学习者永远不可能先学到它——这属于内容顺序自相矛盾，直接报错而不是留给运行期。
4. **界面把先修显示为可点击的小标签**，按熟练度区分已学与未学，未学时给一句提示，
   但**不禁用运行入口**。自用平台上跳着学是常态，这里只负责让依赖关系看得见。
5. **只给已经写出教学内容的章节声明依赖**，其他章节留空；空数组是合法状态。

## 后果

- 依赖图是内容质量的检查工具：写 `requires` 时如果发现依赖方向和页面顺序相反，
  说明页面顺序或依赖有一个错了。本章的 `decltype_deduction` 依赖 `value_category`
  就暴露了这一点——页面上 decltype 排在值类别之前。
- 将来可以据此做“下一个适合学的知识点”推荐和卡壳回溯，数据已经就位，不必再改配置格式。
- 依赖只描述知识顺序，不描述实现依赖，也不参与构建；它是内容元数据，不是模块依赖。
