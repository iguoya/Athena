# ADR 0080：应用意图整体改变时，可由应用级 ADR 声明重组豁免（限定 ADR 0054）

- 日期：2026-10-03
- 状态：已接受；限定 [ADR 0054](0054-prefer-adding-over-deleting.md) 第 2、3 条的适用边界，
  0054 原文不改
- 范围：整个仓库；首例是 `subjects/machine`（原 `subjects/c`）的应用级 ADR 0005
- 关系：与 [ADR 0049](0049-portability-is-a-cost-benefit-call.md) 限定 [ADR 0047](0047-portable-by-default.md)
  同类——不推翻原则，只写清它在哪里停下

## 背景

ADR 0054 防的是一件具体的事：执行者把使用者一句「参考 X」读成重划结构的许可，沿用 `id`
替换内容，在 diff 里看不出这是删除。它的解法是「宁增勿删、`id` 不改嫁」。

这条规则没有区分两种情形：

1. **使用者没有决定重组，执行者擅自重组。** 0054 要拦的是这个。
2. **使用者明确决定这个应用的意图整体变了，要求重写。** 例如 `subjects/c` 原来的目标是
   「把 C 教成看见内存」，现在要改成「C 与汇编两条线独立又联合，统一高层与底层」。章集合、
   章序、知识点前缀都要重排。

第二种情形下，继续「只增不改」会留下一批与新意图无关的旧章和旧 `id`，新旧并存反而让课程图
失去主线。使用者原话：「不怕重写，重新组织章节，因为整体意图都改变了。」

## 决策

1. **0054 防的是未经决定的重组，不是使用者明确决定的重组。** 当使用者明确决定某个应用的意图
   整体改变，该应用可以在**自己的应用级 ADR** 里声明对 0054 第 2 条（宁增勿删）和第 3 条
   （`id` 不改嫁）的豁免，允许重写、重组章节与知识点、改 `id`。
2. **声明必须写明三件事**：意图改了什么；豁免范围（哪些内容允许重组）；哪些规则不因此放宽。
   **出处要求（ADR 0043）、各应用自己的语义基准不在豁免之列。**
3. **动手前打 tag 作基线**，命名 `pre-<新id>-reorg`，指向重组前的提交。0054 第 4、5 条继续
   适用：基线先入库；确实删除的内容，在提交信息里写清删了什么、为什么、在哪能取回。
4. **豁免只对该应用、该次重组有效，不是先例。** 不扩大到其他应用，也不改变 0054 第 1 条：
   使用者说「参考 X」仍然只能校准深度，不能被执行成重划。
5. **目前只有一例**：`subjects/machine` 的 ADR 0005。

## 后果

- 0054 的状态栏补「第 2、3 条由 0080 限定」；根 `AGENTS.md` 对应条补一句指向本条。
- 豁免有被滥用的风险，所以门槛是三样同时具备：使用者明确决定、应用级 ADR 写明范围、重组前有
  tag。缺一样就回到 0054。
- 重组之后旧内容不会消失：tag 指向的提交里原样都在，需要时可以取回。
