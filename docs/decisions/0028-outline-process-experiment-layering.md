# ADR 0028：学习内容的三层分工——大纲、过程、实验

- 日期：2026-09-09（同日补充第 6 节「大纲的写作范式」）
- 状态：已接受；`type_semantics` 章已按本决策重写大纲，其余章节待跟进
- 延续：ADR 0024（内容改由 GTK 控件承载）、ADR 0026（Markdown 不约束学习场景）、
  ADR 0027（学习页自足讲解与多媒体）
- 关联：ADR 0012（分类手册合并，`overview_document` 必须收录在 `handbook_documents` 内）

## 背景

ADR 0024–0027 明确了「学习页怎么讲、用什么媒介」，但一直没有界定每个章节那份
Markdown 文档（`chapter.overview_document` 指向的 `*_overview.md`）在整套学习内容里
处于什么位置。历史上它叫「独立参考文档 / 理论讲解文档」，里面混着代码块、语法规则和
API 用法，和原生学习页要做的事大量重叠，边界不清；作者不知道某段解释该写进大纲还是
写进学习页，评审也无从判断一章的内容是否完整。

需要把学习内容自上而下切成职责清晰的三层，并规定方向从哪层流向哪层。

## 决策

### 1. 三层及其职责

| 层 | 载体 | 负责什么 | 不负责什么 |
|---|---|---|---|
| **教学大纲文档** | 一章一份 Markdown（`*_overview.md`），收录在本分类 `handbook_documents` 内，由 `chapter.overview_document` 关联 | 指引大方向：知识点的前因后果、发展脉络、要解决现实编程里的什么问题、达到什么目的、每一小节对应哪类现实麻烦、与其它章节的关系 | 不写具体语法机制、代码示例、API 用法细节；不绑定练习或实验；不规定学习页的标题、顺序或媒介 |
| **教学过程** | 原生学习页 / 学习场景（Blueprint + GTK 模块，遵循 ADR 0026/0027） | 在大纲划定的方向内落实细节与教学目的：讲清每个知识点为什么这样、怎么工作、何时适用、易错在哪，穿插预测与练习，形成「建立框架 → 形成预期 → 实验 → 观察 → 修正」闭环 | 不承担建立全局知识框架的职责（那是大纲的事）；不把真实源码与完整输出挤进正文（那是实验的事） |
| **教学实验** | 章节课程类的 public 成员函数 / 专注实验页 | 结合真实源码，把理解落到可运行、结果可观察的具体体验上，用来验证或推翻预期 | 不替代讲解；不在 UI 或 C++ 里维护第二份教学代码字符串 |

### 2. 方向自上而下，反馈可上溯但不倒置

- 大纲设定「学什么、为什么学、要达到什么目的」；教学过程据此展开细节；教学实验
  据此提供可观察的体验证据。
- 实验和使用中的反馈**可以**揭示大纲的遗漏、错误或认知边界，并推动大纲修正、深化。
- 但**不得**从现有代码实现反推应该教哪些知识点（重申 `AGENTS.md` 既有原则）：出现
  三层不一致时，先按正确的 C++20 语义核对大纲，再让教学过程和实验覆盖确认后的目标。

### 3. 三层可以重复表达，语义必须一致

同一条规则在大纲、学习页、实验里重复出现是可接受的（延续 ADR 0026 第 0 条）；但它的
条件和结论必须一致，以 C++20 为本项目基准。

### 4. 鼓励在大纲文档里使用可视化

大纲讲的是脉络和分类，天然适合图。首选静态 SVG，放 `resources/articles/cpp/images/`，
Markdown 以 `![说明](images/xxx.svg)` 引用，随手册打包进 GResource（`mermaid` 等
运行时渲染方案仍不使用，见 `AGENTS.md`）。演进时间线、「N 个小节 ↔ N 类现实麻烦」的
对应、主线示意图都适合画出来。

### 5. 旧 overview 文档逐份重写

历史上带代码块的 `*_overview.md` 逐份从「参考讲解」重写为纯大纲。
`type_semantics_overview.md` 已完成，作为样板；`reference_overview.md`、
`raii_overview.md`、`program_organization.md` 待跟进。

### 6. 大纲的写作范式：八个固定字段

「讲前因后果、发展脉络、解决什么现实问题、达到什么目的」是方向描述，不是可校验的
契约：作者不知道写到什么程度算完整，评审也无从判断哪里缺了。因此给大纲文档定一套
**固定字段**，每章都回答同样八个问题。

字段不是凭空拟的，取自三套成熟框架：

- **先行组织者**（Advance Organizer，Ausubel 1960）——大纲这一层的学名。它的定义
  特征是"比即将学习的材料更抽象、更概括"，作用是提供认知锚点让细节有地方挂。这解释
  了大纲为什么只谈方向、不谈语法机制。
- **UbD 逆向设计 Stage 1**（Wiggins & McTighe, *Understanding by Design*）——
  持久理解、基本问题、知识与技能。
- **GoF 设计模式模板**——Intent / Motivation / Applicability / Consequences，
  对技术知识点的描述粒度最贴合。

| 字段 | 回答什么 | 出处 |
|---|---|---|
| **痛点** | 没有它之前，现实工程里出什么事 | GoF Motivation |
| **来历** | 何时、为解决什么被引入；后来怎么演进 | 发展脉络 |
| **意图** | 一句话：它承诺解决什么 | GoF Intent |
| **基本问题** | 贯穿全章、要反复自问的 2–4 个开放问题 | UbD Essential Questions |
| **心智模型** | 用什么结构或比喻去理解它 | 先行组织者核心 |
| **判断点** | 实际写代码时它让你做哪些选择 | UbD Skills |
| **边界与代价** | 何时不该用、用了付什么代价 | GoF Consequences |
| **落点** | 它是后面哪些知识的地基 | 比较性组织者 |

约束：

- 八个字段都要出现，顺序可按叙述需要调整，允许合并进同一节，但不得整段缺失。
- 每个字段 1–3 段，可配静态 SVG；仍然不写语法机制、代码示例和 API 细节。
- 末尾保留「小结」节（`AGENTS.md` 对章节正文的既有要求）。
- 固定字段同时是 UI 契约：页面可以按字段做成固定区块，不必再把一整份自由格式的
  Markdown 塞进某个容器。**内容契约先定，页面形态由它推导**——先给未定型的内容找
  UI 位置会反复返工。

## 与手册的区别

分类手册（`category.handbook_documents` 收录的正文文档）是**跨章节**的体系化参考、
完整规则与回查；教学大纲是**单章节**的纲领。二者都是 Markdown、都由 `DocumentView`
阅读，实现上大纲文档本身也收录在 `handbook_documents` 里（ADR 0012 之后手册合并的
结果），本决策不改这个机制，只界定大纲文档的内容职责。

## 后果

- `docs/CHAPTER_CONFIG.md` 6.2 与 `AGENTS.md` 里 `overview_document` 的描述改为
  「章节教学大纲」定位。
- 新增或重写一章的顺序固定为：先定大纲（方向）→ 再做教学过程（细节与目的）→
  再挂教学实验（体验与验证）。
- 评审检查项：大纲是否只谈方向而未陷入语法；八个字段是否齐全；教学过程是否覆盖大纲
  提出的每一个理解目标；每个实验是否对应大纲某一小节且结果可观察。
- 大纲的 UI 呈现暂缓定型：类型与表达式章现在把大纲放在学习页标题栏下的折叠区，那是
  字段范式确定前的过渡形态。字段稳定后再决定最终形态（候选是章节入口页，让先行
  组织者出现在学习之前），不在范式定稿前反复改容器。
