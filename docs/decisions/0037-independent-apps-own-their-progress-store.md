# ADR 0037：独立应用自建进度库，取消共用学习库

- 日期：2026-09-12
- 状态：已接受；取代 ADR 0032 第 4 条
- 影响：`apps/*`、`ui/external_app_launcher`、`MainWindow`

## 背景

ADR 0032 第 4 条把学习库定为主程序与 `apps/` 下独立应用之间**唯一共享的基础设施**：
主程序解析一次路径，通过 `--store` 传给被启动方；表结构的 owner 是主程序，应用
只读写 `knowledge_progress` 的约定列，不建表、不迁移。

`apps/dsa` 落地后暴露了这个约定的问题：

1. **应用的正确性依赖主程序的启动时序。** 应用在拿到 `--store` 时不建表，于是
   "主程序从未启动过、库文件还不存在"这种完全正常的情况下，应用的第一条
   `SELECT` 就会因为表不存在而失败。要修就得让应用也建表，那"owner 是主程序"
   这条约定本身就不成立了。
2. **schema 演进被绑在一起。** 主程序后来给 `knowledge_progress` 加了
   `last_correct` / `last_total`（评定成绩），应用对此一无所知。两边任何一侧
   改表，都要考虑另一侧的读写假设。
3. **它和 ADR 0032 的主张相抵触。** 那份 ADR 的核心是应用必须能脱离主程序
   独立开发与运行；共用一份由对方拥有的库，是把最关键的持久化路径又接了回去。

共用的唯一收益是"首页图谱将来能显示外部应用的完成度"——而这件事至今没有实现，
主程序也根本不认识 `dsa.*` 这些 ID。用一条已兑现的耦合，去换一个未兑现的收益，
不划算。

## 决策

1. **每个独立应用自建、自管、自迁移它自己的进度库。** 库放在应用自己的用户
   数据目录下（`apps/dsa` 用 `<data_dir>/AthenaDSA/learning.db`），无条件
   `CREATE TABLE IF NOT EXISTS`，不假设任何外部进程先跑过。
2. **主程序不再向外部应用传递学习库路径。** `launch_external_app` 只负责
   把应用作为独立进程拉起；`MainWindow` 不再为此解析用户数据目录。
3. **应用仍接受并忽略 `--store`。** 旧版本主程序可能还会传它，应用据此退出
   会让用户莫名其妙看不到窗口。忽略并在 stderr 记一行，不作为错误。
4. **知识点 ID 前缀继续保留**（`dsa.`、`c.`）。它现在只服务于应用自身的可读性，
   但也让将来真要做跨应用汇总时不必重新造 ID。

## 后果

- 主程序首页图谱上的 `ExternalApp` 节点只有「独立应用」徽章，没有完成度——
  这和取消共用之前的实际表现一样，不是新的损失。
- 将来若确实需要在主程序里看到外部应用的进度，走**汇总导出**而不是共享写入：
  应用把自己的完成度写成一份小的只读汇总（例如 `app.json` 旁的一个状态文件），
  主程序读它。这样依赖方向仍然是单向的，应用不必知道主程序的表结构。
- 用户在两处分别记录的进度不会自动合并。这是取消共用的直接代价，接受。
