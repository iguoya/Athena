# ADR 0059：教学实验给骨架，不给白板

- 日期：2026-09-20
- 状态：已接受
- 统一：`apps/dsa` ADR 0003、`apps/cpp` ADR 0053（editable-scaffold-experiments）、
  `apps/mathematics` ADR 0014（渐隐完形第一级）
- 依赖：ADR 0028（学习内容三层，「教学实验」一层的具体落地形态）

## 背景

三个技术栈完全不同的应用，各自独立收敛到同一个实验形态：

- `apps/dsa`：C++ 案例自带接口/类声明与 `main` 驱动，学员只补 `TODO` 函数体，
  验收标准是「不改任何一行就能编译运行」（ADR 0003）。
- `apps/cpp`：知识点挂的骨架案例同样要求「不改任何一行就能编译运行」，编译诊断
  完整展示、不截断（ADR 0053）。
- `apps/mathematics`：推导验算按「渐隐完形」设计梯度，从补最后一步逐级挖空到
  独立完成，第一级就是「完整解答、读懂即可、不作答」（ADR 0014）。

三者面对的问题是同一个：如果实验/练习从空白开始，学员要先解决「怎么搭起一个能
跑的东西」这个工程问题，才能触及真正要练习的知识点——两个问题混在一起，教学
效果被工程门槛稀释，而工程门槛本身通常不是这一节要考察的内容。
`apps/design-patterns/README.md` 已把这条列为给未来应用的建议第二条。

## 决策

**教学实验与需要动手完成的练习，默认提供已经可运行的骨架，学员只补全被明确标记
出来的空缺，不从零开始。** 骨架必须满足「不改任何一行也能编译/运行/提交出一个
合法结果」——这是可机械验收的标准，不是「大概能跑」。

补全的粒度对应知识点的掌握目标：要求「精通」的知识点可以把骨架留得更空，要求
「了解」的知识点骨架可以只留一两处关键步骤。示范与待填可以并存：先给一个已实现
的参考，再留一个同构的变式让学员照做一遍。

具体载体（源码骨架、渐隐完形的挖空表达式、半成品配置）各应用自定，字段名和实现
方式不强求一致——统一的是「给骨架不给白板」这个方法论，不是某种具体格式。

## 后果

**得到**：学员的注意力落在被考察的知识点上，而不是「如何从零搭起一个能跑的
程序/推导」；编译或运行失败时暴露的是学员补全部分的问题，而不是骨架本身的问题，
诊断信息因此可以完整展示、不需要过滤噪声。

**付出**：出题者需要多写一层骨架代码或模板，比直接甩一道题目文字成本更高；骨架
本身也要维护——底层依赖升级、接口变化时骨架要跟着更新，否则学员遇到的第一个
错误来自骨架而不是自己的答案，会破坏「诊断信息就是教学内容」这条前提。
