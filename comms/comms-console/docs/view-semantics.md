# 观察台：对话与决策记录的口径

给 `tools/comms-console` 的「对话」和「任务时间线」用。文件仍是权威，观察台只读（ADR 0166 决策 1、决策 2）。下面每条都是可执行的判定，不用「重要消息」这类说法。

核对用的是 `comms/driver`：22 条正式消息、`chat/cursor.log` 两行、任务进展里的 `review → done`。该舱 `config.json` 的 leader 是 zcode，worker 是 cursor。

## 1. 统一时间线

正式消息（`msgs/*.md`，一条一个文件）和即时 chat（`chat/<名字>.log`，一行一条）放在同一条时间线上（ADR 0166 决策 2「对话」）。

**排序。** 不用正文头的 `created`。它只到分钟（`2026-10-15 23:15`），和 chat 的秒对不齐。正式消息用文件名开头的 15 位 `YYYYMMDD-HHMMSS`（`comms.py` 的 `msg_id`，也是 `reply` 写入的线程 id）。chat 用行首 `YYYY-MM-DD HH:MM:SS`。两边都折成秒再比。同一秒里正式消息在前，chat 在后；再相同就按文件名或整行文本，保证次序稳定。

为什么：ADR 0165 把长效消息和即时 chat 分成两套机制，观察台要并排看，但不能让分钟精度把同一秒里的先后弄反。

driver 例：`20261015-182835__cursor__zcode__科目二建议….md` 的文件名时间是 18:28:35，`chat/cursor.log` 第一行也是 `2026-10-15 18:28:35`。按上面的次序，这条正式消息排在那行 chat 前面。

**不去重回复。** `reply` 会新写一条消息，带 `Re:` 标题和 `thread`（`comms/README.md`「线程」）。它不是原文的副本，两条都留。chat 和正式消息即使文字相近也不合并：一个是即时通道，一个是留档。只丢掉完全相同的投影（ADR 0166 决策 3：舱 + 文件名 + 内容哈希）。同一舱的文件视图里，正式消息以文件名为唯一键；chat 以「时间|发件人|收件人|正文」整行相同才算重复，留第一次出现的那行。

driver 例：`20261016-011500`（zcode 请提交）和 `20261016-011600`（cursor 回复已提交）是两条，标题都带终验，不能并成一条。

**线程折叠。** 折叠键：有 `thread` 就用它，没有就用这条消息自己的文件名时间戳。chat 没有 `thread`，每行单独成条，不按文字去猜它属于哪个正式线程。

driver 例：`20261015-210606` 没有 `thread`，它是根。`20261015-231505` 的 `thread` 是 `20261015-210606`，折叠进这根下面。

## 2. 什么算决策

决策只出现在**任务视图**的强调层，不靠对话里的语气。四条，满足任意一条就进入：

1. **任务发布。** 任务文件的 `created`。发布者记成该舱 `config.json` 的 leader。任务由 leader 创建（`comms/README.md` 归属表；ADR 0165 决策 2）。
2. **验收。** 进展记录里形如 `- [时间] 名字：旧 → 新` 的一行，箭头两端是 `review` 和 `done`，且名字等于该舱 leader。`done` 只有 leader 能标（ADR 0165 决策 2；`comms/README.md`）。
3. **返工。** 同一类进展行，名字后面的说明以 `返工：` 开头。这是打回 review/done 时 `--note` 的强制前缀（`comms/README.md`；`comms.py` 的 `cmd_status`）。
4. **leader 的裁决消息。** `from` 等于该舱 leader，并且（头里有 `task`，或标题含「验收」「解锁」「裁决」「打回」「终验」之一）。worker 发出的消息一律不是决策，哪怕它在复述结论。leader 发给自己、且不满足上面条件的备忘也不是。

为什么：ADR 0166 决策 2 把任务时间线写成「创建、doing、review、done、打回」加上「leader 裁决、返工意见」。doing、交 review 是过程，不是决策；验收、打回、裁决才是。

driver 例：

- 发布：`tasks/T-003-….md` 的 `created: 2026-10-15 18:32`。
- 验收：同文件进展 `- [2026-10-16 01:15] zcode：review → done · leader 终验…`。
- 裁决消息：`20261016-011500`，from=zcode，`task: T-003`，标题含「终验」。
- 不是决策：`20261016-011600` 是 cursor 的回复；`20261015-195448`（zcode→zcode，「T-901 草稿已备」）没有 `task`，标题也不含那五个词。
- 返工：driver 全部任务进展里没有以 `返工：` 开头的行。规则仍按第 3 条匹配，出现才强调。

## 3. 角色标色

颜色按**当前舱**的 `config.json` 取，不按人名写死（ADR 0165 决策 1「角色跟配置走」；ADR 0166 决策 2「leader/worker 角色标色」）。

- `from`（chat 的发件人）等于该舱 `leader`：leader 色。
- 其余 `agents`：同一种 worker 色。worker 之间平级，不再按人分色。
- 换舱就重读那一舱的 leader。同一个人在别的舱可能是 worker。

driver 例：zcode 的 `20261016-011500` 用 leader 色，cursor 的 `20261016-011600` 用 worker 色。

## 4. 噪音

不删除，默认折叠成一行。展开仍能读原文。

- 标题以 `FYI` 开头：不需要回复（`comms/README.md`「消息」）。折叠。
- 标题以 `联络` 开头，或 `ping` 命令发出的联络：折叠。`ping` 是 leader 的在线探测（ADR 0165 决策 1），不是裁决。
- 标题以 `请回` 开头，或标题里有问号：保持展开。这类要人回（同一节 README）。

driver 例：22 条正式消息里，标题以 `FYI` 或 `联络` 开头的是 0 条。应展开的例子是 `20261015-182847`（「必读：科目二审视结论与第一批分工」），它不是备忘，是分工。
