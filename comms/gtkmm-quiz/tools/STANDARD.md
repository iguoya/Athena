# 测验标准版写法（应用 ADR 0011，`guide/gtkmm/docs/decisions/0011-quiz-standard.md`）

先读 ADR 0011，再读 `examples/ch3.py`、`examples/ch6.py`（已通过 check 的范例）。

## 你要交付什么

在 `artifacts/<你的名字>/chN.py` 里写题目规格（Python），**照 `examples/ch3.py` 的结构**：
`INPAGE`（挂在各官方节页后的随堂题）和 `CHECKPOINT`（章末综合题）两个列表，每题是一个 dict，
文件末尾保留 `if __name__ == "__main__"` 里只做 `report()`、**不要调用 `apply()`**（改课表是 leader 的事）。
运行 `python chN.py` 看均衡报告（位置分布、「正确项是最长项」个数、代码题个数）。

题规格字段：`id`（新 id，格式 `<章前缀>-<节缩写>-<序号>`，不得沿用旧题 id）、`page`（官方节页 id；章末题不写）、
`stem`、`code`（可选，读代码题的代码，**别用反斜杠**）、`lang`（默认 cpp，命令行用 bash）、
`right`（正确项）、`wrong`（3 个干扰项，**顺序即最终顺序**）、`pos`（正确项最终位置 0~3）、
`why`（解析）、`ref`（出处说明，指向原文节），章末题另给 `locator`。

## 硬指标（check.py 会强制）

1. 每题有 `why`（解析）：1~3 句，说明为什么对，并点出最常见的错误理解错在哪；引用原文节的依据。
2. 每题 4 个选项；任一答案位置的题数 ≤ ⌈0.4·n⌉（n 为本章总题数，含章末题）。
3. 「正确项是唯一最长项」的题数 ≤ ⌈0.4·n⌉——写完逐题看 `report()` 输出的选项长度，把正确项写短或干扰项补细节，
   让四个选项长度相近、语法平行。
4. 带 `code` 的题 ≥ ⌈n/3⌉。
5. 题 id 唯一。

## 题目质量

- 题型：读代码预测输出/行为约 1/3 以上；辨析（何时用 A 不用 B）、找错（这段代码哪里不对）、机制因果各若干；
  纯定义回忆不超过 1/6。章没有多少代码时（如引言、安装），可用命令行、配置片段、官方示例的几行、
  C 与 C++ 写法对照来做代码题；实在做不出来，在交付说明里写明原因和你建议的题数，由 leader 裁决。
- **所有事实以本章快照为准**：`guide/gtkmm/content/chapters/<章 id>/<节 id>.json`（`blocks[].text` 是英文原文，
  `zh` 是译文；译文可能有误，以英文原文和 docs.gtk.org 语义基准为准）。不要凭印象出题。
- **预期输出必须可核对**：代码题的结论要么直接来自本章原文/官方示例，要么你亲自验证过（`guide/gtkmm/exercise/`
  里的官方示例已可编译，构建目录 `guide/gtkmm/build-exercise/`；或写几行小程序实际编译运行）。
  验证不了的断言不要出。在 `why` 里写明依据。
- 干扰项来自本章真实存在的误解（如把 clicked 当成按下就发出、把容器摆放当成分组），不要写一眼假的凑数项，
  不要用「以上都对/都不对」。
- 题干说清前提（初始状态、谁在调用）。一题只考一个点。
- 术语遵守 `guide/gtkmm/content/glossary.json`（widget=部件、packing=装填、signal handler=信号处理函数 等），
  写完用 `python guide/gtkmm/scripts/glossary.py` 自查（它检查整个应用，只看与你的草稿相关的行）。
- 每章总题数：与旧题数相当（见任务书），不要为凑数而加题；弱题直接删。

## 交付

1. `artifacts/<你的名字>/chN.py` 全部章；
2. `status T-xxx review`，`--note` 写：每章 `report()` 输出的那一行，以及你验证过哪些代码题的预期输出、怎么验证的，
   哪些题你不确定。leader 会逐题复核，不通过的会打回并指出具体题 id。
