# 模块边界检查

本页保留代码组织讨论中可直接用于开发的判断方法。系统现状见 [ARCHITECTURE](ARCHITECTURE.md)，
编码要求见根目录 AGENTS.md。原来的政府组织类比与长篇评注完整保留在
[历史背景](archive/2026-09-09/CODE_ROLES.md)，不作为每次开发的必读材料。

## 新增或拆分前的四问

1. **变化原因**：哪些代码会因同一个需求一起变化？优先放在同一模块，不只按行数切文件。
2. **依赖方向**：这个模块需要认识谁？下层不得依赖窗口，页面之间不得互相持有控件。
3. **接口契约**：协作方是否只需稳定 ID、小数据对象和回调？接口是否隐藏了内部复杂度？
4. **生命周期**：谁拥有数据、控件和任务？回调到达时持有者是否仍在，是否位于正确线程？

## 常见判断

- MainWindow 负责导航与模块生命周期；页面行为、后台执行、SQL、网络和绘制属于各自模块。
- 信息可以通过回调向上返回，依赖仍保持单向；回调不是反向持有窗口的理由。
- 同一用途的稳定协作者可直接合作，只有第二实现或测试替身需求出现时才补接口。
- 提取模块应减少调用者需要知道的内容；只多一层原样转发通常不能降低复杂度。
- 静态布局进入 Blueprint，业务数据与图形呈现分开；不把每一张图都做成一套通用框架。
- 复用应来自已观察到的重复需求。两个教案可以采用不同布局，共享实验执行和资源能力。

架构是否合适，最终由职责、依赖、生命周期和变更成本判断，不由类比或模式名称证明。
