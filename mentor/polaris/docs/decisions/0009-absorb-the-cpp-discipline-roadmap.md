# ADR 0009：吸收 apps/cpp 首页学科路线图，技术体系层扩到八张

- 日期：2026-09-16
- 状态：已接受
- 相关：ADR 0001（实践优先）、ADR 0002（出处与依据契约）；仓库级 ADR 0045
  （`apps/cpp` 没有特权）、0054（宁增勿删）、0055（脱敏）

## 背景

`apps/cpp` 首页有一张手工维护的学科路线图（`registry/domain_graph.cc`）：28 个
节点分计算机与电子信息两侧，每个节点把「讲什么」「为什么学」「难在哪」分三段
写清，标注验证方式（编程 / 开发板 / 硬件仪表）、学习优先级、是否可作入门起点；
34 条依赖各带一段历史渊源与必要性说明，并区分真门槛和「知道渊源会更透彻」的
虚线来路；另有 10 条不建节点的理论科目。

信息密度比 polaris 现有的两张技术体系图（各 6 个节点）高一个量级。但它住在一个
学科应用里，不该承载全平台的学科地图（仓库级 ADR 0045）。使用者决定让 polaris
彻底取代它，并且**随时可能删掉源文件**。

## 决策

1. **原料先落库，再谈改造。** `scripts/extract_cpp_roadmap.py` 已把那张图逐字
   导出到 `content/absorbed/cpp-roadmap.json`（提交 `b481c54`）：相邻字符串
   字面量按 C++ 规则拼接，枚举转小写，`side` / `entry` 由原文的两个 id 集合
   还原。吸收工作从这份 JSON 出发，不再依赖源文件是否还在。手抄 28 个节点 ×
   四段文字外加 34 条理由，必然漏字漏条。

2. **技术体系层从两张扩到八张**，判据是难易层次加知识体系连贯性。一张图塞
   二十个节点，横向会拉到 2500px 以上，只能靠缩放看。**课程知识图谱的张数已由
   ADR 0010 收窄为两章**（计算机 / 电子信息），与原图两侧对齐；下面这张八张表
   是当时的切分方案，六张碎片图的节点已迁入那两章，实践主干两张仍保留：

   | 地图 id | 标题 | 收哪些 |
   |---|---|---|
   | `computer-practice` | 计算机科学与技术 · 实践主干 | 现有 6 个节点，原样不动 |
   | `computer-programming` | 程序设计与算法 | Python、C 语言、C++、数据结构与算法、设计模式、工程实践与工具链、应用实践 |
   | `computer-machine` | 机器与系统基础 | 汇编语言、计算机系统基础、操作系统 |
   | `computer-network-intelligence` | 并发、网络与智能 | Linux 系统编程、并发与并行、计算机网络、网络编程、模型开发 |
   | `electronic-practice` | 电子信息技术 · 实践主干 | 现有 6 个节点，原样不动 |
   | `electronic-circuit` | 电路、器件与制板 | 电路基础、传感器与信号调理、FPGA 与硬件描述语言、EDA · 电路仿真与 PCB 设计 |
   | `electronic-mcu` | 单片机与外设接口 | 51 单片机、STM32、通信协议与总线、FreeRTOS |
   | `electronic-embedded` | 嵌入式、信号与控制 | 数字信号处理、电机控制、嵌入式 Linux、Linux 驱动开发、端侧 AI 部署 |

   **现有两张原样保留，吸收来的 28 个节点自成六张新图。** 一开始的方案是把
   现有 12 个节点按同一把尺子重新分配进新图，算下来它们那 12 条依赖边会全部
   变成跨图边——现有 6 个计算机节点本身就是一条连贯的链（程序构建与调试 →
   数据结构与并发 → 操作系统与网络接口 → 端到端数据管线 → 剖析与可观测性 →
   系统集成与交付），拆开等于打散它。这也正好是 ADR 0054 要求的做法：新方向
   用新增表达，不动已有条目的结构。

   两个原 id 的地图只补新增的必需字段（见第 4、5 条），其余一字不改。

3. **原料要改造到 polaris 的契约上，不放宽契约。** `content` → `stable_definition`，
   `purpose` → `engineering_role`；`practice`、`validation`、`validation_note`、
   `volatility`、`source_refs` 逐个补写。`verify`（编程 / 开发板 / 仪表）连同
   设备条件并入 `validation_note`——它回答的正是「拿什么验」。

4. **新增 `pitfall` 字段承载「难在哪」。** 这是原料里最有价值的部分之一
   （「指针和手动内存管理陷阱多，未定义行为编译器不拦你」）。polaris 没有对应
   字段，与其并进别的字段里稀释掉，不如正式加一个：校验器要求非空，现有 12 个
   节点一并补写。

5. **重要性与必要性由职业目标层反推，不照搬原料的优先级。** 节点新增三项：

   - `priority`：`essential` / `important` / `optional`
   - `priority_reason`：这个等级的理由，**写技术要求本身**（「控制周期内最坏
     延迟与抖动必须可测」），不写单位名（ADR 0055）
   - `targets`：它支撑的职业目标层地图 id，校验器保证引用存在

   原料里的 Core / Recommended / Optional 是通用学习视角的排序，留在
   `cpp-roadmap.json` 里作参考，但不直接采用。换成目标层那套专业方向当判据，
   「这门为什么必学、那门为什么可以缓」才有落点，而不是一句通用建议。

6. **跨图依赖放顶层 `cross_edges`**，保留原料里的渊源说明。图内 `requires`
   不跨图。C 语言在入门图、单片机在 MCU 图，这类关系真实存在，丢掉就是丢信息。

7. **理论科目按方向分配到各图的 `theory`。** 它们不建节点——原图这个判断是对
   的：纯理论科目建成节点，会和可验证的实践科目混成一排。

8. **承载应用写进节点的 `app` 字段。** 原料区分了三种承载方式：已由独立应用
   承载（数据结构与算法 → `dsa`、C 语言 → `c`）、由 `apps/cpp` 的分类承载
   （C++、设计模式、应用实践）、以及规划中。前两种在界面上应当可以直接点进
   那个应用，规划中的降级显示。

## 验收：什么算吸收完毕

删掉 `apps/cpp` 那张图之前，下面每条都要成立，由 `scripts/check.py` 对照
`content/absorbed/cpp-roadmap.json` 逐条比对，不靠人眼：

- 28 个节点全部出现在八张技术体系图里，`content` / `purpose` / `difficulty`
  三段文字无丢失
- 34 条依赖的渊源说明全部落在图内边的 `rationale` 或 `cross_edges` 上，
  强先修与虚线来路的区分保留
- 10 条理论科目全部落在某张图的 `theory` 里
- 五个入门起点在对应图的 `summary` 里说明
- 每个节点都有 `pitfall`、`priority`、`priority_reason`、`targets`，且
  `targets` 引用的目标层地图存在
- `python3 scripts/check.py polaris` 跑绿

## 后果

- 侧栏技术体系组从 2 张变 8 张；职业方向 5 张、职业目标 9 张不变。
- 节点字段变多，详情面板要把「难在哪」「为什么这个等级」「支撑哪些目标」
  展开出来，否则吸收进来的信息在界面上看不见，等于没吸收。
- `apps/cpp` 删掉首页那张图之后首页改成什么，由该应用自己决定（另开 ADR）。
  polaris 这一侧不依赖它——原料已经在库里。
